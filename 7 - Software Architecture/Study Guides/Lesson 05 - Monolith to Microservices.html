Monolith to Microservices

Covers (guest session, part 2): Conway's Law, N-tier layering and the controller / service / repository rule, how clients and servers talk (HTTP, REST, status codes), the monolith, the modular monolith, microservices and their costs, the honest checklist, worked examples, the Prime Video case, five microservice patterns, orchestration vs choreography. No prior lecture attendance needed.

Source: the guest session From Problem to System Design, section 5 (Architecture: monolith to microservices).

Learning outcomes

  • Explain Conway's Law and how team structure shapes architecture
  • Describe N-tier layering and the controller → service → repository dependency rule
  • Describe a request / response, REST conventions and status codes
  • Compare the monolith, the modular monolith and microservices; decide whether microservices are needed
  • Explain the costs of microservices and five microservice patterns; sync vs async; orchestration vs choreography

1. People first: how organisations are structured

Traditionally organisations form functional silos: a BA team, a UI/UX team, a backend team and a DB team, each with its own manager, backlog and vocabulary. Each is excellent at one specialty, and every feature needs all four.

N-tier architecture

One style among many, common wherever teams specialise by function. Not a law of nature.

Conway's Law (1968)

"Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations."(Melvin E. Conway, How Do Committees Invent?, Datamation, 1968.) System boundaries appear where communication is weakest: a UI team, a backend team and a DB team talking through tickets and hand-offs produce a UI, a backend and a database as separate pieces. Choose your team structure like you choose your architecture.

The modern counter-move: cross-functional teams own business capabilities: Team A owns Ordering (backend, frontend, QA, domain knowledge) and Team B owns Payments; each capability is independently owned, built and shipped. Organisational structure can influence architectural structure. Microservices are not a cure for silos; they are what capability-owning teams naturally produce.

2. Inside the server: three layers, one direction

LayerDoesKnows
1 ControllerReceives HTTP, validates input, returns status codes. This is where the API lives.HTTP. Nothing about SQL.
2 ServiceThe rules of the system ("a student cannot join a full course").Neither HTTP nor SQL.
3 RepositoryReads and writes the database. The only place SQL appears.SQL. Nothing about HTTP.

The dependency rule: arrows point one way only. Controllers call services; services call repositories; never backwards and never skipping a layer. The UI never touches the database. This is single responsibility and dependency inversion applied at project scale.

One request, end to end

  1. Browser sends POST /courses/42/registrations.
  2. The framework routes it to the registration controller.
  3. The controller reads the body and calls the service.
  4. The service applies the rule: is the course full?
  5. The repository inserts a row into the database.
  6. The service returns the new registration object.
  7. The controller replies 201 Created with JSON.

The rule at step 4 lives in exactly one place: it works the same whether the request came from a browser, a mobile app, a command-line tool or an automated test. That is the whole payoff of layering.

Day-one decision: what folders do I create?

Package by layerPackage by feature
controllers/ services/ repositories/ models/ config/registration/ (controller, service, repository) courses/ shared/

By feature usually wins for group projects (one teammate owns a folder). Either is fine; no structure is the only wrong answer.

4. Style 1: the monolith

Simple transactions: one database

For a team of four with twelve weeks, the advantages column is worth a lot of marks. Not a binary choice:

1 Monolith2 Modular monolith3 Microservices
One deployable unit, all code together; layers may be messy or clean. Where most projects start.Still one deployment, but internal boundaries are clean enough to separate later. A well-structured monolith can become services later. A tangled monolith cannot become anything.

5. Style 2: microservices

Every arrow is an HTTP call (or a queue message), which is why REST was taught first.

Definition, preciselyA style where the system is a set of small, independently deployable services, each owning one business capability and its own data, communicating over the network.
PropertyMeaningTest
Independently deployableShip it alone, no coordination meetingCan you release it on a Tuesday by yourselves?
Scoped to a business capabilityPayments, ordering, deliveryWould a manager recognise its name?
Owns its dataIts tables are private; others use its APIDoes any other service read your tables? Must be no.
Communicates over the networkREST, gRPC or events; never shared memoryIs every dependency an explicit call or event?
Owned end to end by one teamBuild it, run it, get paged for itDoes exactly one team own its on-call?

Fail any one of the five and you have a distributed monolith: network prices, no independence.

What pushes an organisation to split?

ForceMeaning
1 Release traffic jamTwo hundred developers, one deployment pipeline: every release waits for everyone.
2 Uneven loadOne module is hammered, the rest idle, but you must scale it all together.
3 Blast radiusOne memory leak in one module takes the entire product offline.
4 Team autonomyTeams want to ship on their own schedule with their own technology.

Three of these four are people problems, not technical ones.

Worked example: same checklist, two systems

System A: CampusEats (university food ordering)System B: IslandWide (national delivery platform)
Team4 students, 12 weeks9 teams, 60 engineers
Users / load3,000 students, one campus; about 2 orders per minute at peak2 million nationwide; ordering spikes 20x at lunch
Domain / deploysStill changing every sprintPayments needs same-day hotfixes

VerdictModular monolith: one deployment, one databaseMicroservices: spike isolation, deploy autonomy

The rows that flipped the answer: team count, load shape, deploy independence, ops maturity. The system decides, not the fashion.

IslandWide: which capabilities earn a service? Ordering (20x lunch spike must scale alone), Payments (compliance and same-day hotfixes: isolate), Delivery/dispatch (GPS ping load shape, one owning team), Restaurant and menu / Catalog (read-heavy, cache-friendly, rare deploys). Accounts/profiles and Notifications are candidates with no driver. The discipline: no driver, no service. Reality pass: merge where boundaries cost more than they earn: Accounts join the Ordering service (same team, low load), Notifications become a worker on the queue, Profile + Menu form one Catalog service (a chatty pair always fetched together); Payments and Delivery stay isolated. 6 deployments become 4, roughly a third off the infrastructure bill, because each service has a fixed cost (DB, pipeline, monitoring, on-call). Merging without losing a boundary is architecture, not defeat.

6. The honest part: what the network charges you

  1. The network fails. A method call becomes a request that can time out, arrive twice or vanish; every call site needs a failure plan.
  2. No shared transaction. "Registration saved but notification lost" becomes a design problem; consistency becomes eventual.
  3. Operational weight. Many deployments, service discovery, per-service configuration, debugging across scattered logs.
  4. Boundaries become permanent. Moving a responsibility between services is far harder than moving a class between folders.

A distributed mess is far worse than a monolithic mess; you cannot even read it in one place.

The six challenges in practice

#ChallengeNote
1Debugging across servicesOne request = logs in 6 places; needs correlation IDs and tracing
2TestingIntegration tests need other services alive; contract tests help
3Data consistencyNo joins, no shared transactions; eventual consistency is on you
4API versioningYour change breaks their old client; now you run v1 and v2
5Operations loadEvery service: its own pipeline, monitoring, alerts, secrets
6Local developmentA day-one teammate must run 12 containers just to log in

Real world: the return trip

Prime Video, 2023: a video-quality monitoring system built from distributed components (orchestrator, frame grabber, defect detector, aggregator) paid orchestration cost and data transfer on every hop. Collapsing the steps into one process (function calls, no network, no per-hop state) gave a 90 % cost reduction and it scaled further. Also Segment, 2018: "Goodbye Microservices" collapsed about 140 services into fewer, bigger ones for the same reason: overhead outgrew the benefit. Every boundary has a price; pay it only where it earns its keep.

Microservices are not an upgrade. They are a trade-off."You shouldn't start a new project with microservices, even if you're sure your application will be big enough to make it worthwhile." (Martin Fowler, MonolithFirst, 2015)

7. If you do split: patterns and communication

Five microservice patterns worth knowing

PatternIdea
API GatewayOne front door: clients call the gateway, which routes to services.
Database per serviceEach service owns its data; no shared tables, ever.
Service discoveryServices find each other by name through a registry, not hard-coded IPs.
Circuit breakerStop calling a service that keeps failing; fail fast to a fallback.
Async messagingSend a message to a broker and move on; the receiver processes it later.

Patterns are vocabulary, not obligations: name them in a report only where they earn their keep.

How services talk

Synchronous: the caller waitsAsynchronous: fire and move on
REST (simple, universal) or gRPC (fast, typed, internal). Use when the answer is needed now: "authorise payment" before confirming the order.Events via a broker: OrderPlaced → queue → whoever cares. Use when nobody is waiting: receipts, notifications, analytics, loyalty.

Per interaction ask: is anyone waiting for this answer? (A system built entirely around events as its backbone is event-driven architecture, a separate style.)

Orchestration vs choreography

Orchestration (a conductor)Choreography (a dance)
HowA central orchestrator calls Payment, Kitchen, Delivery in turnEach service reacts to the previous event: OrderPlaced → PaymentTaken → MealReady ...
ProsFlow visible in one place; clear error handlingNo central coupling; add steps freely
ConsThe conductor knows and couples to everyoneNobody sees the whole flow; errors scatter

Rule of thumb: orchestrate money and critical workflows (payments need one clear owner of failure); choreograph broadcasts (notify, analyse, reward). The pattern name for distributed workflows is saga. Ask of every workflow: who needs to see it, and who owns its failures?

Anatomy of one well-designed microservice (Payment service)

  1. Pick one business capability (payments, not "utils").
  2. Define the API contract first (POST /payments, GET /health), then build in parallel.
  3. Own your data: your tables are private.
  4. Choose edges: sync where waiting, async where not (emits PaymentTaken).
  5. Plan failure: timeouts, retries, idempotency.

Config lives in .env. Acid test: can you deploy it alone, on a Tuesday, without a meeting?

How big is "micro"?

Nano-servicesCapability-sizedDistributed monolith
One function per service (AddTax svc, FormatDate svc): network cost exceeds business value; ops load explodes.Payment service: everything payments, nothing else. One team, one reason to change, deploys alone.Services sharing a DB that must deploy together: network tax plus coupling kept; worse than a monolith.

Split along capabilities the business would recognise, never along lines of code.

Key takeaways Conway's Law: systems copy the communication structure of the organisation. Layer the server (controller → service → repository), keep rules in one place. REST: nouns in URLs, verbs in methods, correct status codes, idempotency. Start with a monolith, aim for a modular monolith; split into microservices only when there are real drivers (release jams, uneven load, blast radius, team autonomy) and you can afford the operations. Microservices cost: network failures, eventual consistency, operational weight, permanent boundaries. Patterns: gateway, DB per service, discovery, circuit breaker, async messaging; orchestrate money, choreograph broadcasts.

Written questions

W1. Explain Conway's Law and how it relates to microservices.

Organisations that design systems produce designs that copy their communication structures: boundaries appear where communication is weakest (separate UI, backend and DB teams give separate UI, backend and database pieces). Cross-functional teams that own business capabilities (ordering, payments) naturally produce independently owned services, so microservices follow from capability-owning teams and are not a cure for silos.

W2. Describe the controller, service and repository layers and trace a registration request through them.

Controller: receives HTTP, validates input, returns status codes. Service: business rules (a student cannot join a full course). Repository: reads and writes the database, the only place with SQL. Request: browser POST /courses/42/registrations, routed to the controller, which calls the service; the service checks the course is not full; the repository inserts a row; the service returns the registration; the controller replies 201 Created with JSON. The rule lives in one place and works for any client.

W3. Compare monolith, modular monolith and microservices and give the decision checklist for choosing microservices.

Monolith: one deployable unit, simple to build and debug, one-DB transactions, but everything scales and deploys together. Modular monolith: one deployment with clean internal boundaries (best for small teams). Microservices: independently deployed capability services with their own data and team, giving independent deploys, scaling and failure isolation at the cost of network complexity, eventual consistency and operations. Need them when several teams block releases, one part needs 10x scaling or different tech, you can run 24/7 ops and boundaries are stable; avoid them with one small team, a changing domain, no ops or no users yet.

W4. List the costs of microservices and five patterns used when splitting.

Costs: network failures, no shared transaction (eventual consistency), operational weight (pipelines, monitoring, discovery), permanent boundaries; challenges include debugging across services, testing, API versioning and local development. Patterns: API gateway, database per service, service discovery, circuit breaker, asynchronous messaging.

W5. When should communication be synchronous and when asynchronous? Contrast orchestration and choreography.

Synchronous (REST/gRPC) when the caller needs the answer now (authorise a payment). Asynchronous (events via a broker) when nobody is waiting (email receipts, notifications, analytics). Orchestration uses a central conductor, giving a visible flow and clear error handling but coupling to everyone (use for money and critical workflows); choreography has services react to events, giving loose coupling but a hidden flow and scattered errors (use for broadcasts).
