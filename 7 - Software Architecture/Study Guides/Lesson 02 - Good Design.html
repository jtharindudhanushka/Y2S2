Good Design, Architects and SOLID

Covers: cohesion and coupling, architecture vs design vs design patterns, why architecture matters, architect vs developer vs tech lead, the architect's responsibilities, quality attributes, ATAM, architectural patterns, and the five SOLID principles with examples. No prior lecture attendance needed.

Learning outcomes

  • Explain the characteristics of a good design: high cohesion and low coupling
  • Distinguish software architecture, software design and design patterns; analysis vs design
  • Explain why architecture is needed and what the architect does
  • Define quality attributes and describe how an architecture is evaluated (ATAM)
  • Define an architectural pattern, list the common ones and explain why they matter
  • State and apply the five SOLID principles

1. Characteristics of a good design

High cohesion

General meaning: the state of sticking together, forming a united whole, working well together. In software: the software is divided into modules developed independently, each capable of performing some specific functionality. For the software to be efficient, each module must have high cohesion: everything inside it belongs together and serves one purpose.

Low coupling

General meaning: something that joins two objects. In software, coupling is the connection between two modules; the measure of the degree of interdependency of two modules on each other. A good design has low coupling: modules depend on each other as little as possible, so a change in one rarely forces changes in another.

Kitchen analogy (from the lecture)A chef (high cohesion) does all the cooking tasks: chopping, seasoning, plating. The chef does not need to know how the dishwasher works internally; they hand dirty plates through a small, well-defined opening (low coupling) and the dishwashing station handles the rest.

3. Why do we need software architecture?

  • Any software has a significant impact on the business of an organisation.
  • One of the main reasons for software failure can be the selection of the wrong architecture pattern.
  • Without a formal architecture, teams end up with code that lacks clear roles, responsibilities and relationships between its parts.
  • Planning an architecture lets you analyse risks beforehand and avoid adverse impact on the business.

6. Evaluating an architecture before building it: ATAM

Architects stress-test designs on paper using structured walkthroughs; the best known is ATAM, the Architecture Trade-off Analysis Method.

7. Architectural patterns

DefinitionAn architectural pattern is an outline that lets you express and define a structural schema for all kinds of software systems: a reusable solution providing a predefined set of subsystems, roles and responsibilities, including the rules and roadmap for relationships among them. It helps address concerns such as performance limitations, high availability and minimising business risk. It is a rough image or blueprint of the system.

Common patterns (the lecture's list)

  • Monolithic architecture: the entire system is built as one large application.
  • Multi-layered architecture
  • MVC architecture
  • Event-driven architecture
  • Client–server architecture
  • Microservice architecture

For each pattern the lecture asks you to know: the pattern, its usage, its shortcomings, and example applications. A first overview (the lecture itself develops only the monolith; the detailed comparison continues in Lessons 5 and 6):

Why architectural patterns matter

  1. Defining the basic characteristics of an application; 2. Maintaining quality and efficiency; 3. Providing agility; 4. Problem solving; 5. Enhancing productivity.

8. SOLID principles

SOLID is a set of five principles of object-oriented programming and design. Goal: build software that is maintainable, extendable and easy to understand. Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. All five fight the same enemy: coupling.

S: Single Responsibility Principle

A class should have only one reason to change. Non-technical: a restaurant cashier only handles billing, not cooking or cleaning; if the menu changes, the cashier is unaffected.

// Wrong: one class does login AND emailing
class UserService { login(user, password) {...}  sendEmail(message) {...} }

// Right: one responsibility each
class AuthService  { login(user, password) {...} }
class EmailService { sendEmail(message) {...} }

O: Open/Closed Principle

Software entities should be open for extension, but closed for modification. Non-technical: a power socket accepts new appliances without rebuilding the electricity system. Wrong: an if-else chain edited for every new payment method. Right: depend on an abstraction and add a new class.

interface Payment { process() }
class CreditCardPayment implements Payment { process() {...} }
class PayPalPayment     implements Payment { process() {...} }

class PaymentProcessor {
  processPayment(payment: Payment) { payment.process() }   // never edited for a new method
}

L: Liskov Substitution Principle

Subclasses should be replaceable for their parent classes without breaking the system. Non-technical: a car rental promising a "vehicle" should let you drive a car, van or truck without surprises.

// Wrong: Penguin breaks the Bird contract
class Bird { fly() {...} }
class Penguin extends Bird { fly() { throw Error("Can't fly") } }

// Right: redesign the hierarchy
interface Bird { eat() }
interface FlyingBird extends Bird { fly() }
class Sparrow implements FlyingBird { fly() {...} }
class Penguin implements Bird { eat() {...} }

I: Interface Segregation Principle

Clients should not be forced to depend on methods they do not use. Non-technical: a phone has separate apps (camera, messaging) so you need not install one giant app for one feature.

// Wrong: a Printer is forced to implement scan() and fax()
interface Machine { print()  scan()  fax() }

// Right: small interfaces
interface Printer { print() }   interface Scanner { scan() }   interface Fax { fax() }
class SimplePrinter implements Printer { print() {...} }

D: Dependency Inversion Principle

Depend on abstractions, not on concrete implementations. Non-technical: a car depends on a general "fuel system", not specifically on petrol or electric; it works with any that provides energy. Wrong: a high-level class created directly on a low-level class. Right:

interface Database { save(data) }
class MySQLDatabase implements Database { save(data) {...} }
class MongoDatabase implements Database { save(data) {...} }

class UserRepository {
  db: Database
  constructor(db: Database) { this.db = db }   // injected
  saveUser(user) { this.db.save(user) }
}
LetterOne-line test
S"Does this class have more than one reason to change?"
O"Can I add behaviour without editing tested code?"
L"Can any subclass stand in for its parent safely?"
I"Is any client forced to depend on methods it never uses?"
D"Does my high-level code depend on a promise (interface) rather than a product?"
Key takeaways Good design = high cohesion, low coupling. Architecture gives enough detail to produce a design; design gives enough detail to implement; architectural patterns are blueprints (design phase), design patterns are implementations (build phase). The architect decomposes the system, analyses trade-offs, communicates, owns quality attributes, documents decisions and keeps the roadmap. Evaluate architectures with scenarios (ATAM). SOLID: SRP, OCP, LSP, ISP, DIP.

Written questions

W1. Explain cohesion and coupling and why a good design has high cohesion and low coupling. Use the kitchen analogy.

Cohesion: how strongly the parts of a module belong together; coupling: the interdependency between modules. High cohesion makes modules do one specific function; low coupling makes changes local and modules independent. Analogy: the chef does all cooking tasks (high cohesion) and hands plates through a small well-defined opening to the dishwashing station without knowing how it works (low coupling).

W2. Distinguish software architecture, software design and architectural vs design patterns.

Architecture is a plan with enough detail to produce a design; design is a plan with enough detail to implement. An architectural pattern is a blueprint used in the designing phase and is the base everything adheres to; a design pattern is an implementation approach in the building phase, structuring classes to solve common problems.

W3. Compare a developer, tech lead and software architect and list six responsibilities of an architect.

Developer: implements features, sprint horizon, function/class design. Tech lead: team execution and code quality, sprint/release, task breakdown and standards. Architect: system structure and long-term integrity, months to years, boundaries/tech stack/integration. Architect responsibilities: system decomposition, trade-off analysis, stakeholder communication, quality attribute ownership, decision documentation, technical roadmap.

W4. Explain ATAM with an example scenario.

The Architecture Trade-off Analysis Method evaluates a design on paper: identify scenarios (e.g. 10x traffic spike during a sale), map them to quality attributes (scalability, performance), analyse how the current architecture responds, and surface risks and trade-offs (where it breaks and the cost to fix).

W5. State the five SOLID principles with a violation example for any two.

SRP: one reason to change. OCP: open for extension, closed for modification. LSP: subclasses replaceable for parents. ISP: no forced dependence on unused methods. DIP: depend on abstractions. Violations: a class that both logs users in and sends emails (SRP); a Penguin subclass of Bird whose fly() throws an error (LSP); an if-else chain edited for each new payment method (OCP).
