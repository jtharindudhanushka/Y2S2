C4 modelSimon Brown. Four zoom levels: 1 Context (users + external systems), 2 Container (web/mobile apps, APIs, databases + protocols), 3 Component (controllers, repositories, auth services inside one container), 4 Code (classes / implementation).
UniMart Stage 1Actors (seller, buyer, email verifier, payment gateway, email/SMS). 3 NFRs traced to text: availability in textbook rush; payments never lost/double-charged; low cost, fast delivery.
UniMart monolithLayered (presentation, business logic with Auth, Catalog, Messaging, Orders/Payments, Reviews, Notifications; data access; single DB) on one VM. Reflection: one crash takes everything; scale everything to scale search; one-line fix goes through the whole pipeline.
Growth crisis causesSearch leak crashed app = shared process / failure domain. Payments vs Catalog DB = shared database. 3-day copy change = shared deploy pipeline. Conflicting changes = shared codebase.
MicroservicesAuth, Catalog, Messaging, Orders & Payments, Reviews, Notifications; each owns data; API gateway; sync Orders→Auth; async events (OrderPlaced, PriceDropped, NewMessageReceived, OrderCompleted) on the bus.
Trade-offsBetter: independent deploys, fault isolation, DB choice, team autonomy. Harder: six pipelines, network failures, no single ACID transaction, service discovery and monitoring, API contracts.
Event-driven notificationBroker (RabbitMQ / Kafka). Buys decoupling and resilience; costs traceability and eventual consistency.
SOA vs microservicesSOA: heavier shared middleware (ESB), coarser services. Microservices: independent, fine-grained, lightweight comms, own data. Serverless fits a nightly report, not real-time messaging.
Decision memoMonolith right at Year 0; crisis from shared process/DB/pipeline/code; partial decomposition (Orders & Payments first); next problem: distributed transactions and cross-service monitoring.
Course registration problemsLast-seat race (transaction + constraint); client tampering (server-side validation); double-click (idempotency, unique constraint); read-heavy catalogue (cache); email delay (queue / async); single DB (replica, redundant instances).
Registration APIGET /courses; GET /courses/42; POST /courses; PUT/PATCH /courses/42; DELETE /courses/42; GET /students/10/registrations; POST /courses/42/registrations (retry-risk: idempotency).
Decision chainRequirement → problem/risk → quality attribute → architectural decision → mechanism.
ZippoProblems: shared DB locks (location writes vs matching reads), synchronous payment in trip completion, no queue. NFRs: 3 s matching (95 %), 75,000 location writes/s, 99.95 %, zero double charge, data residency, 2G, extensibility, observability. Solution: separate location pipeline + geo-index, async idempotent payments with circuit breaker, per-country payments, small payloads for 2G, tracing.
Exam tipFor a "monolith to microservices" question: diagnose causes first (shared process, DB, pipeline, codebase), propose boundaries by capability and data ownership, label sync vs async, and include the real costs.
