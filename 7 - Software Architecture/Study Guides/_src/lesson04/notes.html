Its spine: Problem → Requirements → Domain → Architecture → Quality attributes → Components → Trade-offs → Communication → Technology. "Architecture is a chain of reasoning, not a diagram you draw at the end."

Learning outcomes

  • Place architecture in the life cycle and decide which decisions are architectural
  • Compare big up-front design with incremental design
  • Separate functional from non-functional requirements and identify architectural drivers
  • Move from a problem domain to components, data and APIs
  • Apply cohesion, coupling and SOLID at project scale, and avoid over-engineering (YAGNI)

0. Why bother? Two codebases

You join a team in week 6. Project A: app.js (2,400 lines), helpers.js (900), stuff.js, final_v3.js, test_backup.js: everything talks to everything. Project B: controllers/ services/ repositories/ models/ tests/ docs/decisions/: each part has one job. Which do you want? Also: under 10 % of a typical modern application is code its own developers wrote; the rest is frameworks, libraries and packages. Knowing what to reuse, what to build and where to deploy is an architectural decision.

1. From SDLC to software architecture

Architecture is not one isolated phase. It begins when we ask "what kind of system do we need to build to solve this problem?" and decisions continue through implementation, testing and maintenance. Requirements and domain understanding flow down (client: what needs solving → architect: how to solve it well → developers: building it); feedback from building flows back up.

What is an architectural decision?

DefinitionArchitecture is the set of decisions that are expensive to change later. Test: how expensive would this decision be to change in week 10? There is no universal best architecture, only better and worse fits for a given problem. Architecture exists whether you plan it or not; unplanned just means accidental.

Big up-front design vs incremental design

Traditional: big up-front designIncremental
IdeaRequirements → specify UI + business logic + database completely → implement → testProblem → user story → understand the domain → design → implement → feedback, next increment
Problems / strengthsMany decisions made before you have enough knowledge; users see nothing until the end, so feedback arrives when change is most expensive; wrong assumptions are discovered in testing, not in week twoStays up front: the expensive-to-change decisions (language, framework, data-model style, system boundaries). Decided per increment: endpoints, schemas, screens, internal structure

The failure mode is not planning; it is pretending early guesses are certain knowledge. Modern architecture is not "don't design upfront" but "don't pretend you know everything upfront".

There is no best architecture, only trade-offs

Four forces shape every choice: 1 Requirements (what must it do, how well?), 2 Team (e.g. four people, mixed skills, limited hours), 3 Time (e.g. twelve weeks including testing and demo), 4 Change (what is most likely to change?). Every choice buys something and costs something else; your job is to know what you paid and why.

Functional requirements shape features. Non-functional requirements shape architecture.

If someone asks "why is your architecture so complex?", the answer is always an NFR.

Architectural drivers

Not all requirements are equal. "User can change their profile picture" probably does not drive architecture (any reasonable structure absorbs it). "System must support 1 million users" absolutely does: it forces load balancing, stateless servers, caching, replication. A requirement is a driver if changing it would change your diagram. Hint: ask "if this requirement doubled or vanished, would my diagram change?"

3. From problem domain to system design

Design around the problem, not the technology. Technology-first thinking gives a pile of tools (React, C#, .NET, Node.js, PostgreSQL, Redis, AWS, Docker) and still no idea what to build. Domain-first thinking lists the concepts of the problem (for a university: student, course, lecturer, enrolment, assignment, examination, payment), which exist in every implementation. The structure of your software should reflect the structure of the problem you are solving.

Why it works: requirements talk about the domain ("a student enrols in a course"), code lives in components, and this pipeline translates between them, giving every component a name your client already understands. Name your components after the problem and the code explains itself.

Domain concepts do not automatically become services

Customer, Order and Payment can be Option A: three modules in one monolith (customer/ order/ payment/, one deployable app) or Option B: three microservices each with its own database. Both are valid; the trade-offs decide. The architecture should reflect the important concepts and boundaries of the domain, not mirror every noun as a service.

4. Design principles at project scale

CohesionCoupling
How strongly related the things inside one unit are. High cohesion = one module does one job well.How much one unit depends on another. Low coupling = change one thing without breaking five others.

Coupling is the reason two teammates cannot work in parallel: it shows up as merge conflicts, "your change broke my feature", and one person being the only human who understands a file. Count the arrows: every arrow is a way for a change to spread ("every edge is a reason to have a meeting"). Low cohesion example: UserService with login, createInvoice, sendEmail, calculateTax, generateReport, processPayment. High cohesion: AuthenticationService, PaymentService, InvoiceService, EmailService, ReportingService.

Anti-example and fix

class Student {                       // 4 jobs, endless pain
   save()             { db.query("INSERT INTO students ...") }   // knows SQL
   sendWelcomeEmail() { sendgrid.send({to: this.email}) }        // knows the email provider
   toHtml()           { return `<div class="card">${this.name}</div>` } // knows the UI
}
// Fix: one reason to change per unit
class Student { constructor(name, email) {...} }        // just data and rules
class StudentRepository { save(student) {...} }         // only this knows SQL
class EmailService     { sendWelcome(student) {...} }   // only this knows SendGrid
class StudentView      { render(student) {...} }        // only this knows HTML

Ask yourself: the email provider changes, how many files do you touch? Can you test the registration rule without a database? Two teammates edit this file, what happens at merge time? Gains: swap the email provider by editing one file; test rules without a database; four teammates in four files; newcomers find things by name.

SOLID, weighted by how much it helps you now

PrincipleIn one lineReal-world picture and example
S Single ResponsibilityOne class, one reason to change. "The one you will break daily."A restaurant where one person takes orders, cooks, delivers and bills works when quiet; at lunch rush everything fails at once. OrderManager with placeOrder, calcDiscount, chargeCard, sendInvoiceEmail, logAnalytics has 5 reasons to change; split into OrderService, PricingService, PaymentGateway, InvoiceMailer, AnalyticsClient. Test: "how many different reasons does this class have to change?"
O Open / ClosedAdd behaviour by extension, without editing tested code.Phone apps: you install new apps every week without re-soldering the board. pay(order, type) with if card / paypal / crypto must be reopened and retested for each new method; instead an interface PaymentMethod { pay(order) } with CardPayment, PayPalPayment, CryptoPayment: a new method is a new file only.
L Liskov SubstitutionA subtype must behave correctly wherever its parent is expected: "a subclass must not lie".Bird.fly(); Penguin throws "cannot fly" so every caller must check. Project version: CashOnDelivery extends Payment whose refundToCard() throws, so refund(payment) crashes for COD. Fix: a Refundable interface, or refund() returning a result instead of throwing; split the promise (FlyingBird, SwimmingBird).
I Interface SegregationMany small interfaces beat one fat one.OfficeMachine { print scan fax staple } forces SimplePrinter to stub fax() and staple(); instead Printable, Scannable, Faxable. Project: if the driver app must implement restaurant callbacks it never uses, every driver release depends on restaurant changes; split the interface.
D Dependency InversionDepend on a promise, not a product. High-level logic should not depend on low-level details.RegistrationService doing new MySqlDatabase() is locked in forever. Inject a Repository interface: production uses MySqlRepository, fast tests use InMemoryRepository, a later swap is one line (PostgresRepository). "The arrows flip": business logic and MySQL both depend on the abstraction. Leads to dependency injection, clean architecture, hexagonal architecture. Another example: OrderService depends on a Notifier interface (EmailNotifier, SmsNotifier, PushNotifier, FakeNotifier for tests).

Treat SOLID as habits that reduce coupling, not as rules to obey. Five principles, one enemy: coupling.

Do not over-engineer: YAGNI

Abstraction has a costFifteen interfaces and a factory for a to-do list app is a worse crime than none: every layer of indirection is another file a teammate must read. Add abstraction when it hurts: feel the coupling first, then remove it. Two implementations existing today is a reason for an interface; one hypothetical future one is not. YAGNI: "You Aren't Gonna Need It": build for the requirements you have, in a way that does not block the requirements you might get.
Key takeaways Architecture = decisions that are expensive to change; it exists whether planned or not. Design incrementally: fix the expensive decisions early, defer the rest. NFRs (not features) shape architecture; find the drivers by asking whether changing the requirement changes the diagram. Start from the problem domain: concept → responsibility → data → API → interactions. Aim for high cohesion and low coupling; use SOLID as habits and respect YAGNI.
