Short note: revision sheet

TopicRemember
Architecture in the SDLCNot one phase: begins at "what system do we need?" and continues through implementation, testing, maintenance. Requirements flow down; feedback flows up.
DefinitionArchitecture = the set of decisions that are expensive to change later. Exists whether planned or not (unplanned = accidental). No best architecture, only trade-offs (requirements, team, time, change).
Architectural vs implementation decisionsSQL/NoSQL, where business rules live, frontend-backend communication, framework vs list/dictionary, private method name, for/while, button colour.
Big up-front vs incrementalUp-front: decisions before knowledge, late feedback. Incremental: fix expensive decisions early (language, framework, data-model style, boundaries); decide the rest per increment. "Don't pretend you know everything upfront."
FR vs NFRFR shape features; NFR shape architecture. 500 users = one server; 1M users 24/7 <2 s 99.9 % = load balancer, many servers, cache, replica.
Architectural driverA requirement that would change your diagram if it changed (1M users, 10,000 orders/min, payment never twice, search under 300 ms). Not: PDF export, pie chart, button text.
Domain-first designProblem domain → entities/concepts → responsibilities → relationships → components. Name components after the problem. Domain concepts do not automatically become services (modules in a monolith vs microservices).
One concept unfolded (Order)Component (OrderService), data (orders table), API (POST /orders, GET /orders/42, PATCH /orders/42/status), interactions (sync Payment, async Restaurant, event OrderPlaced).
Cohesion / couplingHigh cohesion (one job well), low coupling (change one thing without breaking five). Every arrow is a way for a change to spread.
SOLID (project scale)S: one reason to change (OrderManager split). O: PaymentMethod interface. L: CashOnDelivery refund throws, fix with Refundable. I: small Printable / Scannable / Faxable. D: inject Repository (MySQL / InMemory). Habits, not rules.
YAGNIAbstraction has a cost; add it when it hurts; two real implementations justify an interface, one hypothetical does not.
Exam tipBe able to (1) say what makes a decision architectural, (2) pick drivers out of a requirement list, and (3) turn a domain into components with responsibilities and data.
