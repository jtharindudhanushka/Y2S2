Answer shape (Q13)"We chose X because A, accepting B and C." Never just "we chose microservices".
13-question worksheetUsers, user stories, domain concepts, FRs, NFRs, drivers, components, monolith vs microservices, communication, load, failure, security, trade-offs.
Ex 1 University registrationv1 modular monolith. Reveal: 15,000 hit register at 9 AM, capacity never exceeded → seat race (101/100) fixed by atomic transaction (check + decrement) + DB constraint seats >= 0 → transactional SQL. Budget: 3 devs, $500/month, 2 app servers + PostgreSQL + Redis: modular monolith, stateless servers + cache, NOT microservices.
Ex 2 Food delivery at scalev1 monolith. Reveal: 5M users, 50k concurrent, 10k orders/min: four load shapes (search = reads: cache + replicas; ordering = write spike: scale out; payment = never fail: isolate; GPS = firehose: own pipeline). Five teams, 20 devs, DevOps, $15,000/month: microservices (gateway, DB per service, broker events, per-service scaling x2/x4/x8/x2/x10).
Ex 3 Ticket booking1,000 users/day then 500,000 at 10:00:01. Adding app servers is necessary, not sufficient (one DB). Cache the browsing, never the buying. Last-seat race: atomic transaction + constraint. Payment: reservation state machine with a clock (Available → Reserved 10-min hold → SOLD / Released). Concurrency and time are architecture.
Numbers are architectureSame system, new number, dead design. Every box has a "birthday".
Food delivery brief100,000 users, under 2 s, 99.9 %, secure payments. 8 steps: concepts; actions; drivers (requirement → quality attribute → structure); components; style decision (modular monolith); communication (sync vs async); performance additions (LB, cache, queue, replica); failure drill (timeout, circuit breaker, pending-payment).
Sync vs async (food delivery)Sync: browse, place order, authorise payment. Async: receipt email, notify restaurant, analytics, assign driver.
7-question checklistProblem; FRs; NFRs; concepts and components; communication; slow/overloaded/failing; why this over alternatives.
MethodProblem → requirements → domain → quality attributes → components → architecture → communication → technology (last) → trade-offs.
Exam tipIn a design question: list concepts, drivers (requirement → attribute → structure), pick the style by the checklist, say what is sync vs async, add LB / cache / queue / replica where drivers demand them, answer "what if X fails?", and end with the trade-off sentence.
