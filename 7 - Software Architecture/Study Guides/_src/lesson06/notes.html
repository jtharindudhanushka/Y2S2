Quality attributes you already use daily: Google search feels instant (caching + replication across the planet: performance); WhatsApp ticks sent/delivered (async message queues); Netflix at 8 pm never buffers (popular titles cached inside your ISP, a CDN: performance; load balancer + many stateless servers: reliability); a bank transfer never half-happens (transactions, all or nothing); flash sales survive the stampede (scalability); you stay logged in on every device (tokens, not server memory: stateless).

1. Quality 1: performance

Latency vs throughputLatency = how long one user waits for one operation (a request and its response, e.g. 200 ms). Throughput = how much work the whole system does per unit time (e.g. 1,000 requests per second). Low latency does not imply high throughput.

A bus moves fifty people an hour (great throughput) but each waits at every stop (poor latency); a sports car is instant for one person and useless for a crowd. Architecture constantly trades one for the other: batching buys throughput with latency. Performance is money: Amazon measured about 1 % of sales lost per extra 100 ms of latency; Google measured about 20 % less traffic when results took 500 ms longer (widely cited experiments, 2006–09).

Why systems actually get slow

#Cause#Cause
1Slow database queries (missing indexes, N+1 loops)2Too many network calls (chatty APIs, one call per item)
3Sequential processing (waiting for work that could overlap)4Large payloads (data nobody asked for)
5Inefficient algorithms (an O(n²) hiding in a loop)6Resource contention (everyone queuing for one lock)
7External dependencies (your speed is their speed)

Measure before you optimise; the slow part is almost never where you guessed.

Caching: the fastest query is the one you never run

Cache what is: read often, changed rarely, expensive to compute, tolerant of being slightly stale. The catch is invalidation: when the real data changes the cached copy is a lie until refreshed; decide acceptable staleness per data type (menu: 5 minutes; order status: never cache it). Tools: Redis, Memcached, HTTP caching headers, CDN caching.

Load balancing: many hands, one front door

Clients → load balancer → Server 1, 2, 3. It spreads requests, health-checks servers and hides failures from users; a dead server simply stops getting traffic (so it is also your first reliability tool). The catch: any server must be able to answer any request, which is the stateless idea below.

2. Quality 2: scalability

Vertical scaling (scale up)Horizontal scaling (scale out)
A bigger server. Simple, no code changes. But: a ceiling, a price curve, still one point of failure.Keep adding machines as load grows. But: needs a load balancer and stateless design.

Cloud pricing made the choice for you: ten small machines are cheaper than one huge one.

The server does not remember you (stateless)

// wrong: dies on restart, breaks with 2 instances
let loggedInUser = null;

// right: prove it every time
GET /me
Authorization: Bearer <token>

Each request must carry everything the server needs to understand it: your token is sent on every request; any server instance can answer any request; nothing user-specific may live in a server variable. The second point is the entire secret of horizontal scaling.

Stateful vs stateless: the session trap

If the session lives in Server A's memory, the next request that lands on Server B finds "no session" and the user is logged out. Fixes: A: a shared session store (e.g. Redis) used by all servers; B: stateless tokens (JWT): the request itself proves who you are and any server can verify it locally. If servers hold no per-user state, any server can answer any request and scaling out becomes trivial.

Execution shapes

SequentialParallel
A → B → C → D: total time = A + B + C + D (e.g. 3 × 200 ms = 600 ms)Independent work at the same time: total time = the slowest branch (200 ms). Example: a dashboard needs courses, grades and notices (three independent queries): fire them together; 600 ms becomes 200 ms. Parallelism is free speed, but only for work that is truly independent.
Synchronous: the caller waitsAsynchronous: fire and move on
A is blocked until B answers.A returns immediately; B works later. Classic example: email after an order: save the order, put the email on a queue, return success (~50 ms); the email service delivers seconds later and nobody is waiting.

Never make the user wait for work they do not need to see.

3. Quality 3: reliability

ReliabilityThe ability of a system to continue providing its intended service correctly over time, including when components fail. Availability = uptime / total time. Failure is not an exception: at scale something is always failing, so design for it.
AvailabilityDowntime per year
99 %3.65 days
99.9 % ("three nines")8.8 hours
99.99 %53 minutes
99.999 %5 minutes

Each extra nine costs roughly 10× the engineering effort: redundancy, failover, monitoring, on-call, rehearsed recovery.

Single points of failure and redundancy

Ask of every box and every arrow: "What happens when this dies?" If the answer is "everything stops", you found a single point of failure (SPOF). A replica follows the primary and takes over if it dies.

When giants fall

AWS S3, February 2017Meta, October 2021
One mistyped command during routine debugging removed too many servers. 4 hours down in the main US region; thousands of sites broke; even status dashboards depended on S3.
Lessons: humans are a failure mode; a shared dependency is a shared SPOF.		One network configuration change withdrew the routes telling the internet where Facebook lives. 6 hours: Facebook, WhatsApp, Instagram gone; internal tools on the same network; even office badge readers affected.
Lessons: blast radius is a design choice; recovery paths must be independent.

Partial failure and three coping tools

In a monolith everything fails together; on a network things fail one at a time. If Service B is down and A is not, that is a partial failure, the normal failure mode of a distributed system. A must decide: wait, retry, give up, or degrade gracefully.

ToolMeaning
1 TimeoutDo not wait forever: give every call a deadline (e.g. give up after 2 s). A request that hangs is worse than one that fails: it holds a thread, a connection, a user.
2 RetryTry again, carefully. Good for transient blips; only safe on idempotent operations, with a limit and a growing delay (retry ×3 with backoff 1 s, 2 s, 4 s).
3 Circuit breaker"Stop kicking a dead horse": after repeated failures stop calling B and fail fast to a fallback; occasionally let one probe through to see if B recovered. States: closed → open → half-open. (From Michael Nygard's Release It!, 2007.)

4. Quality 4: security

Security is not something added at the end; it is an architectural concern from day one. (For further reading: XSS, CSRF, SSRF and friends: the OWASP Top 10.)

Authentication: "Who are you?"Authorisation: "What are you allowed to do?"
Login with a (hashed) password
Tokens prove identity on every request
Multi-factor for sensitive systems		Roles: student, lecturer, admin
Checked on the server, every request
A student must not see others' grades

Security rule number one: never trust the client

// IN THE BROWSER: anyone can edit this in devtools
let price = 4999;
if (form.coupon === "STAFF") price = 0;
sendOrder({ total: price });

// ON THE SERVER: the only version that counts
const item = await repo.findById(id);
const total = pricing.apply(item, user);
order.create({ total });

Client-side checks are for user experience; server-side checks are for correctness and security. Anything the client sends can be forged (prices, user ids, roles, quantities, hidden fields): validate on arrival, every time, even if the form already checked it.

Protecting data

WhereHow
In transitHTTPS / TLS on every connection (free certificates such as Let's Encrypt removed the last excuse).
At restEncrypt the database volume and the backups: a stolen disk should be a useless disk.
PasswordsNever stored, never encrypted: hashed with a slow one-way function (bcrypt or argon2). Why hash, not encrypt? Encryption has a key, and keys leak; a hash has no way back.

SQL injection: when input becomes code

// VULNERABLE: user input pasted into the query
const q = "SELECT * FROM students WHERE name = '" + input + "'";
// input:  '; DROP TABLE students;--   -> goodbye, students table

// SAFE: parameterised, input stays data
db.query("SELECT * FROM students WHERE name = ?", [input]);

One habit fixes it forever: parameterised queries (your ORM already does this; do not bypass it).

Configuration and secrets

Config changes between machines; code does not. Never hard-code postgres://admin:P@ss123@localhost/app; use connect(process.env.DATABASE_URL) with .env locally and real values on the server. Secrets never enter Git: once pushed, a secret is public forever (deleting the file does not delete history). In the repo: .gitignore lists .env and node_modules; a committed .env.example template lists names only (DATABASE_URL=, JWT_SECRET=).

5. Technology: the last decision, not the first

Only after the domain, components, communication style and quality attributes are understood are we equipped to choose tools.

The reuse ladder

1 Module2 Package3 Library4 Framework
One file of related code; smallest unit (utils/dates.js)Modules bundled with a name and version so others can install them (npm: date-fns)Code you call; you stay in control of the flow (axios, requests)Code that calls you; owns the skeleton, you fill the gaps (Express, Spring, Django)

All four are the same idea at different sizes: do not rewrite what exists. Inversion of control: who calls whom? With a library your code is the main character (const res = await axios.get(url)); with a framework your code is a plug-in (app.get("/courses", (req, res) => ...): Express called this). A framework gives structure for free and takes some freedom in return; that trade is the decision.

Most student projects have relational data: choose NoSQL because the data is document-shaped, not because it sounds modern.

Data setReasonStore
Orders + paymentsJoins users, orders, payments; money must never orphan; transactionsSQL (Postgres): integrity + joins
Restaurant menusNested tree, read whole, shape differs per restaurant, rarely joinedDocument (MongoDB): flexible shape

One system, four stores, each earned by a requirement: choose per data shape, never "one DB for the system".

Team agreements: conventions are architecture too

Agree in week 1 (twenty minutes saves days): 1 Naming (one casing style for files, classes, endpoints); 2 Formatting (a formatter like Prettier or Black); 3 Errors (where caught, what the client sees, what is logged); 4 Definition of done (merged, reviewed, tested, documented; not "works on my laptop").

Key takeaways Performance: latency vs throughput; measure first; cache read-heavy, rarely changing data (mind invalidation); load-balance. Scalability: scale out with stateless servers (tokens or a shared session store); parallelise independent work; make slow work asynchronous. Reliability: availability nines, remove single points of failure, plan for partial failure with timeout, retry (idempotent only) and circuit breaker. Security: authentication vs authorisation; never trust the client; TLS, encryption at rest, hashed passwords; parameterised queries; no secrets in Git. Choose technology last; frameworks invert control; choose SQL/NoSQL per data shape.
