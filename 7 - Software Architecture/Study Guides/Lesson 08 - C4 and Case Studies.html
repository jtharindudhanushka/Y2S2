C4 Model and Case Studies

Covers: the C4 model (context, container, component, code), and the three case studies worked in class: UniMart (monolith, growth crisis, microservices, events, decision memo, with the model answers), the University Course Registration System, and the Zippo ride-hailing super-app. No prior lecture attendance needed.

Learning outcomes

  • Describe the four levels of the C4 model and draw context and container diagrams
  • Walk through the UniMart case: monolith, growth crisis diagnosis, microservice redesign, event-driven notification, decision memo
  • Diagnose and fix the problems of the University Course Registration System (concurrency, validation, idempotency, caching, async, single point of failure)
  • Approach the Zippo ride-hailing super-app: prioritise quality attributes, decompose, design matching, consistency, outage handling and risks

1. The C4 model

DefinitionThe C4 model is a lean, developer-friendly approach to visualising software architecture by breaking a system into four hierarchical levels of detail: Context, Containers, Components and Code. It was created by Simon Brown (see c4model.com). Each level "zooms in" on a box of the level above.
LevelDiagramShowsLecture example (Internet Banking System)
1System ContextThe big picture: who uses the system (users / roles) and what external software systems it interacts with.Personal Banking Customer uses the Internet Banking System; it sends e-mails via Amazon Web Services Simple Email Service and gets account data from the Core Banking System.
2ContainerZooms into the system boundary to show high-level technical building blocks (web applications, mobile apps, API services, databases) and how they communicate over protocols.Static content, single-page UI, Backend (JSON/HTTP API), Statement Store and Database inside the system.
3ComponentZooms into a single container to show its structural components (controllers, repositories, authentication services) and their internal interactions.Backend: Statement API, Sign-in API, Accounts Summary API, Email, Security and Core Banking adapter components.
4CodeZooms into an individual component to show implementation details (e.g. a UML class diagram).Interfaces and classes of the Core Banking System adapter.

What a good C4 diagram contains: a title, boxes labelled with name, type and a short description, arrows labelled with the interaction ("Views account balances and makes payments using"; "Sends e-mails to customers using"), and a key/legend (person, software system, external system, relationship). In UniMart the first two levels (context and container) are what you draw; deployment and sequence diagrams complement them.

2. Case study A: UniMart, a student marketplace that outgrows itself

The lecturer's 3-hour workshop (progressive stages; each stage's output feeds the next, so you cannot skip the reasoning). Pre-reading: deployable unit, coupling vs cohesion at system level, bounded context ("a part of the business with its own vocabulary and rules"), the "-ilities", C4 context and container levels. The case: three final-year students built UniMart in a semester for ~2,000 users on one campus: register/log in with university e-mail verification; sellers post listings (title, description, price, category, photos); buyers search/browse/filter; buyer and seller message; buyers pay by card or campus wallet and orders are tracked (posted, paid, completed); reviews after a transaction; notifications (new message, price drop, order status). Launch NFRs: reliable during the two textbook-rush weeks each semester; payments never lost or double-charged; fast shipping with almost no budget by students themselves.

Stage 2: the Year 0 monolith

  • Deployment: a single VM / container running one monolith application and one PostgreSQL database.
  • Technology justification: a Node.js/Express-style monolith on one PostgreSQL database lets three students build, test and deploy one codebase without a dedicated ops person and keeps hosting cost near zero.
ReflectionAnswer
A messaging bug crashes the server: what else goes down?Everything (catalog, payments, auth...) because all modules run in the same process on the same machine; one unhandled exception takes the whole application down.
Textbook-rush traffic hits only search: options?Scale the whole VM vertically or run more copies of the whole app horizontally: awkward because catalog, payments and every other module are duplicated though only search needs capacity.
Time for a one-line reviews fix to reach production?Could be hours rather than minutes: it passes through the same build, test and deploy pipeline as the whole app.

Lesson: monolith-first is often correct, not a mistake to avoid.

Stage 3: the growth crisis (18 months later, 5 campuses, 60,000 users, four squads)

Squads: Catalog & Search, Messaging, Payments & Orders, Platform (auth, notifications). Map each symptom to its architectural cause, before solutioning:

Pain pointArchitectural cause
A search memory leak crashed the whole app, including payments mid-transaction (students charged with no confirmation)Shared process / failure domain: one module's failure takes down the entire app
Payments wants a strict-consistency database, Catalog a search-optimised one; neither can moveShared database: one schema / instance serves all modules
A copy change to a listing page takes 3 days to reach productionShared deploy pipeline: every change rides the same build, test and release cycle as payments code
Two squads shipped conflicting changes to the same file twice this monthShared codebase: unrelated features collide during merges (merge contention)

Stage 4: redesign as microservices

Identify service boundaries by bounded-context reasoning: each service maps to one squad and owns its own data. Expected services: Auth/Identity, Catalog, Messaging, Orders & Payments, Reviews, Notifications (justification matters more than matching the list).

The container diagram: all services behind an API gateway, each with its own datastore, arrows labelled sync (e.g. Orders → Auth) vs async (events on the bus, all feeding Notification). Sequence "student buys a used textbook": student selects listing and checks out → gateway → Catalog (GET listing details) → Orders & Payments (POST /orders: verify identity and process payment) → "order confirmed" → publish OrderPlaced on the event bus → Notification service sends the order confirmation.

Trade-off table (what got better / what got harder)

Grounded statements score well ("Catalog can now scale its search index independently of Payments during textbook rush"); generic ones ("microservices are more scalable") score poorly. Microservices are not a strict upgrade.

Stage 5: event-driven notification

Introduce a message broker (e.g. RabbitMQ, Kafka, a cloud pub/sub). Catalog (PriceDropped), Messaging (NewMessageReceived) and Orders & Payments (OrderPlaced) publish events without knowing who listens; Notification subscribes and acts independently. Buys: decoupling (producers need not know Notification exists) and resilience (Notification slow or down during the rush blocks neither a purchase nor a message). Costs: traceability ("what happened and when" across producer, broker and consumer is harder than one call stack) and eventual consistency (a purchase may complete seconds before the confirmation arrives).

Take-home: SOA and serverless

  • SOA vs microservices: SOA typically relies on heavier shared middleware, an Enterprise Service Bus, to route messages and enforce contracts centrally, and its services are coarser-grained (e.g. one "Order Management" service covering several sub-functions). Microservices are independently deployed, much finer-grained, use lightweight communication (REST or events) without a central bus owning business logic, and each strictly owns its data store.
  • Serverless fit: a nightly sales / top-category report for the founders suits a serverless function (runs briefly on a schedule, needs no permanently running service); Messaging is a poor fit (it must stay available and stateful for real-time conversations).
  • Optional stretch (build it): implement two services (e.g. Catalog and Orders) as separate applications with their own local database talking over HTTP, containerised with Docker, to feel redeploying one without touching the other.

Stage 6: the decision memo (150–200 words to the non-architect co-founders)

It must answer: (1) was a Year-0 monolith the right call? (2) what triggered the change (cite the pain points)? (3) is full microservices right at 60,000 users, or something in between? (4) what new problem comes next? Model answer summary: yes, the monolith was right (one semester, no budget, no ops person: ship fast at near-zero cost). Growth exposed shared process, database, pipeline and codebase. Full microservices is not necessary yet: partially decompose: pull out Orders and Payments first (hardest consistency requirement and biggest blast radius) and keep Catalog, Messaging, Reviews and Notifications as a modular monolith until each squad's pain justifies splitting. Next problem: distributed transaction handling and cross-service monitoring.

3. Case study B: University Course Registration System

Scenario: a university needs a Course Registration System for about 10,000 students: log in, view courses, register, drop, view registrations; administrators manage course information. Requirements: a course has a maximum capacity (e.g. Database Systems at most 100); capacity must never be exceeded; a student must not register twice for the same course; only authenticated and authorised students may register; registration data stored reliably; confirmation email after successful registration; course information is read very frequently but changes rarely; during registration week several thousand students use it simultaneously. Starting point (no planned architecture): Browser → one application (login, registration, validation, email, reporting and DB access mixed together) → one database. Do not redesign yet: first investigate.

Step 3: the improved architecture

Start with responsibilities, not technologies. It should show: client / UI; REST API; business logic / registration rules; data access and database; a cache for read-heavy course data; a message queue and email service for asynchronous confirmation; an authentication / authorisation boundary; a mechanism for safe concurrent registration; a mechanism to prevent duplicate registration; an availability / scalability approach.

Steps 4–7

  • Label responsibilities (and what each component should not do): e.g. the controller handles HTTP only; the service holds registration rules; the repository holds SQL; the cache holds course reads only; the queue worker sends email and never blocks registration.
  • REST API: all courses GET /courses; Course 42 GET /courses/42; create POST /courses; update PUT/PATCH /courses/42; delete DELETE /courses/42; registrations of Student 10 GET /students/10/registrations; register Student 10 for Course 42 POST /courses/42/registrations (body {studentId: 10}). Challenge: the POST registration endpoint is affected by a double-click or retry; prevent duplicates with a unique (student, course) constraint plus an idempotency key.
  • Critical scenario: one seat left in Course 42; A and B submit at almost the same time. Race: both read 1 free seat, both insert, 101/100. Prevention: one database transaction that checks capacity and inserts/decrements atomically (row lock or optimistic locking) with a DB constraint; one gets a clean "course full".
  • Justify each decision with the chain: Requirement → Problem/Risk → Quality attribute → Architectural decision → Mechanism. Example: "capacity never exceeded" → race on last seat → consistency → transactional DB → atomic check + insert with constraint.

Step 8: challenge your architecture (update only if necessary)

ChangeDoes the architecture need to change?
Traffic grows from hundreds to several thousand simultaneous usersNot structurally: add stateless API instances behind the load balancer; the transaction protects capacity.
Catalogue becomes even more read-heavyStrengthen the cache (and read replicas); no structural change.
Email service temporarily unavailableNo: the queue holds messages and retries; registration is unaffected (this is why email is async).
University launches a mobile applicationNo: a second client of the same REST API; server-side rules and auth are reused.
A second campus uses the same systemMostly data/config (campus identifier, per-campus courses, capacity); scale the same components; revisit capacity of the database.

Final group check: major components identified with clear responsibilities; the client never touches the database; business rules enforced on the server; concurrent registration cannot exceed capacity; duplicates prevented; course reads efficient; email does not delay registration; availability and single points of failure considered; each decision explainable. 3-minute presentation: diagram, component responsibilities, last-seat race handling, duplicate prevention, caching and async messaging use, one remaining risk or trade-off. Key takeaway: architecture connects requirements and quality attributes to decisions about structure, responsibilities, communication, data and failure handling; it is not just a diagram or a list of technologies.

4. Case study C: Zippo ride-hailing and delivery super-app

Role: you are the Lead Software Architect for Zippo, a ride-hailing and food-delivery "super-app" in South and Southeast Asia. Context: 50,000 → 5 million monthly active riders and 300,000 active drivers across 6 countries in 18 months; approved expansion into 10 more countries within a year (including unreliable mobile networks); investors want a food/grocery vertical on the same platform reusing the driver fleet; a promotion caused a 3-hour outage at peak surge (drivers could not receive offers, riders double-charged, about $400,000 lost). CEO: "this cannot happen again, and it has to work in villages with 2G."

Current broken system: one monolithic backend, one PostgreSQL database in a single AWS region; driver location updates written to the same rows the matching logic reads (read/write locks are the bottleneck); payments processed synchronously inside the trip-completion request (a slow gateway hangs the whole flow); no message queue, only direct HTTP calls between internal modules.

FunctionalNon-functional (with numbers)
F1 request a ride / food order and see nearby drivers in real time
F2 match to the best driver within a target time
F3 drivers get offers and accept/reject within a countdown
F4 live location tracking
F5 payment at completion (cards, wallets, cash)
F6 surge pricing from real-time supply/demand
F7 shared driver/courier pool for rides and food		Matching latency: matched driver within 3 s for 95 % of requests
Location throughput: 300,000 drivers pinging every 4 s = 75,000 writes/s steady, up to 3x in surge
Availability: 99.95 % for trip-critical services (matching, payments)
Payment consistency: zero double or lost charges, strongly consistent
Geographic scale: 16 countries, some with data-residency laws (payment data stays in-country)
Network tolerance: driver apps acceptable on 2G/3G, intermittent
Extensibility: new vertical without rewriting matching or payment core
Observability: full trip lifecycle traceable for disputes
Constraint: cost-aware cloud budget

The six tasks (the case provides the tasks; the suggestions below are a worked approach built from the lecture concepts, not an official answer):

TaskSuggested approach
1 Prioritise quality attributes: which 3 conflict?Availability + latency vs strong payment consistency vs cost (and data residency). Prioritise availability and matching latency for the trip-critical path and strong consistency for money; deliberately sacrifice strict consistency for location data (eventual is fine) and accept higher infrastructure cost only where the numbers demand it.
2 DecomposeServices by capability: rider/driver apps and API gateway; Location service (high-volume pings); Matching / Dispatch; Trip; Pricing / surge; Payments (isolated, per-country); Notification/offers; Catalog/Orders for the food vertical reusing the driver pool; observability (tracing). Payment data and location data must not cross each other's boundary; no shared tables.
3 Real-time matching flowRider taps Request → gateway → Trip service creates a request (write) → Matching reads nearby drivers from an in-memory geo-index fed by location pings (reads, not the main DB) → sends offers to top candidates over push → first accept wins (atomic assignment) → rider notified. If none within 3 s: widen the radius, keep searching asynchronously, show an honest "still looking", and degrade gracefully (surge price or queue).
4 Data consistency strategyLocation data: high-volume, short-lived, losing a ping is harmless: append to a stream / in-memory geo store, eventual consistency, batched writes, TTL. Payment data: strongly consistent relational store with transactions, unique idempotency keys, per-country residency. Different stores, different guarantees.
5 The outage that already happened(a) Surge overload: load balancers, autoscaling, separate location pipeline from matching (no shared locks), caching, queues to absorb spikes, load shedding. (b) Slow payment gateway: take payment asynchronously after trip end via a queue; timeout + circuit breaker; idempotent retries so no double charge; complete the trip first. (c) 2G: small payloads, compact protocols, retry with backoff, offline buffering of location in the app, push over lightweight channels.
6 Top 3 risksExamples: distributed-transaction bugs between trip and payment (mitigate with sagas, idempotency, reconciliation); hot-spot overload of the geo-index in a city (shard by region, replicate); data-residency / multi-region complexity and cost (per-country payment deployments, cost monitoring); operational complexity of many services (tracing, SLOs, on-call).
Key takeaways C4 = Context, Containers, Components, Code (zoom in). UniMart shows why a monolith is right first and why shared process, database, pipeline and codebase cause growth pain; the redesign gives each service its own data, mixes sync (identity) and async (events) and honestly lists new costs (distributed transactions, monitoring); a partial decomposition (Payments first) may fit better than full microservices. Course registration: concurrency (atomic transaction), server-side validation, idempotency, caching, async email, no single point of failure. Zippo: separate location from payments, async payments, geo-index matching, 2G tolerance.

Written questions

W1. Describe the four levels of the C4 model with what each shows.

Level 1 System Context: the big picture, who uses the system and what external software systems it interacts with. Level 2 Container: zooms into the system boundary to show high-level technical building blocks (web and mobile apps, API services, databases) and how they communicate over protocols. Level 3 Component: zooms into one container to show its structural components (controllers, repositories, authentication services) and internal interactions. Level 4 Code: zooms into one component to show implementation details such as a class diagram.

W2. For UniMart, map each growth-crisis symptom to its architectural cause and describe the redesign trade-offs.

Search leak crashing payments: shared process / failure domain. Payments and Catalog needing different databases: shared database. 3-day copy change: shared deploy pipeline. Conflicting commits: shared codebase. Redesign into Auth, Catalog, Messaging, Orders and Payments, Reviews, Notifications with their own data, API gateway, sync identity checks and async events. Better: independent deploys, fault isolation, database choice, team autonomy. Harder: six pipelines, network failures, no single ACID transaction, service discovery and monitoring, API contracts.

W3. Explain how the university course registration architecture handles the last-seat race, duplicate registration, read load and email delay.

Last seat: the registration service performs the capacity check and insert/decrement in one atomic database transaction (row lock or optimistic locking) with a DB constraint as a backstop, so one student succeeds and the other gets 'course full'. Duplicates: a unique (student, course) constraint plus an idempotency key on the POST. Read load: cache the course catalogue (read-heavy, rarely changing) and use a replica. Email: place confirmation on a queue processed by a worker, so registration is not delayed and an email outage does not affect it.

W4. Outline an architecture for the Zippo ride-hailing app that prevents a repeat of the 3-hour outage and works on 2G.

Decompose into location, matching/dispatch, trip, pricing, payments (isolated, per country), notifications and a food vertical reusing the driver pool, behind an API gateway. Separate the location pipeline (in-memory geo index, batched eventual writes) from matching so there are no read/write locks. Make payments asynchronous after trip completion with a queue, timeouts, circuit breaker and idempotency keys so a slow gateway never blocks trips and no double charges occur. Autoscale and shed load under surge. For 2G use small payloads, retries with backoff and offline buffering of location in the app. Add tracing for dispute resolution.
