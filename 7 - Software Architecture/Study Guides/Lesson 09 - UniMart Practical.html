Practical: UniMart Full-Stack Monolith Labs

Covers the ten UniMart lab guides as one end-to-end picture: ER design and the layered monolith, React + TypeScript frontend, Spring Boot MVC backend, MySQL, environment configuration and secrets, Git and pull requests, CRUD APIs with Postman tests, frontend features with RTK Query, full-stack integration and debugging, and Docker / GitHub Actions deployment. Explains what each lab teaches architecturally. No prior attendance needed.

Source: the ten guides of the UniMart Monolithic Full-Stack Lab Series (B.Sc. (Hons) IT Level 2, hands-on laboratory practical). This lesson explains the architecture and reasoning behind each lab; commands and code are summarised, not copied in full. It builds the Year-0 monolith of the UniMart case study (Lesson 8).

  • Explain why containers do not make a monolith into microservices

1. Guide 01: ER model and monolithic architecture design

Outcomes: convert the narrative into a normalised relational model; build an EER diagram in MySQL Workbench (keys, cardinalities, constraints); draw C4-style context, container, component and deployment diagrams; map MVC to Spring Boot. Scope discipline: add only implementation-level fields (IDs, timestamps, statuses, optimistic-lock versions) that the case requires.

Case statementEntity / rule
Register and log in with a university emailUser; university_email UNIQUE; password stored only as a hash
Sellers post listings (title, description, price, category, photos)Listing, Category, ListingImage; one seller owns many listings
Buyers and sellers message each otherConversation and Message (a message belongs to one conversation and one sender)
Buyers pay and orders move through statusesOrder and Payment; payment reference and idempotency key UNIQUE
Buyer reviews after a transactionReview belongs to a completed order; one review per order
Users receive notificationsNotification belongs to one user with a type and read state

Entity catalogue (key constraints)

EntityImportant constraints
UserUNIQUE university_email; password_hash never returned by APIs
CategoryUNIQUE name

  • EER steps: new model, schema unimart, create tables; BIGINT ids, DECIMAL(12,2) money, VARCHAR bounded text, TEXT descriptions, TIMESTAMP; mark PK, NOT NULL, unique indexes and foreign keys; most links are non-identifying (children have their own surrogate keys); add indexes for access paths: listing(status, category_id, created_at), message(conversation_id, created_at), review(reviewee_id, created_at), notification(user_id, is_read, created_at); review generated DDL (Forward Engineer) before executing; export PNG/PDF and keep the .mwb.
  • Money rule: never FLOAT or DOUBLE for prices; use DECIMAL so binary floating-point rounding cannot change currency values.
  • Normalisation: 1NF (photos are rows in listing_images, not comma-separated URLs); 2NF/3NF (category names stored once, seller details in users, payment details in payments). Status values: Listing AVAILABLE, RESERVED, SOLD, ARCHIVED; Order POSTED, PAID, COMPLETED, CANCELLED; Payment PENDING, SUCCEEDED, FAILED, REFUNDED. Prefer soft deletion for listings with transaction history (keep audit evidence). Apply business constraints in both the service layer and the database.

2. Guide 02: frontend (React + TypeScript SPA)

  • Tools: Google Antigravity (AI-assisted IDE: read generated diffs, run tests, explain code, never paste secrets or student data into prompts); Node.js 22.12+; npm create vite@latest unimart-frontend -- --template react-ts (Create React App is deprecated); run npm run build early and fix TypeScript errors immediately.
  • Feature-first structure: src/app (store, hooks), components (genuinely reusable UI only), features/auth|listings|reviews (slice, API, types, components, pages), layouts, routes (AppRouter, ProtectedRoute), services/baseApi.ts, theme, utils. It keeps catalog and review code cohesive and eases future extraction (the same cohesion idea as Lesson 4).
  • Libraries: Redux Toolkit + React Redux (store with auth reducer, typed hooks, Provider in main.tsx); Material UI (accessible components, theme tokens); Tailwind CSS v4 via the Vite plugin (layout and spacing). Styling rule: MUI for interactive components and theme; Tailwind for layout; do not apply competing sx props and Tailwind classes to the same CSS property. Routing with react-router-dom; forms with react-hook-form + zod.
  • Environment: .env.local with VITE_API_BASE_URL=http://localhost:8080/api/v1; commit .env.example; only VITE_ variables reach client code, so never put passwords, JWT secrets, DB credentials or private keys there (browser users can inspect bundles).
  • Quality scripts: npm run dev / build / lint, npm audit, npm outdated.

It is still MVC (controllers HTTP, services use cases, repositories data, React the view); package-by-feature keeps each business module cohesive and reduces merge contention.

  • First proof: a public GET /api/v1/public/ping returning service, status UP and time proves the web layer runs before the database is configured.
  • API conventions: base path /api/v1; plural resources; return DTOs not entities; ISO-8601 UTC timestamps; 201 created, 204 deleted, 400 validation, 401 missing/invalid auth, 403 insufficient permission, 404 absent, 409 state conflict; pagination from the start; one global exception handler returning a predictable Problem-Details style ApiError(code, message, path, timestamp, fieldErrors); thin controller methods.
  • Security to prepare: BCrypt password hashing (never logged); public endpoints = registration, login, token refresh, public listing reads, health; protected = listing/review writes and user-specific actions; short-lived JWT access tokens; CORS only for configured frontend origins (no wildcard with credentials); production secrets from environment variables or secret stores.
  • Common errors: invalid target release (IntelliJ and Maven use different JDKs: set all to Java 21); port 8080 busy; unresolved dependencies (./mvnw -U clean test); 401 on /ping (permit /api/v1/public/**); startup failure before DB setup (needs variables or a test profile).

4. Guide 04: MySQL and Workbench

  • MySQL Server 8.4 LTS with Workbench (Workbench stays on the 8.0 line; some features may not work with newer servers: test the exact class image). Use a Development Computer configuration, TCP/IP on 3306, a strong unique root password (in a password manager, not a text file).
  • Least privilege: create schema unimart (utf8mb4) and user unimart_app with only SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES on it. Never configure the Spring Boot app to use root.
  • Workbench connection "UniMart Local" (127.0.0.1:3306, user unimart_app); store passwords in the vault only on a trusted personal computer; verify with SELECT VERSION(); SHOW DATABASES; USE unimart;.
  • Naming: snake_case in the database, camelCase in Java DTOs; map explicitly. Let Flyway own schema creation; use Forward Engineer only as a review tool; after migrations run, Reverse Engineer to compare the live schema with the model.
  • Safe practice: explicit column lists (not SELECT *); limit results; never show password_hash or tokens on a projector; export before big migrations; dedicated local database; no destructive reset without a backup and approval. Backup: mysqldump --single-transaction --routines --triggers; restore into an empty dev schema.

  • Commit .env.example (names and placeholders only); ignore .env, .env.* (except the example), application-secrets.yml, *.pem, *.key.
  • application.yml reads ${DB_URL} etc.; Hikari pool (maximum-pool-size, minimum-idle); jpa.open-in-view: false; ddl-auto: validate (not update): Flyway creates and changes the schema; Hibernate checks the mappings match; server.error.include-message: never; actuator exposure limited to health and info; CORS and JWT settings from environment.
  • Flyway: V1__create_core_tables.sql creates users, categories, listings (with CHECK price ≥ 0 and index on status, category_id, created_at). A migration is an immutable history record: create later migrations for orders and reviews rather than editing V1 after it has run on shared environments.
  • JPA mapping: @Entity @Table, @ManyToOne(fetch = LAZY), BigDecimal for price, @Enumerated(EnumType.STRING), @Version for optimistic locking.
  • JWT config: decode the base64 secret, fail startup if under 32 bytes, build JwtEncoder / JwtDecoder beans; password checking happens at login before a token is minted.
  • Verify: run with the local profile, check logs for Flyway success and Hikari start, curl /actuator/health returns UP, tables and flyway_schema_history visible in Workbench. Error diagnosis: Access denied (credentials/grants), Unknown database, Communications link failure (server stopped), Flyway validation failed (migration changed after execution: restore it and add a new versioned one), schema validation missing column (entity and migration differ), JWT secret error (not base64 or too short), CORS blocked (origin mismatch).

  • Feature-branch workflow: git switch main; git pull --ff-only; git switch -c feature/listing-create-api; small commits; push; open a pull request into main describing requirement, implementation, evidence, tests, migration; at least one reviewer (the author does not approve their own work); resolve comments with new commits; merge only when CI passes; delete the branch.
  • Commit prefixes: feat, fix, test, docs, refactor, chore, ci (e.g. feat(listings): add create listing endpoint).
  • Sync: git fetch origin; git rebase origin/main; resolve conflicts by reading both versions and the business intent (never blindly "ours" or "theirs"); run tests; rebase local feature branches but never rewrite shared main history; pull --ff-only on main.
  • Protect main: require a PR, required status checks (frontend build/lint, backend tests), conversation resolution and one approval, restrict force pushes and deletion; Dependabot alerts; issues or a board for Listing, Review, Auth and Deployment tasks. Releases: annotated tags (v0.1.0 local CRUD milestone, v1.0.0 cloud deployment milestone) as rollback points.
  • Review checklist: one PR = one coherent change; migration and entity reviewed together; API contract changes reflected in frontend types and the Postman collection; tests cover happy path, validation, unauthorised, forbidden, not found; no generated directories, secrets or DB dumps; README works on a clean clone.

8. Guide 08: frontend features (listings and reviews)

  • Routes: / ListingsPage (search/filter/paginate); /listings/new and /listings/:id/edit ListingFormPage; /listings/:id ListingDetailsPage (listing, seller, reviews; owner sees edit/archive); /orders/:orderId/review ReviewFormPage; /my/listings; /login.

9. Guide 09: full-stack integration, Redux and debugging

End-to-end request flow

  1. A React component calls an RTK Query hook. 2. fetchBaseQuery reads VITE_API_BASE_URL and the token from Redux state. 3. The browser sends the HTTP request with Authorization: Bearer <token>. 4. Spring Security validates the JWT, then Controller → Service → Repository → MySQL runs. 5. The backend returns a DTO as JSON; RTK Query caches it and React re-renders. 6. Mutations invalidate tags so affected queries refetch.
  • CORS: exact origins; http://localhost:5173 and http://127.0.0.1:5173 are different origins; do not combine allowCredentials(true) with wildcard origins; allowed headers Authorization, Content-Type, Accept.
  • Token handling: keep the short-lived access token in memory (Redux) and use an HttpOnly, Secure, SameSite refresh cookie issued by the backend; on reload call /auth/refresh with credentials; avoid localStorage for long-lived bearer tokens (injected scripts can read it). The base query retries once after a 401 using the refresh endpoint, guarded by a mutex so concurrent requests trigger only one refresh; on failure sign out.
  • Store: add baseApi.middleware exactly once; DevTools enabled in development only; use Redux DevTools to inspect auth/credentialsReceived, cache entries and tag invalidation; never expose real tokens in demos.

Acceptance tests: anonymous users can browse but not create/edit/archive/review; a seller manages only their own listings; a buyer reviews only their own completed order, once; mutations update the UI without a full reload; an expired token triggers at most one refresh then retry or sign-out; errors give friendly feedback while technical detail stays in dev tools and logs.

10. Guide 10: DigitalOcean deployment and GitHub Actions

Architecture meaningContainers do not turn the backend into microservices: the Spring Boot application remains one deployable monolith connected to one MySQL database, with separate containers for frontend, backend and database on a single VPS.
  1. Droplet: Ubuntu 24.04 LTS, small Basic plan, SSH-key authentication (no password-only root), billing alert, delete unused resources.
  2. Secure the server first: create a deploy user with sudo and your SSH keys, enable the UFW firewall (OpenSSH), update packages; verify ssh deploy@IP before closing root; disable password auth only after key access is confirmed.
  3. Docker Engine + Compose plugin from the official repository. Docker group membership is root-equivalent: restrict it and protect the deploy key.
  4. Backend Dockerfile (multi-stage): build with Maven + JDK 21, run on a JRE image as a non-root user (spring), -XX:MaxRAMPercentage=75. Frontend Dockerfile: build with Node 22 (VITE_API_BASE_URL=/api/v1), serve static files with Nginx (SPA fallback try_files ... /index.html; long cache for assets).
  5. Docker Compose (/opt/unimart): db (mysql:8.4, volume mysql_data for persistence, healthcheck), backend (image from GHCR, prod profile, environment from .env, depends_on db: service_healthy, port bound to 127.0.0.1:8080), frontend (127.0.0.1:3000); a private unimart network. The .env on the server is chmod 600 and never committed.
  6. Host Nginx reverse proxy: /api/ to 127.0.0.1:8080 and / to 127.0.0.1:3000; nginx -t then reload; open Nginx Full in the firewall; point a domain's A record at the Droplet and use Certbot for a trusted TLS certificate (without a domain/TLS use only non-sensitive demo data).
  7. GHCR: workflows push images with GITHUB_TOKEN; the server authenticates with a narrowly scoped read:packages token if private; prefer immutable SHA tags for rollback (latest only a convenience pointer).
  8. GitHub Actions (backend): on push and PR to main: set up Java 21, ./mvnw -B verify; on push only, log in to GHCR and build/push the image (:latest and :${{ github.sha }}); a deploy job (needs the build job, environment production) uses SSH secrets (DO_SSH_PRIVATE_KEY, DO_HOST, DO_USER) to run docker compose pull backend && docker compose up -d backend && docker image prune -f. Frontend: the same pattern with Node 22, npm ci, lint, build.
  9. Operate: backups, health checks, rollback to a previous SHA tag, cost controls.

Written questions

W1. Explain how the UniMart narrative becomes a data model and list five constraints you would enforce.

Each case statement yields entities: registration/login gives User (unique university email, password hash); listings give Listing, Category and ListingImage; messaging gives Conversation and Message; payments and orders give Order and Payment (unique provider reference and idempotency key); reviews give Review (one per completed order); notifications give Notification. Constraints: UNIQUE university_email; price >= 0 with DECIMAL; UNIQUE review order_id; rating 1 to 5; unique buyer/seller/listing conversation; legal order status transitions; version column for optimistic locking.

W2. Describe the responsibilities of the controller, service, repository, entity and DTO layers in the Spring Boot backend.

Controller: parse path/query/body, trigger validation, call the service and map HTTP status; no repository calls or transactions. Service: business rules, ownership checks, transactions, orchestration. Repository: query and persist entities. Entity: persistence state and simple invariants, never returned directly. DTO/mapper: the API contract, preventing leakage of fields such as passwordHash.

W3. Explain the environment-variable and secrets strategy and the role of Flyway and ddl-auto validate.

DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET, JWT_ACCESS_MINUTES, APP_ALLOWED_ORIGINS and the profile are supplied as environment variables; .env.example with placeholders is committed while .env and key files are ignored; production secrets come from the server environment or secret stores. Flyway creates and evolves the schema through immutable versioned migrations and Hibernate with ddl-auto validate only checks that entity mappings match it.

W4. Trace one request end to end in the integrated app and list the required negative API tests.

A component calls an RTK Query hook; fetchBaseQuery adds the bearer token from Redux; the browser calls Spring Boot; Spring Security validates the JWT; Controller, Service, Repository and MySQL execute; a DTO returns as JSON; RTK Query caches it and React re-renders; mutations invalidate tags to refetch. Negative tests: no token 401, blank title 400, other seller's listing 403, missing listing 404, unfinished order review 409, another buyer's order 403, duplicate review 409, rating outside 1-5 400, expired JWT 401.

W5. Describe the deployment architecture and CI/CD pipeline and explain why it is still a monolith.

One DigitalOcean Droplet runs Docker Compose with a MySQL container (persistent volume, healthcheck), a Spring Boot backend container and a frontend Nginx container, all behind a host Nginx reverse proxy (/api to the backend, / to the frontend) with TLS. GitHub Actions tests and builds on pull requests; on pushes to main it publishes images to GHCR and deploys over SSH with docker compose pull and up. It is still a monolith because there is a single backend deployable using one shared database; containers only package it.
