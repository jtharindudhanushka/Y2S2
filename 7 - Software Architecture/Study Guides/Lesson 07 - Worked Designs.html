Worked Designs: Putting It All Together

Covers (guest session, part 4): the 13-question architecture worksheet and three worked systems (university registration, food delivery at scale, ticket booking), then the full eight-step design of an online food delivery system and the seven-question checklist. Shows how the facts of a problem (numbers, teams, money) change the architecture. No prior lecture attendance needed.

Source: the guest session From Problem to System Design, hands-on exercises (three systems revealed step by step) and the "putting it all together" section. This is the heart of the lecture: it applies Lessons 4–6.

Learning outcomes

  • Use the 13-question worksheet and the "We chose X because A, accepting B and C" answer shape

  • Design an online food delivery system in eight steps and justify it

The three exercises share a pattern: commit to the simplest design the evidence supports, then reveal a new fact that attacks it. The numbers, teams and money, not fashion, change the architecture.

2. Exercise 1: university registration

Users: students (view courses and free seats, register, drop, view timetable), lecturers (create courses, set capacity, view enrolled students), administrators (manage students and courses, generate reports). Concepts: Student, Enrollment, Course, Lecturer, Timetable, Department. Capabilities from the stories: authentication, course management, registration, student management, reporting.

Committed design v1: one application (modules auth, courses, registration, reports) with one database behind a UI. "Given what we know now, is there any reason not to build this simple monolith?" It is right for the evidence so far.

Step 4 reveal: 9:00 AM changes everything

New facts (NFRs)The seat race
20,000 students, 2,000 concurrent normally; registration opens 9:00 AM for everyone, up to 15,000 at once; capacity must never be exceeded; under 2 s; 99.9 % availability. Is this still just CRUD? No.Course capacity 100, one seat left. Student A sees "1 free"; Student B sees "1 free"; both register and the count becomes 101/100.
The fix: a transaction: check + decrement as ONE atomic step; a constraint in the database (seats >= 0) as the last line of defence. Result: one of A or B gets a clean "course full" message.

One business rule (never exceed capacity) reached down and chose transactional SQL for us.

Step 5 reveal: the budget

Resources: three developers and $500 a month: 2 app servers, 1 PostgreSQL, 1 Redis, one team, no DevOps. Microservices? No: one team means no coordination problem to solve; strong transactions mean one database is a feature; no ops capacity for many deployments; the 9 AM spike is solved by 2 stateless servers + cache.

Good architecture is not the most sophisticated architecture. It is the one that fits.

3. Exercise 2: food delivery at scale

Users: customers (search restaurants, browse menus, order, pay, track), restaurants (manage menus, accept orders, update status), drivers (accept deliveries, update location, complete). Capabilities: Restaurant, Customer, Order, Delivery, Payment, Notification. v1 with today's evidence: one modular monolith, one DB (the same answer as the university, and rightly so for now).

Step 2 reveal: the scale

5M registered users, 500k daily active, 50k concurrent, 10k orders per minute at peak, 10 cities. Do all parts feel this load the same way?

PartLoad shapeAnswer
Restaurant searchhuge READScache + replicas
Orderingheavy WRITES, lunch spikescale out horizontally

Four load shapes, one box, one scaling answer: that mismatch is the real pressure to split.

Steps 3–4 reveal: teams and money

Five teams (Customer, Restaurant, Orders, Payments, Delivery), 20 developers, dedicated DevOps, CI/CD, monitoring, $15,000 a month. Conway: the system will mirror this org chart; plan the mirror instead of fighting it. Run the checklist: several teams blocking each other; load shapes needing different scaling; deploy independence wanted; ops maturity to run it. Every box ticks for the first time today: microservices, said with reasons.

Steps 5–7: the result

The ×N numbers are instances at peak: scaling per service, not per system. Patterns used: API gateway, database per service, events via broker (sync: order, pay; async: everything after OrderPlaced), independent scaling. "Nobody memorised these patterns. The problem demanded every one of them."

4. Exercise 3: ticket booking rush

Concerts, 50,000 seats; search events, view seats, select, reserve, pay, receive tickets. Load about 1,000 users a day. v1 = app + DB: correct. Reveal: a global star announces one show; tickets open 10:00 AM; at 10:00:01 there are 500,000 users on the site. What fails first? Same system, new number, dead design. Numbers are architecture.

Steps 3–4: scale out, cache the reads

Adding 100 servers behind a load balancer is necessary, not sufficient: the database is still one, and 100 app servers can hammer it even harder. Look at what they read: 500,000 people load the same event page and the same seat map. One cache entry serves 500,000 requests; DB reads collapse to almost nothing. Caveat: a seat map 5 seconds stale is fine to look at, never fine to sell from. Cache the browsing. Never the buying. Browsing reads come from cache; the purchase decision happens only inside the database transaction.

Steps 5–6: the last seat and a failing payment

ProblemFix
1 The last-seat race: buyers A and B, same seat, same millisecondAtomic check + write in one transaction, constraint as backstop: exactly one winner, one clean "sold out".
2 The winner still has to pay: payment takes a minute and can fail. Marking the seat sold too early strands seats on failed payments; never holding it lets someone else buy it mid-payment.A reservation state machine with a clock: Available → (select seat) Reserved with a 10-minute hold → (payment) SOLD; on failure or timeout → Released and the seat returns to Available.

Every arrow is a business rule the system enforces: who may move a seat between states, and when. Architecture must handle concurrency and time, not just boxes and lines.

Step 7: the result

Browsing path: Users → CDN + cache → done (never touches the DB). Buying path: Users → load balancer → app servers (1–3) → PostgreSQL transaction (bookings, atomic) → payment gateway (with timeout + circuit breaker). Redis holds events and seat maps. One problem taught seven concepts: performance, scalability, load balancing, caching, concurrency, transactions, reliability. Every box has a "birthday": the exact moment in the story that forced it.

5. Putting it all together: design an online food delivery system

The brief. Functional: customer browses restaurants and menus, places an order, pays online; the restaurant receives and confirms the order; a driver delivers; the customer tracks the order. Non-functional: 100,000 registered users; response time under 2 seconds; 99.9 % availability; payments must be secure. Eight steps; each is one section of the lecture.

Every box exists because a driver demanded it. Nothing here is decoration. This is one defensible answer, not the only one.

6. How to architect any system

Problem → Requirements → Domain → Quality attributes → Components → Architecture → Communication → Technology → Trade-offs. Problem first; requirements split into functional and non-functional; the domain gives you components, the drivers give you structure; choose communication styles; choose technology last; write down every trade-off you accepted.

The seven-question checklist (before you draw a single box)

  1. What problem are we solving?
  2. What are the functional requirements?
  3. What are the important non-functional requirements?
  4. What are the major concepts and components in the domain?
  5. How should those components communicate?
  6. What happens when the system gets slow, overloaded or fails?
  7. Why did we choose this architecture over the alternatives?

Answering these seven well is worth more than knowing thirty architecture patterns.

Written questions

W1. Walk through the university registration exercise and explain why microservices were rejected.

v1 is a modular monolith with one DB (auth, courses, registration, reports). The 9 AM reveal (15,000 simultaneous registrations, capacity never exceeded) exposes the seat race (two students see '1 free', result 101/100); fixed by an atomic transaction (check + decrement) with a DB constraint seats >= 0, which selects transactional SQL. With three developers and $500 a month the design is 2 stateless app servers behind a load balancer, PostgreSQL and a Redis cache. Microservices rejected: one team means no coordination problem, one database gives strong transactions, no ops capacity for many deployments, and the spike is solved by stateless servers + cache.

W2. Explain how the facts changed the food delivery architecture from a monolith to microservices.

With today's evidence one modular monolith fits. Then 5M users, 50k concurrent and 10k orders/minute create four different load shapes (search reads, ordering write spike, payment must never fail, GPS firehose) that a single box can only scale in one way. Five teams, 20 developers, DevOps and $15,000/month tick every checklist item (teams blocking each other, different scaling needs, deploy independence, ops maturity), so microservices are justified: API gateway, database per service, events via a broker (sync order and pay, async after OrderPlaced) and per-service scaling.

W3. Design the ticket booking system for a 500,000-user spike and explain the seat reservation state machine.

Browsing path: users, CDN and cache (event page and seat map), never touching the DB. Buying path: load balancer, several app servers, one PostgreSQL transaction with a constraint (atomic last-seat check), then a payment gateway with timeout and circuit breaker. Cache the browsing, never the buying. Reservation state machine: Available, select seat gives Reserved with a 10-minute hold, payment gives SOLD, failure or timeout gives Released and the seat returns to Available; this prevents both stranded seats and mid-payment double sales.

W4. Apply the eight steps to an online food delivery system for 100,000 users and justify a modular monolith.

Concepts: customer, restaurant, driver, order, payment, delivery. Actions: browse, order, pay, deliver, track. Drivers: scalability (load balancer, stateless servers, caching), performance (cache, async, parallel), reliability (no SPOF, replicas, timeouts), security (HTTPS, never trust client, delegate card data). Components: order, restaurant and menu, payment, delivery, notification. Style: one small team and no component needing independent scaling today, so a modular monolith. Sync: browse, order, authorise payment; async: receipts, notify restaurant, analytics, driver assignment. Add load balancer with 2+ app instances, cache, queue, DB replica. Failure drill for payment: timeout, circuit breaker, pending-payment order.
