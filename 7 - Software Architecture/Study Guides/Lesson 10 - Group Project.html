Group Project: Process, Scrum and Microservices

Covers the 7-week cross-functional microservices project: the two cases (Apartment Management, University Services), team allocation and roles, mandatory technology and architecture requirements, governance, Jira / Scrum / GitHub rules, Definition of Ready and Done, deliverables and templates, assessment rubric and the demonstration checklist. Includes a short background on process models. No prior attendance needed.

Source: the seven Group Assignment documents (main brief, two case scopes, group responsibilities, rubric, Jira/GitHub/Scrum guidelines, deliverable templates). This lesson applies software process (Lesson 1) and architecture (Lessons 2–9) to a team project.

Learning outcomes

  • Describe the structure, aims and rules of the cross-functional microservices project
  • Explain the mandatory architecture requirements and cross-team governance
  • Apply Scrum, Jira and GitHub rules: stories, acceptance criteria, Definition of Ready / Done, pull requests
  • List the deliverables, templates and assessment criteria

0. Background: software process models (short recap)

The lectures list "software process models" as already discussed and the project uses Scrum; this table is a brief background summary, not slide content.

ModelIdeaFits when

Iterative / incrementalBuild in repeated cycles, each adding working functionalityRisk reduction and early feedback needed

A Team Lead is mandatory; roles may be combined or rotated but changes must be visible in Jira or progress reports, and no student may hold only a ceremonial role: every student must contribute to technical or quality deliverables. Role allocation is recorded in the proposal.

Common responsibilities of every team

  • Appoint a Team Lead for weekly cross-team synchronisation; maintain one Jira project (epics, stories, acceptance criteria, tasks, bugs, sprint evidence, reports, dependencies).
  • Develop the allocated microservices and frontend feature modules; own the DB/schema of each service with versioned scripts or migrations.
  • Publish and maintain OpenAPI specs and announce breaking API changes before implementation.
  • Use pull requests and code review (no direct commits to protected main); provide Postman tests, execution evidence and defect records; take part in shared frontend integration, gateway routing, Docker Compose integration, deployment and release validation; submit team documentation and individual contribution evidence.

4. Required technology and architecture

AreaRequired standard
FrontendOne shared React + TypeScript + Redux application; teams own feature modules in the shared codebase; consistent component library and design system
BackendSpring Boot microservices exposing REST APIs; controller-service-repository/domain organisation; Hibernate/JPA
DatabaseMySQL; each microservice owns a separate database or schema and may not read another service's database
SecurityJWT authentication, role-based authorisation, secure password storage, request validation, safe error responses, protected endpoints
API docs and testingOpenAPI/Swagger and Postman collections
ContainersDocker images per service; Docker Compose for local integrated execution
Version controlOne GitHub organisation per project; one repository per microservice; one shared frontend repository
TrackingOne Jira project per team (its own backlog; dependencies synchronised with the other three teams)
CI/CDGitHub Actions must at minimum build and test on pull requests; automated deployment encouraged, not required
DeploymentA working integrated release on an instructor-approved cloud or university environment

Mandatory microservice architecture requirements

  • Business capabilities separated into independently deployable microservices with explicit ownership.
  • An API Gateway as the controlled entry point routing frontend requests to services.
  • A centralised authentication service issuing JWTs; services validate authorisation for protected operations.
  • Each service owns its data store; cross-service database access is prohibited.
  • Inter-service communication through documented REST APIs; teams define timeout, error and failure behaviour.
  • Consistent response conventions, validation rules, HTTP status codes and centralised exception handling.
  • Docker Compose runs the complete local system including services and databases.
  • Health information and usable logs for diagnosing failures; versioned OpenAPI contracts maintained throughout.
  • An integrated frontend with modular feature ownership sharing navigation, authentication state and design conventions.

Optional advanced features (extra technical merit, never replacing the mandatory scope): RabbitMQ or Kafka, service discovery, distributed tracing, Kubernetes, centralised log aggregation, circuit breakers, automated cloud deployment.

Cross-team governance

  • A Project Integration Council of the four Team Leads meets weekly, recording decisions, dependencies, interface changes, integration risks and action owners.
  • API contract changes are communicated before implementation, documented in the project-documentation repository and reflected in dependent Jira issues. No team may silently change shared authentication, gateway routes, common data definitions or response formats.
  • Shared frontend changes follow pull-request review and must not break other teams' modules.
  • Integration responsibility is shared by all four teams; the Team Lead coordinates but is not solely responsible.
  • Teams choose their own sprint duration (justified, time-boxed, visible in Jira) with at least two completed development iterations before the final release and closure.

Weekly liaison checklist: unresolved dependencies and blocked Jira issues; API or shared-model changes; shared frontend integration status and merge risks; Docker Compose and environment compatibility; integration defects with owners, dates and retest status; shared architecture decisions and contract registry; a concise status update to the full team. Shared integration duties for all eight teams: contribute to the frontend only by reviewed PRs; register gateway routes and test unavailable-service responses; publish OpenAPI definitions with examples and change notes before dependent work; never access another service's database; provide image, environment variables, health checks, dependencies, ports and startup instructions for Compose; write at least one test of a workflow involving another team's service; support release-candidate validation and the tagged final release; maintain READMEs.

User story format"As a [role], I want [capability], so that [benefit]." Acceptance criteria must be testable (bullets or Given-When-Then). Example: Given an eligible user and an available facility, when the user submits a valid reservation request, then the reservation is created with Pending status and becomes visible to the resource manager. Avoid "Create backend" or "Do frontend" (no user value); split stories that cannot be completed, tested and reviewed within a sprint; link tasks and tests to the story; add dependency links when another team's API is needed.

Workflow statuses: Backlog (defined, not committed) → Ready (meets Definition of Ready) → In Progress → Code Review (PR awaiting review) → QA / Verification (tested against acceptance criteria) → Done (meets Definition of Done with linked evidence); Blocked records blocker, dependency, owner and next action.

Scrum guidance

  • Sprint length is the team's choice (1 or 2 weeks recommended), justified in the plan and used consistently unless a documented retrospective changes it.
  • Hold sprint planning, short progress coordination meetings, sprint review and retrospective; keep the sprint goal visible in Jira; do not overload the sprint with unestimated work; move unfinished items back or to a justified next sprint (never mark incomplete work Done); keep a final stabilisation window for integration, defects, deployment, documentation and demo preparation.

Shared milestone dates, API freeze, release candidate and final release must be aligned across the four Jira projects; each team stays responsible for testing its behaviour in the complete system.

GitHub

  • Organisation per project with repositories: shared-frontend, api-gateway, identity-access-service, the team services, deployment-infrastructure, project-docs (names may be shortened but ownership and purpose must be clear; do not duplicate repos to avoid integration).
  • Branching and PRs: main protected, no direct pushes; feature branches such as feature/AMS-G3-invoice-generation or fix/USM-G7-status-validation; each PR states purpose, linked Jira issue, screenshots or API evidence, testing performed and known limitations; at least one meaningful peer review (shared frontend, gateway, security or integration changes reviewed by the relevant liaison or owner); resolve comments or record a justified decision; keep PRs focused; keep a clear release tag history.
  • Commit traceability: concise coherent commits that reference the Jira key (e.g. AMS-G3-24 add invoice balance calculation); do not mix unrelated features, generated folders, secrets and documentation; no artificial commits to inflate activity; contribution quality, review behaviour, testing and integration work matter more than raw commit count.
  • Hygiene: proper .gitignore; commit .env.example never real secrets; synthetic data only; enable dependency and code scanning where available; remove debug credentials, hard-coded tokens and sensitive logging before release; document third-party dependencies and licences.
  • CI and releases: each service builds on PRs with GitHub Actions; the shared frontend runs type checking, build and available tests; a failed required check must be fixed before merge unless the teaching team approves; at least one release-candidate tag and one final release tag identifying compatible frontend, gateway, service, database and infrastructure versions; deployment must be reproducible.

Written questions

W1. Describe the structure of the group project and the mandatory architecture requirements.

Seven weeks; eight teams of seven; two projects (Apartment Management, University Services) each built by four teams who own bounded microservices but are jointly responsible for the integrated product. Mandatory: independently deployable services with explicit owners, an API Gateway, a centralised JWT authentication service, one database or schema per service with no cross-service DB access, documented REST APIs with defined timeout and failure behaviour, consistent response conventions and centralised exception handling, Docker Compose for the full local system, health information and logs, versioned OpenAPI contracts and a shared modular React frontend.

W2. Explain the cross-team governance rules and why they are needed.

A Project Integration Council of the four Team Leads meets weekly and records decisions, dependencies, interface changes, risks and owners. API contract changes must be announced before implementation and documented; nobody may silently change shared authentication, gateway routes, data definitions or response formats; shared frontend changes need reviewed PRs. They are needed because each team's services depend on others' APIs, and uncoordinated changes would break the integrated release (Conway's law: communication structure shapes the system).

W3. Define the Definition of Ready and Definition of Done and write a user story with Given-When-Then acceptance criteria for a reservation.

Ready: clear purpose and value, testable criteria, dependencies and API assumptions identified, sufficient design, estimate and owner, fits the sprint. Done: acceptance criteria pass with evidence linked, code reviewed and merged by PR, tests pass, API docs and README updated, no secrets committed, integrated environment not broken, Jira updated. Story: As an eligible user, I want to reserve an available facility, so that I can use it at a set time. Given an eligible user and an available facility, when the user submits a valid reservation request, then the reservation is created with Pending status and is visible to the resource manager.

W4. List the GitHub workflow rules for branching, pull requests, commits and releases.

Main is protected with no direct pushes; feature or fix branches named with the Jira key; each PR states purpose, linked Jira issue, evidence, tests and limitations and gets at least one meaningful peer review; commits are coherent and reference the Jira key; contribution quality matters more than commit count; CI builds and tests on every PR and failures are fixed before merge; at least one release-candidate tag and one final tag identify compatible versions; no secrets, synthetic data only.
