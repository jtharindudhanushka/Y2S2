03  Facade Structural

Intent (GoF)Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.
Use whenClient must call many subsystem classes in the right order to do one job; you want one simple entry point (“one door, many rooms”). Wedding planner, restaurant waiter, Netflix “Play”, BankService.
Trigger words“one simple interface”, “single entry point”, “hide the complexity of”, “by internally calling inventory, payment, notification and login services”, “combine air tickets, hotels and taxis”, “complex subsystem calls scattered everywhere”.
ParticipantsFacade (knows which subsystem does what, delegates) · Subsystem classes (do the real work, don’t know the facade) · Client (talks only to the facade).
Key rules (slides)Facade does NOT add functionality · it is a wrapper / point of entry · client can still access subsystems directly if needed · there can be more than one facade for a big system.

Java

public interface IAccount {
    void deposit(double amt);
    void withdraw(double amt);
    double getBalance();
}
public class SavingAccount implements IAccount {
    private double balance;
    public void deposit(double a)  { balance += a; }
    public void withdraw(double a) {
        if (a > balance) throw new IllegalStateException("Insufficient");
        balance -= a;
    }
    public double getBalance() { return balance; }
}
// CurrentAccount, InvestmentAccount: same shape, own rules
public class BankService {                 // FACADE
    private Map<String, IAccount> accounts = new HashMap<>();

    public void createAccount(String no, String type) {
        accounts.put(no, type.equals("SAVING") ? new SavingAccount()
                       : type.equals("CURRENT") ? new CurrentAccount()
                       : new InvestmentAccount());
    }
    public void deposit(String no, double a)  { accounts.get(no).deposit(a); }
    public void withdraw(String no, double a) { accounts.get(no).withdraw(a); }
    public void transferMoney(String from, String to, double a) {
        accounts.get(from).withdraw(a);    // coordinates a sequence
        accounts.get(to).deposit(a);
    }
    public double getBalance(String no) { return accounts.get(no).getBalance(); }
}
// CLIENT: one object, one entry point
BankService bank = new BankService();
bank.createAccount("John", "SAVING"); bank.createAccount("Alice", "CURRENT");
bank.deposit("John", 5000);
bank.transferMoney("John", "Alice", 1000);

Questions & model answers

Approach to provide one simple interface for borrowing books by internally calling inventory, payment, notification and login services. Quiz 3 Q5
Facade. Create LibraryFacade.borrowBook(userId, bookId) which, in order, calls LoginService.verify() → InventoryService.checkAvailable()/reserve() → PaymentService.chargeFee() → NotificationService.sendConfirmation(). The librarian UI calls only the facade, so it is decoupled from four services; a change in any service is handled inside the facade.
public class LibraryFacade {
    private LoginService login = new LoginService();      private InventoryService inv = new InventoryService();
    private PaymentService pay = new PaymentService();    private NotificationService note = new NotificationService();
    public boolean borrowBook(String user, String book) {
        if (!login.verify(user) || !inv.isAvailable(book)) return false;
        inv.reserve(book);  pay.chargeFee(user);  note.send(user, "Borrowed " + book);
        return true;
    }
}
Travel website: user books air ticket, hotel and taxi; collect data from different web services. Draw a diagram; which pattern for the sub-system that combines them and why? Challenges and mechanism? 2022 Q1.1–1.2 (15)
{{uml:travel}}
Facade for combining: TravelBookingFacade.bookTrip() calls Air, Hotel and Taxi services and returns one itinerary — user does one action, subsystem complexity hidden, low coupling. Challenges: (1) facade grows into a God class as services are added; (2) a failure in one service (taxi down) affects the whole booking / single point of failure; (3) partial booking consistency (air booked, hotel failed). Mechanisms: split into smaller facades; delegate only; timeouts + retries + fallback and run facade as stateless replicas; compensating actions (cancel air if hotel fails). For connecting each sub-service to different third-party web services → Adapter (Note 04).
Can you access each subsystem directly? Should there be only one facade? slide Q&A
Yes — the facade is a convenience, not a lock; advanced clients may use subsystems directly. No — a complex system can have several facades (one per use-case area) to avoid a God class.
How is Facade different from Adapter?
Adapter converts one interface into another the client expects (usually wraps one object, makes it compatible). Facade simplifies: a new, higher-level interface over many objects. Adapter = translator, Facade = simplifier.

Mistakes

Putting business logic in the facade (it only delegates) · drawing subsystems pointing back to the facade (they don’t know it) · calling it creational · confusing with Adapter (interface conversion) or Proxy (same interface, access control).
