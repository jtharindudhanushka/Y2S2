How to answer a 25-mark case study

  1. Understand the problem first (case-study lecture): what varies? what must stay fixed? what will change in future?
  2. Categorize: creation / structure / behaviour → decision map.
  3. Name the pattern + category + GoF intent (1 line).
  4. Map the case to participants (“Target = Printer, Adapter = …”) — this is where marks are.
  5. Reasons (2–4): problem removed + benefit (coupling, OCP, reuse, consistency).
  6. Diagram: scenario diagram (boxes/arrows) if asked “depict the scenario”; class diagram with stereotypes, +/−/#, underline static, correct arrows.
  7. Code: interface → concrete → pattern class → 3-line client.
  8. Challenges → mechanism pairs (table in each note).
  9. State assumptions (paper says so).

public void placeOrder(Order o) {
    Validator chain = new InventoryCheck();                                   // CoR
    chain.linkWith(new FraudCheck()).linkWith(new DeliveryAreaCheck());
    if (!chain.validate(o)) { System.out.println("Order rejected"); return; }

Smart home — Facade (“away mode”), Adapter (Zigbee/Bluetooth devices), State (device modes), Proxy (remote/authorization). LMS — Factory (modules), Proxy (lazy content, access), Template (exam/grading flow), Decorator (premium features). ATM — State (idle/card inserted/PIN ok), Singleton (bank connection), Proxy (authorization), CoR (cash dispenser denominations / validations). Shopping cart — Decorator (promotions/gift wrap), Template (checkout), Factory (payment), CoR (validations), Singleton (ID/tax). Travel — Facade + Adapter. Generic answer bank

Why not inheritance for everything?Class explosion, rigid compile-time hierarchy, changes ripple to subclasses ⇒ prefer composition (Decorator, State, Strategy, Adapter).
Use of interfaces / abstract classesInterface = contract (CAN-DO), enables polymorphism and loose coupling, DIP, swap implementations, mocking. Abstract class = shared code + enforced steps (IS-A), used by Template Method and abstract Decorator/Handler.
General pattern trade-offs+ reuse, flexibility, loose coupling, maintainability, common vocabulary. − more classes/abstraction, learning curve, overuse = over-engineering; “Is it worth the extra abstraction?” (case-study lecture).
Configurability (parameters change over time)Move rates/limits to external config (DB table, properties/YAML) read by a Singleton ConfigManager; admin UI to update; version and audit changes; no recompilation.
High Availability (HA) & Disaster Recovery (DR)HA: stateless services replicated behind a load balancer, health checks and auto-restart (Kubernetes), no single point of failure (avoid single Singleton server → replicas), DB replication/cluster, retries/timeouts/circuit breaker, fallback handler in CoR. DR: regular backups, replicated DB to a second region/data centre, defined RPO/RTO, automated failover, infrastructure-as-code to rebuild, periodic DR drills.

Q2 in every past paper: Microservices (not in the slides — standard answers)

{{uml:micro}}
Draw the scenarioClients → API Gateway → one service per business capability, each with its own DB; message broker for events; registry, config, monitoring; containers on Kubernetes. Library: Book, User, Borrowing, Notification, Catalog Search (search index e.g. Elasticsearch). Supermarket chain: Purchasing, Sales/POS, Warehouse/Inventory, Supplier, Branch, Reporting. Streaming: User Profile, Content Delivery (transcode + CDN), Recommendation (ML), Billing/Subscription, Analytics.
Scalability, fault isolation, continuous deploymentScalability: each service scales independently (horizontal pods, auto-scaling on CPU/requests; e.g. scale Content Delivery and Search, not Billing); stateless services; caching/CDN. Fault isolation: separate processes/DBs; circuit breakers, timeouts, bulkheads, retries with back-off; graceful degradation (recommendations down → show popular list). CD: own repo + CI/CD pipeline per service, automated tests, Docker images, blue-green/canary releases, versioned APIs; independent teams per service; centralized logging, metrics and tracing.
Data consistencyDatabase-per-service ⇒ no shared transactions; use Saga pattern (sequence of local transactions with compensating actions, choreography via events or orchestration), eventual consistency via event-driven messaging (Kafka), transactional outbox, idempotent consumers, CQRS for read models (catalog search), two-phase commit only where strong consistency is essential (rare), data versioning.
SecurityAPI Gateway as single entry: authentication (OAuth2/OpenID Connect, JWT tokens), authorization by role (RBAC); service-to-service: mutual TLS, service mesh, short-lived tokens; HTTPS everywhere; encrypt sensitive data at rest (PCI-DSS for payments); secrets vault; rate limiting, input validation, WAF; least privilege per service DB; audit logging and monitoring.
Same hardware/config for each platform? (2023)Consistent environments (containers/IaC) make deployment, scaling and failover predictable: any node can run any service, same performance baseline, easier capacity planning, automation, monitoring and troubleshooting; avoids “works on my machine”; simplifies DR (rebuild identical nodes). Exceptions: GPU nodes for ML recommendation services.
