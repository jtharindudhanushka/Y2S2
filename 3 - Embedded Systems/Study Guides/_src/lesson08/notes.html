1. Serial communication

  • Used by embedded systems to communicate with other systems: a PC, another microcontroller, a GPS module, a Bluetooth/Wi-Fi module, a display, a memory chip.
  • Serial sends one bit at a time over one line (plus ground).
  • Why not parallel? Parallel sends many bits at once but needs many wires and pins (scarce on a microcontroller), is costly, and over longer cables the bits arrive at slightly different times (skew) and the lines interfere (crosstalk), so the speed over distance is limited. Serial needs few pins, few wires and works over longer distances at high speed.

2. The USART

The USART (Universal Synchronous Asynchronous Receiver Transmitter) is a peripheral device that implements both asynchronous and synchronous serial communication. Why a separate peripheral? Sending a bit every 104 µs (at 9600 baud) with precise timing in software would occupy the CPU; the USART shifts the bits out and in by itself using its own baud rate generator, so the CPU only handles whole characters (and can do other tasks in between).

Asynchronous data transfer

  • The line is high when idle. Each character is framed: a start bit (0), then the data bits, least significant bit first, then the stop bit (1). 8N1 means 8 data bits, no parity, 1 stop bit, so 10 bits per character.
  • Example: ASCII 'A' = 0x41 = 01000001, sent as start 0, then 1 0 0 0 0 0 1 0 (LSB first), then stop 1.
  • Why is the baud rate important? There is no clock line, so the receiver times each bit with its own clock. Both ends must use the same baud rate (bits per second) or the bits are sampled at the wrong times and characters are garbled.
  • How does the receiver recognise characters? The falling edge of the start bit marks the beginning of a frame; the receiver then samples each bit in the middle of its bit time (it oversamples 16 times per bit) and checks the stop bit.
  • Character time at 9600 baud = 10 / 9600 = 1.04 ms, so about 960 characters per second.

3. Connecting to a PC

  • Serial port with a line driver: the PC's RS-232 port uses voltages of about ±3 to ±15 V (a logic 1 is a negative voltage), while the microcontroller uses 0 and 5 V. Why not connect directly? The levels and polarity differ and the RS-232 voltages would damage the microcontroller. A line driver (MAX232) converts between the levels (with charge-pump capacitors). Example: Arduino Severino (ATmega328P with MAX232) and a DB-9 connector.
  • USB port with a UART-to-USB interface controller: modern PCs have no serial port, so a chip converts the UART signals to USB. Arduino Duemilanove: ATmega328P with the FT232RL. Arduino Uno: ATmega328P with an ATmega16U2 (another microcontroller programmed as the UART-to-USB converter).
  • The PC then sees a virtual COM port. TX of one device connects to RX of the other (crossed), and the grounds are common. On the Uno the chip's PD0 (RXD) and PD1 (TXD) are Arduino pins 0 and 1.

4. How the USART transmits and receives

Transmitter

CPU writes the character to UDRn (transmit data buffer) → moved to the Transmit Shift Register → shifted out bit by bit on TXD by the baud rate generator, with the start and stop bits added by the pin control.

  • UDREn flag = data register empty (ready for a new character). TXCn flag = the whole frame in the shift register has been sent and UDRn is empty.
  • Which flag gives maximum throughput? UDRE: as soon as the data register is empty (the previous character has moved to the shift register) the next character can be loaded while the previous one is still being shifted out, so the line never idles. Waiting for TXC would leave gaps.
  • Purpose of TXC: to know when the last bit has really left (for example before turning off the transmitter, entering sleep mode, or switching a half-duplex line driver like RS-485 to receive).

Receiver

Bits arrive on RXD → pin control → synchronisation with the baud rate clock → Receive Shift Register assembles the frame → the character is transferred to the receive data buffer UDRn → RXCn flag set (unread data). Reading UDRn clears RXC.

  • Role of pin control: it connects the RXD/TXD pin to the USART and manages the pin direction when the receiver/transmitter is enabled (overriding the normal I/O function).
  • Need for shift registers: the data arrives bit by bit and must be assembled into a byte (or shifted out one by one on transmit); the shift registers do this and let the CPU work with a whole character, and with double buffering a new character can be received while the previous one is waiting to be read.
Summary sequences (slide)Receive: bits arrive on RXD → Receive Shift Register assembles bits → character moved to the receive data buffer → UDR gives access to the unread character → RXC = 1 → if RXCIE = 1, USART_RX_vect ISR runs → CPU reads UDR → RXC = 0.
Transmit: transmit data buffer empty → UDRE = 1 → if UDRIE = 1, USART_UDRE_vect ISR runs → CPU loads a new character into UDR → UDRE = 0 → character moves to the Transmit Shift Register → UDRE = 1 → bits transmitted on TXD.

Why enable and disable RX and TX separately? Enabling them connects the USART to the pins (taking over PD0 and PD1) and starts the hardware. Disabling them frees the pins for ordinary I/O and saves power, and a device that only transmits (or only receives) needs just one of them. The flags TXC is cleared by writing 1 (W1C) like the timer flags.

Setting the baud rate: choose a standard rate (2400, 4800, 9600, 14400, 19200, 28800, 38400, 57600, 76800, 115200, 230400, 460800, 921600). Why not other values? Standard rates are what PCs, terminal programs and USB converters support, and they divide common crystals with small error. In code: UBRR0 = 16000000 / (16 * 9600UL) - 1;. Why UL? On the AVR an int is 16 bits (maximum 32 767), and 16 × 9600 = 153 600 would overflow; UL (unsigned long, 32 bits) forces 32-bit arithmetic.

Baud rate error

Actual baud rate = F_CPU / (16 × (UBRR + 1)). Baud rate error = (actual − desired) / desired × 100 %.
9600 baud at 16 MHz: UBRR = 16 000 000 / (16 × 9600) − 1 = 103.17, so UBRR = 103; actual = 16 000 000 / (16 × 104) = 9615.4 baud; error = +0.16 %.

  • What if the error is high? The receiver's bit sampling drifts from the middle of each bit; over the 10 bits of a frame the error accumulates, so bits are mis-sampled and characters are corrupted (about 2 to 3 % total mismatch is the practical limit). 115 200 baud at 16 MHz (−3.55 %) is unreliable without the double-speed mode (U2X0).
  • How to minimise error? Choose a baud rate with a small error, use a crystal that divides exactly (an 18.432 MHz crystal, as shown in the lecture, gives UBRR = 119 for 9600 baud with 0 % error), or use the U2X double speed mode.

6. System 16: charEncloser (polling)

Task: receive characters from the PC, enclose each in square brackets and send it back (typing a returns [a]). Hardware: the Arduino Uno's USB interface (no extra parts): the ATmega328P PD0/PD1 connect to the USART-to-USB interface; the board connects to the PC with the USB cable. In the schematic: USB → USART-to-USB interface (TXD to RXD pin 2, RXD to TXD pin 3), 10 kΩ reset pull-up, 16 MHz crystal.

// charEncloserC.c
#include <avr/io.h>                                  // I/O definitions

void transmitChar(char ch)                            // transmitChar() subroutine
{
    while (!(UCSR0A & 0b00100000));                   // poll for data register empty flag (UDRE0)
    UDR0 = ch;                                        // write character to data register
}

int main(void)
{
    UBRR0 = 16000000 / (16 * 9600UL) - 1;             // set baud rate as 9600 bps
    UCSR0B = UCSR0B & 0b11111011;                     // UCSZ02 = 0
    UCSR0C = UCSR0C | 0b00000110;                     // specify char size as 8-bit (UCSZ01, UCSZ00 = 1)
    UCSR0B = UCSR0B | 0b00011000;                     // enable RX and TX (RXEN0, TXEN0)
    while (1)
    {
        while (!(UCSR0A & 0b10000000));               // poll for receive complete flag (RXC0)
        char ch = UDR0;                               // read character from data register
        transmitChar('[');
        transmitChar(ch);                             // call transmitChar()
        transmitChar(']');
    }
    return 0;
}
// Arduino wrapper version
void setup() { Serial.begin(9600); }                  // set baud rate
void loop() {
  if (Serial.available()) {                           // if new data available
    char ch = Serial.read();                          // read incoming character
    Serial.print('[');
    Serial.print(ch);                                 // print enclosed character
    Serial.print(']');
  }
}

Testing: terminal emulators

A terminal emulator is a program that sends the characters you type to a serial port and shows what arrives (the software version of an old computer terminal). Examples: the Serial Monitor of the Arduino IDE (set the baud rate to match), the Terminal window extension of Atmel/Microchip Studio, PuTTY. Typing a then b shows [a][b]. CR and LF: carriage return (\r, ASCII 13) moves the cursor to the start of the line; line feed (\n, ASCII 10) moves down one line. Terminals can append them (the "No line ending / Newline / Carriage return / Both" setting) and println() sends CR + LF.

7. System 17: charEncloserUsingInterrupts

The USART raises USART_RX_vect when a character is received and USART_UDRE_vect when the data register is empty, so no waiting is needed in main().

// charEncloserUsingInterruptsC.c
#include <avr/io.h>
#include <avr/interrupt.h>
char ch[] = {'[', ' ', ']'};                     // character array with enclosing brackets
volatile int i = 0;                              // array index

int main(void)
{
    UBRR0 = 103;                                 // 9600 bps
    UCSR0B = UCSR0B & 0b11111011;                // UCSZ02 = 0
    UCSR0C = UCSR0C | 0b00000110;                // 8-bit
    UCSR0B = UCSR0B | 0b00011000;                // enable RX and TX
    UCSR0B = UCSR0B | 0b10000000;                // enable receive complete interrupt (RXCIE0)
    sei();                                       // enable global interrupts
    while (1) { }
    return 0;
}

ISR(USART_RX_vect)                               // receive complete
{
    ch[1] = UDR0;                                // read character into the array
    UCSR0B = UCSR0B & 0b01111111;                // disable receive complete interrupt
    UCSR0B = UCSR0B | 0b00100000;                // enable data register empty interrupt (UDRIE0)
}

ISR(USART_UDRE_vect)                             // data register empty
{
    UDR0 = ch[i++];                              // send next character and increment the index
    if (i == 3)                                  // all three characters written
    {
        i = 0;                                   // reset the index
        UCSR0B = UCSR0B & 0b11011111;            // disable data register empty interrupt
        UCSR0B = UCSR0B | 0b10000000;            // enable receive complete interrupt
    }
}

The UDRE interrupt must be disabled when there is nothing more to send, otherwise it fires continuously (the flag stays 1 while the register is empty). Reading UDR0 clears RXC; writing UDR0 clears UDRE.

Q3: why the array needs at least four elements

The LM35 range is −55 °C to 150 °C. The longest text is -55 (the minus sign and two digits) or 150 (three digits): three characters. A C string must end with the null terminator '\0', so the array needs 3 + 1 = 4 elements.

Q4: stdio streams (Microchip Studio)

A stream is a sequence of bytes to or from a device. FDEV_SETUP_STREAM(put, get, flags) makes a user-defined stream from two functions. After assigning it to stdin and stdout, getchar() and printf() work through the serial port.

#include <avr/io.h>
#define F_CPU 16000000UL
#include <util/delay.h>
#include <stdio.h>

static int uartPut(char c, FILE *stream)             // write function
{
    while (!(UCSR0A & (1<<UDRE0)));
    UDR0 = c;
    return 0;
}
static int uartGet(FILE *stream)                     // read function
{
    while (!(UCSR0A & (1<<RXC0)));
    return UDR0;
}
static FILE uart = FDEV_SETUP_STREAM(uartPut, uartGet, _FDEV_SETUP_RW);

int main(void)
{
    // initADC() and initUSART() as in Q2
    stdin  = &uart;                                  // standard streams use the serial port
    stdout = &uart;
    char ch = 'N';
    while (1)
    {
        if (UCSR0A & (1<<RXC0)) ch = getchar();   // do not block when nothing was received
        if (ch == 'Y')
        {
            ADCSRA |= (1<<ADSC);
            while (ADCSRA & (1<<ADSC));
            int temp = (int)(ADCW * 5.0 / 1024 * 100);
            printf("%d\n", temp);                    // send the temperature
            for (int i = 0; i < 100; i++)            // wait 1 s but keep listening
            {
                _delay_ms(10);
                if (UCSR0A & (1<<RXC0)) { ch = getchar(); if (ch != 'Y') break; }
            }
        }
    }
}

1. Why serial? Why not parallel?

Embedded systems talk to other systems: a PC (data logging, debugging), or another embedded system (an RC car or aircraft talks to its remote controller over radio: two embedded systems, wireless, but still serial rules).

Serial sends one bit at a time, one after another, so it is slower. Parallel sends several bits at once on several wires, so it is faster. So why serial?

The main reason: I/O pins are precious 8-bit parallel needs 8 wires to send + 8 to receive = 16 I/O pins. Serial needs only 2 (TX and RX). The ATmega328P has only 23 I/O pins; 16 for communication would leave 7 for all the sensors and actuators. A tiny 8-pin ATtiny would have nothing left. Pins are needed for sensors and actuators, so embedded systems use serial.

Second problem of parallel: crosstalk. Current in a wire makes a magnetic field that induces a small current in the wire next to it. A 0 sent on one wire can arrive looking like a 1. It gets worse with long wires. Twisting wire pairs (twisted-pair / UTP network cable) reduces it, but the pin problem remains.

Why the receiver must line up with the sender: it receives a stream of bits and has to know where each character starts and ends (LSB to MSB) to turn 8 bits back into one ASCII character. It can do that either from a shared clock (synchronous) or from a known rate plus start/stop bits (asynchronous).

3. The asynchronous frame

Each character is framed between a start bit (always 0) and a stop bit (always 1), then sent LSB first. The idle line sits at 1. 8 data bits + start + stop = a 10-bit frame. Start and stop are called synchronization (sync) bits.

Figure 1. One 10-bit frame carrying 'A'. Time runs left to right; each box lasts 1/baud seconds.
  • Baud rate = bits per second (bps), named after the French engineer Émile Baudot. 9600 bps = 960 frames = 960 characters per second.
  • Character size can be 5 to 9 bits: 8 is normal; 9 = 8 data + 1 parity bit for error checking (11-bit frame); 5 = a hex digit (4 bits) + parity (7-bit frame).
  • How the receiver decodes (lecturer's 1 bps example): the line drops to 0 → "start bit"; it starts counting; bits 1–8 are data; at the 10th bit time it expects a 1 (stop). If it sees 1, it accepts the 8 bits as a character.
  • If the speeds don't match (e.g. sender 10% slow): at the 10th bit time the receiver reads the MSB instead of the stop bit. If the MSB is 1 it accepts a wrong character; if 0 it detects a framing error and the output is garbage. This is why a wrong baud rate in the Serial Monitor prints weird characters.

4. The USART and why it is a separate peripheral

USART = Universal Synchronous/Asynchronous Receiver Transmitter (UART when used asynchronously). It is a peripheral on the chip, like the timers and ADC, with a transmitter (TX) and a receiver (RX). Why separate hardware? The CPU is a single, slow (MHz), low-power core. If the USART does the bit-by-bit sending and receiving, the CPU is free for computation. It is the same reason we use hardware timers.

The ATmega328P has one USART, so its registers end in 0 (UBRR0, UDR0…). Chips with several (the ATmega2560 on the Arduino Mega has four) use 0, 1, 2, 3; writing the number into the name makes code easy to port.

Pins: RXD = PD0 = D0, TXD = PD1 = D1. Setting RXEN0/TXEN0 overrides their GPIO function (the "pin control" block). So connect nothing else to D0/D1 while using serial; if serial misbehaves, check those two pins first. If you don't need serial, they are normal I/O pins.

Why a line driver? Voltage levels RS-232 comes from the 1960s mainframe era: logic 1 = −3 to −25 V, logic 0 = +3 to +25 V. The microcontroller uses TTL: 1 = 2–5 V, 0 = 0–0.8 V. Connecting them directly would mismatch and damage the chip, so a line driver (MAX232) converts TTL ↔ RS-232 both ways. The USB chips do the voltage and the protocol conversion.

6. How the transmitter and receiver work

Figure 3. USART transmitter and receiver. The shift registers turn 8 parallel bits into a serial stream and back.
  • Transmit: the CPU writes a character to UDR0. When the shift register is free, the character moves into it (so UDR0 empties and UDRE0 is set), gets framed, and is shifted out on TXD at the baud rate. Writing a new character clears UDRE0. UDRE0 is 1 after reset, because the buffer starts empty.
  • Receive: the sync unit recognises the start/stop bits, the bits fill the receive shift register, the character (without start/stop) moves to UDR0, and RXC0 is set. Reading UDR0 clears it.
  • Writing to UDR0 while it is not empty: the new character is ignored (lost). Reading UDR0 without waiting for RXC0 returns the same old character again.
UDRE or TXC: which gives maximum throughput? [EXAM] UDRE. It is set as soon as the buffer is free, so the next character waits in UDR0 while the previous one is still shifting out. TXC waits until both the buffer and the shift register are empty, which leaves a gap.
Then what is TXC for? [EXAM] Knowing that everything has really gone out: (1) half-duplex links, where you release the line only when finished, like saying "over" on a walkie-talkie; (2) power saving: switch off the USART only after the last bit has left, e.g. a battery-powered sensor behind enemy lines.

8. Baud rate: UBRR, the UL suffix, and the baud rate error

Formulas (normal speed) baud = F_CPU / (16 × (UBRR0 + 1))   ⇒   UBRR0 = F_CPU / (16 × baud) − 1
error % = (actual baud − desired baud) / desired baud × 100   (keep below about 2.5%)
Step (9600 bps at 16 MHz)Result
UBRR0 = 16 000 000 / (16 × 9600) − 1103.17 → register holds integers only → 103
Actual baud = 16 000 000 / (16 × 104)9615.38 bps

Standard rates: 2400, 4800, 9600 (most common, the Arduino default), 14400, 19200, 28800, 38400, 57600, 76800, 115200, 230400, 460800, 921600 bps. Both ends must use the same one.

Why the UL suffix in UBRR0 = 16000000 / (16 * 9600UL) - 1; [EXAM] In avr-gcc, plain numbers are int = 16 bits. 16 × 9600 = 153 600 needs 20 bits, so as int only the lower 16 bits survive: 22 528. Then 16 000 000 / 22 528 − 1 = 709, giving a completely wrong baud rate. Writing 9600UL makes one operand unsigned long (32-bit), so the multiplication is done in 32 bits and gives 153 600, and UBRR0 = 103. It is a logic error, not a compile error: the compiler won't warn you.

Why errors matter: the receiver samples at its own rate. With a 10% error at 1 bps, the sender falls 1 s behind every 10 s, so the receiver reads the MSB where it expects the stop bit, giving a wrong character or garbage. Above about 2.5% the link is unreliable. For critical systems (missile guidance, a drone over a crowd) the target is 0%: use a "baud-rate" crystal such as 18.432 MHz. Changing F_CPU changes every timer, PWM and ADC calculation too.

9. System 16: char encloser (polling)

The PC sends a character, the board replies with it in brackets: send a, get [a]. No wiring needed: just the Uno and its USB cable.

// charEncloserC.c
#include <avr/io.h>

void transmitChar(char ch)
{
    while (!(UCSR0A & 0b00100000));      // wait until UDRE0 = 1 (buffer empty)
    UDR0 = ch;                            // write character to transmit
}

int main(void)
{
    UBRR0 = 16000000 / (16 * 9600UL) - 1; // 103 -> 9600 bps
    UCSR0B = UCSR0B & 0b11111011;         // UCSZ02 = 0
    UCSR0C = UCSR0C | 0b00000110;         // UCSZ01 = 1, UCSZ00 = 1 -> 8-bit characters
    UCSR0B = UCSR0B | 0b00011000;         // RXEN0 = 1, TXEN0 = 1
    while (1)
    {
        while (!(UCSR0A & 0b10000000));  // wait until RXC0 = 1 (new character)
        char ch = UDR0;                   // read it (clears RXC0)
        transmitChar('[');
        transmitChar(ch);
        transmitChar(']');
    }
    return 0;
}

How while (!(UCSR0A & 0b10000000)); works: the AND keeps only bit 7 (RXC0). While RXC0 = 0 the result is 0, !0 = 1, and the empty loop repeats; when RXC0 = 1 the result is non-zero, ! makes it 0, and the loop ends.
Lecturer's test questions: remove the UDRE wait in transmitChar and send a: you get only [a. '[' goes straight to the shift register, 'a' waits in UDR0, and ']' is written while UDR0 is still full, so it is ignored. Remove the RXC wait in main: the loop reads UDR0 over and over and keeps sending the old character, so try it and see.

Arduino version void setup() { Serial.begin(9600); }
void loop() {

  char ch = Serial.read();
  Serial.print('['); Serial.print(ch); Serial.print(']');

begin sets UBRR0 = 103, 8-bit, RX/TX on. available() returns the number of unread characters.
More Serial functions println adds \r\n (cursor to the next line); readString() reads a whole string; print(78, BIN) → 1001110, print(78, HEX) → 4E, print(1.2345, 3) → 1.234 (3 decimal places, cut off); Serial.end() turns RX/TX off so D0/D1 become normal I/O again.

Terminal emulator: software that imitates a 1960s "dumb" text terminal (TTY = teletype): keyboard + screen, 24 lines of 80 characters. Used for debugging, sensor calibration, module configuration, data logging. Examples: the Arduino Serial Monitor, or "Terminal for Atmel Studio" (Tools → Extensions and Updates), which can also save to a file. Choose the COM port and the baud rate to match. CR (\r, carriage return: back to the start of the line) and LF (\n, line feed / new line) come from typewriters; the terminal can append them to what you send ("No line ending" sends neither).

10. System 17: char encloser with interrupts

// charEncloserUsingInterruptsC.c
#include <avr/io.h>
#include <avr/interrupt.h>

char ch[] = {'[', ' ', ']'};             // middle element will hold the received character
volatile int i = 0;                      // array index, shared with the ISRs

int main(void)
{
    UBRR0 = 103;                         // 9600 bps
    UCSR0B = UCSR0B & 0b11111011;        // 8-bit characters
    UCSR0C = UCSR0C | 0b00000110;
    UCSR0B = UCSR0B | 0b00011000;        // enable RX and TX
    UCSR0B = UCSR0B | 0b10000000;        // RXCIE0 = 1: receive complete interrupt
    sei();                               // global interrupts
    while (1) { }                        // CPU free for other work
    return 0;
}

ISR(USART_RX_vect)                       // a character has arrived
{
    ch[1] = UDR0;                        // store it in the middle
    UCSR0B = UCSR0B & 0b01111111;        // stop receiving interrupts until it is sent
    UCSR0B = UCSR0B | 0b00100000;        // UDRIE0 = 1: start transmitting
}

ISR(USART_UDRE_vect)                     // UDR0 is empty: send the next character
{
    UDR0 = ch[i++];                      // send ch[i], then i = i + 1
    if (i == 3)                          // '[', char and ']' all written
    {
        i = 0;
        UCSR0B = UCSR0B & 0b11011111;    // UDRIE0 = 0
        UCSR0B = UCSR0B | 0b10000000;    // RXCIE0 = 1 again
    }
}

The receive interrupt is switched off while the bracketed character is being sent, so a second incoming character waits in the hardware buffer instead of overwriting ch[1]. i is volatile because the ISRs change it.

RECEIVE chainTRANSMIT chain
bits arrive on RXD → receive shift register assembles them → character moved to UDR0 → RXC0 = 1 → if RXCIE0, USART_RX_vect runs → CPU reads UDR0 → RXC0 = 0UDR0 empty → UDRE0 = 1 → if UDRIE0, USART_UDRE_vect runs → CPU writes UDR0 → UDRE0 = 0 → character moves to the shift register → UDRE0 = 1 → bits leave on TXD

L. What the lecturer explained in the lectures (2020 recordings)

From the six serial-communication recordings (folders 25–30 in Embedded Systems Lectures). [EXAM] marks things he tied to the exam.

L1. The "?" lines on the slides are exam questions [EXAM] "These statements with question marks on my slides are very important… for the exam point of view." He does not ask "what is baud rate?" or "what is UBRR?" (anybody can answer those). He asks things like why all baud rates are multiples of 80, or "using an example, explain the purpose of the UL suffix". The slide questions in this lesson: why not parallel; why a separate peripheral; why baud rate matters; how the receiver recognises characters; why not connect directly (line driver); UDRE or TXC for throughput; the purpose of TXC; the role of pin control; the need for shift registers; why enable/disable RX/TX; why not other baud values; why UL; what happens with a high error; how to minimise it; what a terminal emulator is; what CR and LF are.

L2. Serial vs parallel, sync vs async

  • A student said "the microcontroller processes one bit at a time". No: the ATmega328P is an 8-bit CPU and processes 8 bits at a time. The real reason for serial is pins: 8-bit parallel costs 16 I/O pins of the 23; an 8-pin ATtiny has only about 3 spare pins.
  • Students guessed "cost of wires"; he said the cost is small compared with the speed gained, so that's not it.
  • Crosstalk: the magnetic field of one wire induces current in the next, so a 0 can arrive as a 1. It is worse over long distances. Twisting the send and return wires so their fields cancel gives twisted-pair (UTP) cable.
  • Synchronous explained with two clocks joined by a wire: one bit per clock pulse, and the receiver need not know the speed. Asynchronous saves that wire, but the receiver must know the rate.
  • The serial standard is RS-232 ("Recommended Standard 232").

L3. Why a separate USART: "living on another planet" [EXAM]

  • Same reason as timers: the CPU is single-core, MHz not GHz, low power. Offload timing, counting, ADC, PWM and communication to peripherals and keep the CPU for computation.
  • "Embedded systems programming is like living on another planet": a small oxygen tank and one bottle of water, so you save every molecule. On PCs you lived in the luxury of gigabytes and gigahertz; here you must save every bit of resource. "One particular thing I am going to assess" in the exam is whether you think this way.

L4. Frames and baud rate

  • Worked at 1 bps sending 'A' then 'B': start bit in second 0–1, LSB in 1–2… MSB in 8–9, stop in 9–10; the next start at the 11th second, stop at the 20th.
  • Baud rate is named after the French engineer Émile Baudot. 9600 is the most common rate and the Arduino default.
  • Parity bit: "I am not going to explain parity, you need to read and learn."
  • Why standard rates are multiples of 80 [EXAM]: dumb terminals showed 80 characters per line, 24 lines. 9600 bps = 960 characters/s = 12 lines per second, half a screen. "No relationship to the word size of the microprocessor."
  • A wrong baud rate makes the receiver "go mad" and the Serial Monitor prints weird characters.

L5. RS-232 and USB bridges

  • DB9 = D-shaped subminiature, 9 pins; only RXD and TXD are used for data.
  • RS-232 dates from the 1960s mainframe era (vacuum tubes, high voltages; introduced by IBM): 1 = −3 to −25 V, 0 = +3 to +25 V. Today we use TTL (2–5 V high, 0–0.8 V low) and newer CMOS uses about 3.3 V. Asked why the voltages are negative, he said honestly that you would need IBM's old documentation.
  • MAX232 (Maxim Integrated) on the Arduino Severino ("serial" in Italian), one of the first Arduino boards (mid-2000s).
  • FT232 (Future Technology Devices International) on the Duemilanove ("2009"): powered from USB, TX/RX LEDs, but not plug-and-play (needs a driver from ftdichip.com). That's why he told students to buy the Uno R3, not cheaper pre-R3 Unos.
  • Uno R3: the ATmega16U2 does USB↔UART; it has a 16 MHz crystal because USB needs accuracy, while the main chip uses a smaller, cheaper, less accurate ceramic resonator. "Uno" means one in Italian.

L6. Transmitter/receiver details [EXAM]

  • "Many people know how to use the transmitter but they don't know how it works. As university students you should know."
  • UDRE vs TXC: he made students reason it out. UDRE gives maximum throughput; TXC is for half-duplex (walkie-talkie "over") and power saving (a spy device behind enemy lines with a tiny battery: make sure the shift register has emptied before switching the USART off). The same applies to the two interrupts.
  • Pin control switches PD0/PD1 between GPIO and RXD/TXD. Shift registers are needed for parallel-in/serial-out (TX) and serial-in/parallel-out (RX).
  • Transmit and receive buffers share one address, hence one name, UDR. "If you write, the transmit buffer is referred; if you read, the receive buffer." There is no conflict, even when sending and receiving at the same time.
  • UDRE's default is 1 (empty at start); the other flags start at 0. The baud formula's derivation (why /16) is in the datasheet (p. 227); he did not cover it.
  • Reasons to enable/disable RX/TX: save power, and override GPIO only when needed.

L7. Baud error, UL and crystals [EXAM]

  • 103.17 → 103 (registers hold integers) → 9615.38 bps → 0.16% (≈ 0.2%). The generally accepted limit is 2.5%; at 10% it never works.
  • UL explained bit by bit: 16 × 9600 = 153 600 (20 bits); as a 16-bit int only 22 528 remains → UBRR = 709 instead of 103. "These are logical errors, not compile errors. Very difficult to find unless you know the subject well."
  • Critical systems (military, medical, automotive, avionics) need 0%: a guided missile link error could cause friendly fire; a drone with carbon-fibre propellers crashing into a crowd. Use a precision crystal such as 18.432 MHz → UBRR exactly 119.
  • Student: changing the crystal also changes the timers? Yes: redo the timer, PWM and ADC calculations. 18 432 000 / 1024 = 18 000 exactly, so prescalers can still give whole numbers.
  • Many developers "just want the functionality" and ignore worst cases. You must consider them.

L8. Code walk-through, terminals, interrupts

  • Setting the character size to 8 is not needed (it is the default) but makes the code more understandable.
  • He explained while(!(UCSR0A & 0b10000000)); bit by bit, twice, for students who asked.
  • Quiz: comment out the UDRE wait → the PC shows [a (the ']' is ignored). Comment out the RXC wait → "try it".
  • Terminal emulator = software imitating a 1960s dumb terminal (TTY, teletype); 24 × 80 characters; used for debugging, sensor calibration, module configuration, data logging. The Atmel Studio terminal can save to a file; the Arduino Serial Monitor works too (separately).
  • CR/LF come from typewriters: carriage return moves the roller back to the start of the line, line feed moves to the next line ("new line", \n).
  • Serial.begin(9600) internally sets UBRR = 103, 8-bit and RX/TX on: "everything wrapped into one user-friendly function". Arduino Serial also uses polling; System 17 shows the interrupt way.
  • Exercise 7 hint: use C#'s SerialPort component from the toolbox. He suggested combining it with the Interactive Application module into a project (database, Crystal Reports). He guides students but does not give answers.
