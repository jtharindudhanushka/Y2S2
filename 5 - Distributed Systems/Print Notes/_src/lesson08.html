2. Server virtualization scenarios (slides 5–6)

Figure 1 — Slides 5–6: the classification and the two architectures.

The three types of (hypervisor) virtualization

Background. A CPU has privilege levels. The OS kernel normally runs in the most privileged mode so it can use privileged/sensitive instructions (change memory mappings, talk to devices, disable interrupts). In a VM, the hypervisor must own the hardware, so the guest OS kernel cannot be allowed to run those instructions directly. Older x86 CPUs had some sensitive instructions that did not "trap" (alert the hypervisor) when run in a less privileged mode, which made x86 hard to virtualize. The three techniques solve this differently:

TypeHow it worksGuest OS changed?Slide notes and examples
Full virtualization (binary translation)The hypervisor scans the guest kernel's code as it runs and rewrites (translates) problem instructions into safe sequences; ordinary user code runs directly on the CPU.No — any unmodified OS runs"Better performance; simple setup and installation." VMware ESXi, Microsoft Hyper-V, Xen (with AMD-SVM or Intel VT), VirtualIron (hardware-assisted)
Para-virtualization (OS assisted)The guest kernel is modified to know it is virtualized; instead of privileged instructions it makes hypercalls (direct calls to the hypervisor).Yes — needs a modified kernel (e.g. Linux)"Best performance; ideal for multiple instances of host OS." Xen (with traditional hardware), Oracle VM Server
Hardware-assisted (Intel VT-x / AMD-V)The CPU adds a special mode for guests; sensitive instructions automatically trap to the hypervisor, so no translation or kernel changes are needed.No"Same as full virtualization, however the guest VM can communicate directly with the hardware, bypassing the hypervisor for certain machine instructions." Needs explicit CPU support.

Application virtualization (slide 10, the hosted branch) "leverages operating system hardware qualification; manages hardware through the generic OS": an application is packaged to run isolated on top of a normal OS without being installed into it. Examples: Microsoft App-V, Citrix Virtual Apps. Slide 10's figure compares full virtualization (unmodified guests on hardware), para-virtualization (modified guests) and application implementation (virtualization application on a host OS).

4. Hardware-assisted virtualization (slides 11–16)

Full virtualization on x86 has significant costs in hypervisor complexity and run-time performance. Hardware extensions address the parts of x86 that are difficult or inefficient to virtualize, giving simpler virtualization code and higher performance, because instructions are handled in hardware instead of in software. There are three generations:

AreaIntel / AMD namesWhat it does
CPU (1st gen, 2006)Intel VT-x (codename Vanderpool) / AMD AMD-V (also SVM, codename Pacifica)Adds a guest mode so sensitive instructions trap to the hypervisor. Requires hardware Data Execution Prevention (DEP): Intel calls it Execute Disable (XD), AMD calls it No Execute (NX); it stops code running from non-executable memory, blocking some buffer-overflow exploits. Must be enabled in the BIOS, and after enabling VT/AMD-V you must POWER CYCLE (switch fully off and on), not just reboot.
MMU (2nd gen)Intel EPT (Extended Page Tables) / AMD RVI (Rapid Virtualization Indexing), also called NPT (Nested Page Tables)Virtualizes the memory management unit in hardware, removing the need for shadow page tables and the overhead of keeping them updated. Gains: EPT up to 48% on MMU-intensive benchmarks (600% on microbenchmarks); RVI up to 42% (500%). Enable in BIOS.
I/O (newer)Intel VT-d (Virtualization Technology for Directed I/O) / AMD AMD-Vi (IOMMU)An I/O memory management unit remaps DMA transfers and device interrupts, so a VM can be given direct access to a hardware device such as a network card. VMware's VMDirectPath I/O uses it to let a VM use a physical NIC directly instead of an emulated or para-virtualized device: little throughput change, but lower CPU cost for network-heavy workloads.
Shadow page tables vs EPT/RVI (why the MMU feature matters) A guest OS keeps page tables mapping its virtual addresses to what it thinks are physical addresses ("guest physical"). Those are not real; the hypervisor must map guest physical → host physical. Without hardware help, the hypervisor builds shadow page tables (direct guest-virtual → host-physical maps) and must update them every time the guest changes its own tables: slow. With EPT/RVI the CPU walks both levels of tables itself (nested paging), so the hypervisor no longer maintains shadows.

Hyper-V high-level architecture (slide 13): the hypervisor runs on the hardware; a root partition (management OS, holds device drivers) controls it; enlightened Windows and Linux child partitions are para-virtualization aware and talk efficiently to the root; an unenlightened child partition runs an unmodified OS with emulated devices.

6. vMotion and Storage vMotion (slides 21–25)

vMotion moves an entire running VM from one host to another without downtime — a "hot" or "live" migration. The VM's whole state is encapsulated, and the shared VMFS file system lets both source and target hosts access the VM's files at the same time, so only the memory and execution state travel, over a high-speed network. The VM keeps its network identity and connections.

Figure 3 — vMotion moves the running state between hosts; the disks stay on shared storage.

vMotion operations, step by step (slide 23)

#StepWhy
1Migration request: move the VM from ESX1 to ESX2Admin or DRS starts it
2vCenter verifies the VM is in a stable state on ESX1 and that ESX2 is compatible (CPU, networking, etc.)The VM must be able to run identically on ESX2
3The VM is registered on ESX2ESX2 prepares an empty VM shell
4VM state (memory, registers, network connections) is copied to ESX2; changes made meanwhile are recorded in a memory bitmap on ESX1The VM keeps running during the copy, so pages it changes ("dirty pages") are tracked
5The VM is quiesced (paused very briefly) on ESX1 and the memory bitmap is copied to ESX2Freeze so the last changes can be sent
6The VM is started on ESX2; all requests now go to ESX2Switch-over (users see no outage)
7A final copy of the VM's memory is done from ESX1 to ESX2Any remaining pages are fetched
8The VM is unregistered from ESX1Clean up the source
9The VM resumes operation on ESX2Migration complete

Storage vMotion (introduced in ESX 3.5) migrates a running VM's disk files from one datastore (a storage location) to another on the same ESX host (local or shared). Difference: vMotion moves the VM to another host but keeps its storage location; Storage vMotion keeps the host but changes the storage location.

#Storage vMotion step (slide 25)
1A new VM directory is created on the target datastore; configuration files and non-disk files are copied there
2The ESX host does a "self" vMotion to the target directory
3A snapshot (without memory) is taken of the VM's disks in the source directory (new writes go to the snapshot, freezing the base disk)
4The VM disk files are copied to the target directory
5The snapshot in the source directory is consolidated (merged) into the disk files in the target directory
6Source disk files and directory are deleted

8. Virtual networking (slides 27–29, 39–43)

8.1 ESX network components

Figure 4 — Slides 39–41: VMs connect through vNICs to virtual ports on vSwitches; physical NICs (vmnics) are the uplinks.
  • ESX network architecture (slide 39): an ESX host runs VMs (App + OS) alongside a console OS, on physical CPU, memory and network adapters, with three networks: management network, VMkernel network (used by the hypervisor itself, e.g. vMotion, storage traffic) and production network (VM traffic).
  • Slide 41 layout: vSwitch0 has the virtual machine port group (Network0) with 10 VMs, uplink vmnic0 to the Internet/trusted LAN VLAN; vSwitch1 has the service console port, uplink vmnic1 to the vMotion LAN; vSwitch2 has a VMkernel port, uplink vmnic2. Separating traffic types on separate vSwitches and NICs keeps them from interfering.

8.2 vSwitch vs a physical switch (slides 42–43)

A vSwitch is a software implementation of an Ethernet switch inside ESX.

Like a physical switchDifferent from a physical switch
Forwards frames by MAC address; supports VLAN segmentationNo need to learn MAC addresses: it already knows the MAC of every connected vNIC. No participation in spanning tree (STP: the protocol physical switches use to avoid loops). No trunk between vSwitches, so no loop is possible inside ESX unless a VM bridges two vSwitches.

Forwarding characteristics: forwarding is by MAC address with no learning; traffic that does not match a local VM's MAC is sent out to the vmnic (uplink); VM-to-VM traffic on the same vSwitch stays local (never touches the physical network); vSwitches tag traffic with 802.1Q VLAN IDs (802.1Q = the standard for adding a VLAN tag to Ethernet frames); vSwitches can create EtherChannels (several physical links bundled into one logical, faster, redundant link).

8.3 Cisco Nexus 1000V and successors (slides 27–29)

  • Nexus 1000V: the industry's first third-party virtual distributed switch (one switch spanning many ESX hosts, managed like a Cisco switch), giving enhanced VM switching for VMware ESX. Features VN-Link: policy-based VM connectivity; mobility of network and security properties (the VM's port settings move with it); non-disruptive operational model; visibility and continued connectivity during vMotion.
  • VN-Link problems it solves: vMotion may move VMs across physical ports, so network policy must follow; it was impossible to view or apply policy to locally switched (VM-to-VM) traffic; traffic from many VMs on one physical link could not be told apart. VN-Link extends the network to the VM, giving consistent services and coordinated, coherent management.
  • Newer options (slide 28): Cisco ACI (Application Centric Infrastructure: an SDN solution with centralized, policy-driven automation and cloud integration); Cisco Nexus 9000 (traditional and programmable switches, supports ACI); VMware NSX (network virtualization platform that builds entire networks in software, with micro-segmentation: firewall rules per VM); Cisco Meraki (cloud-managed networking).

11. Exam-style questions with model answers

Q1. Give three reasons for virtualizing servers. (3 marks)
Effective resource usage (CPU, RAM, disk allocated where needed); ease of management (unused VMs kept off, easier provisioning, maintenance, HA and DR); security (applications isolated on separate VMs that do not risk each other, even for mutually untrusting users).

Q2. Compare full virtualization, para-virtualization and hardware-assisted virtualization. (9)
Full virtualization uses binary translation: the hypervisor rewrites sensitive guest kernel instructions on the fly, so unmodified OSes run (VMware ESXi, Hyper-V); simple setup but translation costs performance. Para-virtualization modifies the guest kernel to call the hypervisor through hypercalls instead of privileged instructions; best performance but needs a modified OS (Xen on traditional hardware, Oracle VM Server). Hardware-assisted virtualization uses CPU extensions (Intel VT-x, AMD-V) so sensitive instructions trap to the hypervisor in hardware and the guest can execute certain instructions directly; unmodified guests, simpler hypervisor code and higher performance, but needs CPU support enabled in the BIOS.

Q3. Explain the three generations of hardware-assisted virtualization. (6)
CPU: Intel VT-x / AMD-V (2006) add a guest mode; need DEP (Intel XD, AMD NX) enabled in BIOS and a power cycle. MMU: Intel EPT / AMD RVI (NPT) do two-level address translation in hardware, removing shadow page tables (up to 48%/42% gains on MMU-heavy benchmarks). I/O: Intel VT-d / AMD-Vi IOMMU remaps DMA and interrupts so VMs can access devices such as NICs directly (VMware VMDirectPath I/O), lowering CPU cost.

Q4. Distinguish Xen, KVM and LXC. (6)
Xen: Type 1 hypervisor running multiple OSes, supporting para-virtualization and hardware virtualization. KVM: Type 1 hypervisor built into the Linux kernel, turning Linux into a bare-metal hypervisor using hardware assistance. LXC: not a hypervisor but OS-level virtualization, running isolated Linux containers that share the host kernel.

Q5. Compare ESXi with vSphere and describe vCenter Server. (5)
ESXi is the free, production-class bare-metal hypervisor for partitioning a single server with advanced resource management. vSphere is the suite that pools many ESXi hosts into resources with centralized management, automation and availability; all editions include ESXi. vCenter Server is the central administration point that manages multiple ESXi hosts and directs actions on VMs and hosts, with a database for configuration and the vSphere Client/Web Access as interfaces.

Q6. What is vMotion? Describe its steps. (9)
vMotion is live migration of a running VM between hosts without downtime; shared VMFS storage lets both hosts access the VM's files, so memory and execution state are sent over a fast network and the VM keeps its network identity. Steps: request ESX1 → ESX2; vCenter checks the VM is stable and ESX2 is compatible; VM registered on ESX2; memory, registers and network state copied while changes are tracked in a memory bitmap on ESX1; VM quiesced on ESX1 and the bitmap copied; VM started on ESX2 and requests redirected; final memory copy; VM unregistered from ESX1; VM resumes on ESX2.

Q7. Distinguish vMotion and Storage vMotion. Outline Storage vMotion. (6)
vMotion moves a running VM to another host while its storage stays put; Storage vMotion keeps the VM on the same host but moves its disk files to another datastore. Storage vMotion: create the target directory and copy config files; self-vMotion to the target directory; snapshot the source disks; copy the disks; consolidate the snapshot into the target disks; delete the source files.

Q8. Explain DRS, VMware HA and Site Recovery Manager. (6)
DRS (Distributed Resource Scheduler) automatically balances workloads across hosts within set limits and guarantees, using vMotion, so resource assignment need not be predicted. VMware HA protects servers and applications against component and whole-host failure by restarting affected VMs on other hosts. SRM automates failover from the production site to a disaster-recovery site and allows non-disruptive DR testing.

Q9. How does a vSwitch differ from a physical switch? (6)
Like a physical switch, it forwards by MAC address and supports VLANs (802.1Q tagging) and EtherChannels. Unlike one, it does not need to learn MAC addresses (it knows each connected vNIC's MAC), does not take part in spanning tree, and has no trunks between vSwitches, so loops are impossible without a bridging VM. VM-to-VM traffic on the same vSwitch stays local; unknown destinations go out through the vmnic uplink.

Q10. What problems does Cisco Nexus 1000V/VN-Link solve? (4)
When vMotion moves VMs across physical ports, network and security policy must follow the VM; locally switched VM-to-VM traffic could not be seen or policed; traffic from many VMs on one link could not be distinguished. Nexus 1000V is a distributed virtual switch whose VN-Link extends the network to each VM, with policy-based connectivity that moves with the VM and visibility during vMotion.

Q11. In Lab 01, explain each part of the nmcli command that sets a static IP and how you verify it. (6)
nmcli connection modify ens160 edits the ens160 connection; ipv4.addresses 192.168.8.X/24 sets the host address with a 255.255.255.0 mask; ipv4.gateway 192.168.8.1 sets the default router; ipv4.dns "8.8.8.8 1.1.1.1" sets DNS servers; ipv4.method manual switches from DHCP to static. Restart with nmcli connection down/up ens160. Verify with ip addr (address), ip route (default via 192.168.8.1), ping 8.8.8.8 (Internet by IP) and ping www.google.com (DNS working).
