1. From commit to consensus

1.1 Recap: 2PC and 3PC (Lesson 4)

2PC: coordinator sends VOTE-REQUEST; all YES ⇒ COMMIT, any NO ⇒ ABORT. Weaknesses: (1) blocking if the coordinator crashes after YES votes; (2) the coordinator is a single point of failure; (3) participants hold locks while waiting, hurting throughput; (4) many messages and log writes (latency). 3PC adds PREPARE-TO-COMMIT so survivors can decide after a coordinator crash, but it assumes no network partitions and costs an extra round.

1.2 What is consensus?

Consensus = a group of processes must agree on one value (e.g. "who is the leader", "what is the next log entry") even though some may crash and messages may be delayed. A correct algorithm guarantees:

  • Agreement: all correct processes decide the same value.
  • Validity: the decided value was proposed by some process.
  • Termination: every correct process eventually decides.
Atomic commit (2PC)Consensus (Paxos/Raft)
Needs every participant to vote YES; one NO or one silent node forces ABORTNeeds only a majority (quorum); tolerates f crashed nodes out of 2f + 1
Blocks if the coordinator fails at the wrong timeKeeps making progress while a majority is up and can talk
Decides commit/abort for one transactionAgrees on any value, repeatedly (a replicated log)

Why consensus is harder: in an asynchronous system (no bound on message delay, Lesson 1) you cannot tell a crashed node from a slow one. The famous FLP result (Fischer, Lynch, Paterson, 1985) proves that no deterministic algorithm can guarantee consensus in a fully asynchronous system if even one process may crash. Practical algorithms (Paxos, Raft) therefore always keep safety (never two different decisions) and achieve liveness (actually deciding) using timeouts and leader election when the network behaves well enough. Commit is "easier" because it is allowed to give up (abort) or to block; consensus must make all correct nodes agree on a value without blocking on minority failures.

1.3 Paxos (in brief)

Figure 1 — Basic Paxos: two phases, each needs replies from a majority (here 2 of 3 is enough).
  1. Prepare: a proposer picks a unique, increasing proposal number n and sends PREPARE(n). An acceptor promises not to accept any proposal numbered below n and reports any value it already accepted.
  2. Accept: with promises from a majority, the proposer sends ACCEPT(n, v), where v is the value of the highest-numbered proposal already accepted (or its own value if none). Acceptors accept unless they promised a higher n. When a majority accepts, v is chosen.

Because any two majorities overlap in at least one acceptor, a later proposer always learns an already-chosen value and re-proposes it, so two different values can never be chosen. Paxos is correct but famously hard to understand and implement.

1.4 Raft

Raft (2014) solves the same problem but was designed to be understandable. It splits consensus into leader election, log replication and safety. Each node is a follower, candidate or leader. Time is divided into numbered terms; each term has at most one leader.

Figure 2 — Raft server states.
Step (worked example: 5 servers S1–S5, leader S1 in term 1)What happens
1. Normal operationS1 sends periodic heartbeats (empty AppendEntries) to all followers.
2. S1 crashesFollowers stop receiving heartbeats. Each has a random election timeout (e.g. 150–300 ms) so they rarely time out together.
3. S3 times out firstS3 becomes candidate, increments term to 2, votes for itself, sends RequestVote to S2, S4, S5.
4. VotingEach server votes for at most one candidate per term, and only if the candidate's log is at least as up to date as its own. S2 and S4 vote for S3.
5. MajorityS3 has 3 of 5 votes (itself + S2 + S4) ≥ majority (3) ⇒ leader for term 2; it starts sending heartbeats. S5 sees term 2 and stays follower.
6. Log replicationA client sends a command to S3; S3 appends it to its log, sends AppendEntries; once a majority stores it, the entry is committed and applied to every state machine in the same order.
7. S1 recoversS1 still thinks it is leader of term 1, sees term 2 > 1, steps down to follower and its log is brought in line with S3's.

With 5 servers Raft tolerates 2 failures (needs 3 alive). If two candidates split the votes, nobody wins, the term times out, and a new election with fresh random timeouts follows. Used in: etcd (the Kubernetes cluster database, Lesson 6), Consul; ZooKeeper uses the similar Zab protocol; Paxos variants are used in Google Chubby/Spanner. Distributed metadata (Ceph, HDFS Federation) needs such consensus (Lecture 07 slide 27).

How consensus supports coordination in multi-agent systems: agents use it to agree on a leader/coordinator, on the order of actions on a shared resource (a replicated log of "who holds the lock"), or on a shared plan, so that all agents act on the same decision even when some agents fail.

2. Multi-agent systems (MAS)

An agent is an autonomous software (or robotic) entity that perceives its environment through sensors and acts on it to achieve goals. A multi-agent system is a set of interacting agents, often on different machines — a distributed system where the components make their own decisions.

CharacteristicMeaning
AutonomyActs without direct human or central control; has its own state and goals
ReactivityPerceives and responds in time to changes in the environment
Pro-activenessTakes initiative to pursue goals, not only reacting
Social abilityCommunicates, cooperates and negotiates with other agents
In a MASEach agent has only a local, partial view; there is no global control; data is decentralized; computation is asynchronous — the same challenges as any distributed system (Lesson 1)

Agent types (Lecture 01 outline): reactive (simple condition–action rules, fast, no internal model, e.g. a thermostat or obstacle-avoiding robot); deliberative (keeps a symbolic model of the world and plans, e.g. the BDI model: Beliefs, Desires, Intentions); hybrid (a fast reactive layer for emergencies plus a deliberative layer for planning, e.g. an autonomous car).

2.1 Communication

Agents exchange messages in an Agent Communication Language (ACL). The FIPA standard (Foundation for Intelligent Physical Agents) defines FIPA-ACL: each message has a performative (the type of speech act: inform, request, propose, accept-proposal, reject-proposal, cfp = call for proposals), plus sender, receiver, content, a content language and an ontology (shared vocabulary). FIPA also defines platform services: an Agent Management System and a Directory Facilitator ("yellow pages"). JADE is a common FIPA-compliant platform.

2.2 Coordination and negotiation

  • Contract Net Protocol: a manager broadcasts a call for proposals for a task; contractors reply with bids; the manager awards the task to the best bid; the winner reports results. (Like a tender.)
  • Auctions (English, Dutch, sealed-bid) to allocate scarce resources.
  • Negotiation and argumentation: exchange offers/counter-offers until agreement.
  • Organisational structures: hierarchies, teams, roles; blackboard systems where agents share a common workspace.
  • Consensus / voting (section 1) for agreeing on a leader or shared decision.

2.3 Resolving conflicts over shared resources

TechniqueExample
Mutual exclusion / locking (central lock manager, token passing, or a consensus-backed lock)Only the agent holding the token may use the charging station
Priorities and timestamps (older/higher-priority request wins)Ambulance agent overrides normal traffic agents

Applications: autonomous vehicles, IoT and smart grids, robot warehouses, supply chains, traffic control.

3. Distributed search engines

3.1 Pipeline

Figure 3 — Search engine pipeline; crawling and index building are big batch jobs (MapReduce, section 5).

Crawling: many crawler machines download pages, follow links, and revisit pages to keep the index fresh. Challenges (Lecture 01 outline): freshness (pages change constantly) and coverage (the web is huge; you cannot crawl it all).

3.2 Inverted index (worked example)

An inverted index maps each term (word) to a posting list: the documents containing it (plus positions/frequencies). It is "inverted" because instead of document → words, it stores word → documents, so a query only reads the lists of its words.

DocumentsInverted index
D1: "cloud storage systems"
D2: "distributed storage"
D3: "cloud computing"		cloud → D1, D3
storage → D1, D2
systems → D1
distributed → D2
computing → D3
Query "cloud AND storage": intersect {D1, D3} ∩ {D1, D2} = {D1}. Query "cloud OR storage" = {D1, D2, D3}.

3.3 Sharding and query processing

The index is far too big for one machine, so it is split into shards (partitions), each replicated for fault tolerance and throughput.

Document-partitioned (local index)Term-partitioned (global index)
SplitEach shard holds a full index for a subset of documentsEach shard holds the complete posting lists for a subset of terms
QuerySent to all shards in parallel; each returns its top results; mergedSent only to the shards holding the query's terms; lists are combined
Pros/consSimple, balanced, easy to add documents; every query touches every shardFewer shards per query; hot terms create hot spots; big lists move across the network
Figure 4 — Scatter-gather query over a document-partitioned index.

3.4 Ranking: PageRank (worked example)

PageRank scores a page by how many important pages link to it. With damping factor d = 0.85 and N pages: PR(p) = (1 − d)/N + d × Σ PR(q)/out(q) over pages q linking to p (out(q) = number of links leaving q).

Links: A → B, A → C, B → C, C → A. N = 3, start all at 1/3, (1 − d)/N = 0.05.

PageIteration 1Converged (after many iterations)
A0.05 + 0.85 × (C/1) = 0.05 + 0.85 × 0.333 = 0.333≈ 0.388
B0.05 + 0.85 × (A/2) = 0.05 + 0.85 × 0.167 = 0.192≈ 0.215
C0.05 + 0.85 × (A/2 + B/1) = 0.05 + 0.85 × 0.5 = 0.475≈ 0.397

C ranks highest (two incoming links); scores sum to 1. On the web this is computed over billions of pages as repeated MapReduce jobs.

4. Peer-to-peer systems

4.1 Unstructured P2P (Gnutella-style flooding)

Peers connect to random neighbours; there is no rule about where data is stored. To search, a peer sends the query to all neighbours, who forward it to theirs, up to a TTL (time-to-live, a hop limit).

Worked example: each peer has 3 new neighbours and TTL = 3: messages = 3 + 9 + 27 = 39 for one search, reaching at most 39 peers. TTL = 5 gives 3 + 9 + 27 + 81 + 243 = 363. Traffic grows exponentially, yet a rare file beyond the TTL is not found even if it exists.

4.2 Structured P2P: Distributed Hash Tables (DHT)

A DHT gives every node and every key an ID from the same space (by hashing, e.g. SHA-1) and has a rule for which node stores which key, so a lookup can be routed to exactly the right node in about O(log N) hops.

Chord: IDs on a ring of size 2m. Key k is stored at its successor: the first node whose ID ≥ k (clockwise). Each node keeps a finger table of m entries: finger i = successor(n + 2i−1). Lookups jump about half the remaining distance each hop.

Figure 5 — Chord worked example: nodes 1, 4, 9, 11, 14 on a 16-ID ring.

Kademlia: the distance between two IDs is their bitwise XOR; each node keeps "k-buckets" of contacts at distances 2i, and queries several of the closest nodes in parallel. XOR is symmetric, so normal traffic keeps routing tables fresh; it handles churn well. Used by BitTorrent's DHT and IPFS.

BitTorrent (content distribution): a file is split into pieces; a tracker or the DHT finds peers in the "swarm"; peers download different pieces from many peers at once and upload pieces they have ("tit-for-tat" rewards uploaders); rarest pieces are fetched first. The more popular the file, the faster it spreads.

4.3 Structured vs unstructured

Trade-offUnstructured (Gnutella flooding)Structured (Chord, Kademlia DHT)
Lookup efficiencyPoor: flooding costs many messages; not guaranteed (TTL); good for keyword/partial searches and popular itemsEfficient and guaranteed: O(log N) hops for an exact key; no keyword search by itself
Churn tolerance (peers joining/leaving)High: no structure to repair; a leaving peer just disappearsLower: finger tables and key ownership must be repaired on joins/leaves (stabilisation); Kademlia copes better than Chord
Implementation complexitySimpleMore complex (hashing, routing tables, stabilisation, replication of keys)
Load / placementData anywhereData placed by hash: balanced, but no control over where data lives

Other outline topics (Lecture 01 slide 11): reputation and trust management (rating peers to avoid free-riders and malicious peers), legal and ethical issues (copyright), and blockchain: a distributed ledger replicated across peers, agreed by consensus — Proof of Work (miners solve a costly puzzle), Proof of Stake (validators chosen by the stake they lock), PBFT (Practical Byzantine Fault Tolerance: votes among known nodes, tolerates f Byzantine of 3f + 1; used in permissioned chains such as Hyperledger); smart contracts (Ethereum) run code on the ledger.

5. MapReduce and cloud programming models

5.1 MapReduce

A programming model (Google, 2004) for processing huge datasets on clusters of commodity machines. The programmer writes only two functions; the framework handles distribution, scheduling and failures.

  • map(key, value) → list of (k2, v2): run in parallel on each input split (e.g. each 64/128 MB block of a GFS/HDFS file, processed on the machine that stores it: data locality).
  • Shuffle & sort: the framework groups all values with the same k2 and sends them to one reducer.
  • reduce(k2, list of v2) → output: combines each group.
  • Fault tolerance: a master pings workers; tasks of a failed worker are re-executed elsewhere; slow "stragglers" get backup copies.
Figure 6 — MapReduce log analysis: count log lines per level (map emits (level, 1) per line).
# Part C-style word count (Python, simulated workers)
from collections import defaultdict
from multiprocessing import Pool

def map_fn(text):                       # one split -> list of (word, 1)
    return [(w.lower(), 1) for w in text.split()]

def reduce_fn(item):                    # (word, [1,1,..]) -> (word, count)
    word, ones = item
    return word, sum(ones)

if __name__ == "__main__":
    splits = ["cloud data cloud", "data node"]
    with Pool(2) as p:
        mapped = p.map(map_fn, splits)  # map phase in parallel processes
    groups = defaultdict(list)          # shuffle: group by key
    for pairs in mapped:
        for w, one in pairs:
            groups[w].append(one)
    with Pool(2) as p:
        print(dict(p.map(reduce_fn, groups.items())))   # {'cloud': 2, 'data': 2, 'node': 1}

How it would scale for real: input in HDFS/S3 split into blocks; thousands of map tasks run where the blocks are; shuffle over the network; results written back to the DFS. Limits of a local simulation: one machine's CPU, RAM and disk; no real network shuffle cost; no machine failures, stragglers or data locality to handle.

6. Related outline topics: ACID vs BASE, concurrency control

ACID (classic transactions)BASE (many NoSQL / AP systems)
Atomicity (all or nothing), Consistency (rules kept), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes)Basically Available, Soft state (state may change without input as replicas converge), Eventually consistent
Fits CP choices: banking (Lesson 1)Fits AP choices: social feeds, shopping carts

Pessimistic concurrency: lock data before using it (two-phase locking); safe under heavy contention but can block and cause distributed deadlock (T1 waits for a lock held by T2 on another server, and T2 waits for T1: detected by building a global wait-for graph and finding a cycle, or avoided with timeouts). Optimistic concurrency: work without locks, then validate at commit time and abort/retry if someone else changed the data; best when conflicts are rare.

7. Exam-style questions with model answers

Q1. Explain why consensus is harder than transaction commitment. (5 marks)
Atomic commit only needs a unanimous yes/no on one transaction and may abort or block when something fails; any NO or silent node aborts it. Consensus must make all correct processes agree on a value while tolerating crashed processes, needing only a majority, and must keep making progress. In an asynchronous system a crashed process cannot be distinguished from a slow one, and the FLP result shows no deterministic algorithm can guarantee consensus there with even one crash; practical protocols (Paxos, Raft) guarantee safety always and liveness using timeouts and leader election.

Q2. Describe Raft leader election with an example. (6)
Servers are followers, candidates or leaders; time is divided into terms. The leader sends heartbeats. If a follower's randomised election timeout expires without a heartbeat, it becomes a candidate, increments the term, votes for itself and requests votes; each server grants one vote per term to a candidate whose log is at least as up to date. A candidate with a majority (e.g. 3 of 5) becomes leader and sends heartbeats; a server that sees a higher term steps down. Split votes cause a new election after another random timeout.

Q3. What are the key characteristics of a multi-agent system? How do agents coordinate and resolve conflicts over shared resources? (8)
Agents are autonomous, reactive, proactive and social; in a MAS each has a partial local view, there is no global control, and data and computation are decentralized and asynchronous. They communicate with an agent communication language such as FIPA-ACL (performatives like inform, request, propose). They coordinate through protocols like the Contract Net (call for proposals, bids, award), auctions, negotiation, organisational roles or consensus. Conflicts over shared resources are resolved with mutual exclusion/locking or token passing, priorities and timestamps, negotiation or auctions, optimistic or pessimistic concurrency control, and social conventions.

Q4. Explain how a distributed search engine indexes and retrieves data using inverted indexes and sharding. (8)
Crawlers fetch pages; pages are tokenised and an inverted index maps each term to a posting list of documents. The index is split into shards (by document or by term) spread over many nodes and replicated. A query goes to a front-end that scatters it to the relevant shards in parallel (all shards for a document-partitioned index); each shard looks up the posting lists, intersects/scores them and returns its top results; the front-end merges and ranks them (e.g. with PageRank and relevance) and returns the answer. Replicas give fault tolerance and throughput.

Q5. Compare centralized and distributed/P2P search architectures. (6)
Centralized: simple and fast at small scale but limited by one machine and a single point of failure. Distributed cluster: scales by adding shards and replicas, tolerates node failures, and keeps latency low with parallel scatter-gather. P2P: no central server and scales with peers, but lookups take many hops or floods, latency is higher and variable, results may be incomplete, and churn and lack of control make freshness and quality hard.

Q6. Compare structured and unstructured P2P systems. (8)
Unstructured (Gnutella): peers link randomly and search by flooding with a TTL; simple and very tolerant of churn, supports keyword search, but lookups are expensive (messages grow exponentially) and not guaranteed to find rare items. Structured (Chord, Kademlia): a DHT hashes nodes and keys into one ID space and assigns each key to a specific node; lookups route in O(log N) hops and always find an existing key, but the routing structures must be maintained when peers join and leave, which is more complex and less tolerant of heavy churn; only exact-key lookup is supported directly.

Q7. In a Chord ring with m = 4 and nodes 1, 4, 9, 11, 14, which node stores key 12, and what is node 1's finger table? (5)
Key 12 is stored at its successor, node 14. Node 1's fingers are successor(2) = 4, successor(3) = 4, successor(5) = 9, successor(9) = 9. Lookup path 1 → 9 → 11 → 14.

Q8. Explain MapReduce with a word-count example. How does it tolerate failures? (6)
Input is split into blocks; map tasks run in parallel and emit (word, 1) for each word; the framework shuffles and groups pairs by word; reduce tasks sum each list (cloud = 2, data = 2, node = 1). The master monitors workers and re-executes tasks of failed workers on other machines, and starts backup copies of slow tasks; map tasks run near their data to reduce network use.

Q9. Compare MapReduce, serverless/FaaS and the actor model. (6)
MapReduce: batch processing of huge static datasets through map, shuffle and reduce; high throughput, high latency. Serverless: stateless functions triggered by events, auto-scaling to zero, pay per invocation; good for bursty short tasks; cold starts and no long-running state. Actor model: actors with private state exchanging asynchronous messages; good for highly concurrent, stateful, interactive systems.

Q10. Distinguish ACID and BASE. (4)
ACID: atomicity, consistency, isolation, durability; strong guarantees, suits banking (CP). BASE: basically available, soft state, eventually consistent; favours availability and scale, suits feeds and carts (AP).

Common mistakes

MistakeCorrect idea
Consensus needs every node to agree before decidingPaxos/Raft need only a majority; 2PC needs everyone.
Raft can have two leaders in the same termAt most one leader per term (one vote per server per term, majority needed).
Chord stores key k at the node before kAt its successor: the first node with ID ≥ k.
Flooding always finds the fileOnly within the TTL; rare items may be missed.
DHTs support keyword search nativelyThey support exact-key lookup; keyword search needs extra indexing.
An inverted index maps documents to wordsIt maps words (terms) to documents (posting lists).
MapReduce is good for low-latency queriesIt is a high-throughput batch model.
Reactive agents plan aheadReactive = condition–action rules; deliberative agents plan (BDI); hybrid combines them.
