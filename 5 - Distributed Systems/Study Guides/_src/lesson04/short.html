Commit & security
2PCVOTE-REQUEST → YES/NO → COMMIT (all yes) / ABORT (any no). Blocks if coordinator dies after YES votes
3PCVote → PREPARE-TO-COMMIT + ACK → COMMIT. Non-blocking (crash-only, no partitions); more messages
DFS securityAuthenticate (Kerberos, mTLS) → authorize (ACL, capability, RBAC) → encrypt (TLS, at rest) + checksums; same policy on all replicas; auditing

Common mistakes

MistakeCorrect idea
Sequential consistency must follow real timeOnly strict consistency needs real time; sequential needs one agreed interleaving.
Causal consistency orders all writesOnly causally related writes; concurrent writes may be seen in different orders.
Eventual consistency = data may be lostAll replicas converge to the last value once updates stop; reads may only be temporarily stale.
Mixing up monotonic reads and read-your-writesMonotonic reads: read → read never goes back. Read-your-writes: write → read sees your own write.
Push is better for rarely-read replicasPush wastes bandwidth there; pull fits a low read-to-write ratio.
CAP availability = 99.99% uptimeCAP availability = every request gets a non-error response.
Fault and failure used as synonymsFault (cause) → error (bad state) → failure (visible).
Heartbeat is decentralizedHeartbeat uses a monitor (centralized); gossip is decentralized.
2PC blocks when a participant votes NOA NO just causes ABORT. Blocking happens when the coordinator crashes after YES votes, before the decision.
3PC works under any failureOnly crash-only failures without network partitions.
Retrying any request is safeOnly idempotent ones; otherwise at-least-once can execute twice.
