Answer technique for a 2-hour closed-book paper Define → explain → example → diagram. Start every answer with the definition; give one point per mark; add a concrete example (bank, Google, AWS, online shop); draw a labelled diagram whenever the topic has one (architecture, 2PC, CAP triangle, hypervisor stack, GFS, HA design). For "compare" questions always use a table with 4–6 rows. For "discuss trade-offs" give both sides and say when each is preferred. Budget about 1.2 minutes per mark.

Part A — Definitions to memorise

Lesson 1 — Distributed systems
Distributed systemA collection of independent computers that appears to its users as a single coherent system, communicating over a network to achieve a common goal.
TransparencyHiding the distribution from users (access, location, migration, replication, concurrency, failure).
ScalabilityAbility to grow capacity, preferably by adding nodes (horizontal scaling), while performing well.
Partial failureSome components fail while others keep running.
CAP theoremA distributed data store can guarantee at most two of Consistency, Availability and Partition tolerance; under a partition choose C or A.
MiddlewareSoftware layer that hides heterogeneity and gives a uniform interface.
Openness / heterogeneityBuilt on standard published interfaces / nodes differ in hardware, OS, network, language.
Lesson 2 — Cloud computing
Cloud computingDelivery of computing as a service rather than a product, where shared resources, software and information are provided as a metered service over a network: on-demand IT, pay-as-you-go.
NIST characteristicsOn-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.
Big dataLarge pools of data that can be captured, communicated, aggregated, stored and analysed to deliver insights and value (5 V's).
Multi-tenancyMultiple customers share the same physical infrastructure securely and independently.
IaaS / PaaS / SaaSVirtual infrastructure (you manage OS and up) / platform to build and deploy apps (you manage app and data) / complete software over the Internet (you just use it).
Public / private / hybrid / multi-cloudThird-party shared / one organisation only / public + private with portability / several public providers.
Serverless (FaaS)Developers don't manage servers; functions run on events, scale to zero, pay per invocation.
Edge / fog computingProcessing close to where data is generated (<10 ms) / a middle layer between edge and cloud that aggregates edge data (10–50 ms).
Shared responsibilityProvider secures OF the cloud (physical, network hardware, hypervisor); customer secures IN the cloud (data, IAM, network config, apps).
Zero Trust"Never trust, always verify": verify explicitly, least privilege, assume breach.
FinOpsBringing financial accountability to cloud spending.
Lesson 3 — NFV, SDN, Docker, HA
NFVDecoupling network functions (firewall, encryption) from dedicated hardware and running them on virtual servers.
SDNSeparating the network control plane from the data plane and centralising control in software.
Container / imageRunning instance / read-only template built from a Dockerfile in layers.
Availability zoneCluster of data centres in a region with independent power, cooling and redundant networking.
RTO / RPOMaximum acceptable downtime / maximum acceptable data loss measured in time.
Lesson 4 — Consistency, fault tolerance
Consistency modelA contract between the data store and processes specifying what values a read may return after writes.
Strict / sequential / causal / eventualLatest write in real time / one interleaving for all / same order only for causally related writes / converge when updates stop.
Fault → error → failureDefect in a component → incorrect internal state → visible service breakdown.
Fault toleranceContinuing to operate correctly despite failures of some components.
Byzantine failureArbitrary output at arbitrary times, including malicious behaviour.
Atomic multicastA message is delivered to every non-faulty group member or to none.
2PCCoordinator collects YES/NO votes; all YES ⇒ COMMIT, any NO ⇒ ABORT; blocking if the coordinator fails after YES votes.
PACELCIf Partition: A or C; Else: Latency or Consistency.
Lesson 5 — Infrastructure and virtualization
VirtualizationCreating a software-based version of a resource so one physical machine behaves like several.
Hypervisor (VMM)Software that creates, runs and manages VMs, allocating hardware and isolating them.
Type 1 / Type 2Runs directly on hardware (ESXi, Hyper-V, Xen, KVM) / runs as an app on a host OS (VirtualBox, Workstation).
Cloud infrastructureHardware and software (servers, storage, networking, virtualization) needed to support cloud computing.
Resource poolingPhysical compute, storage and network combined into a shared pool from which slices are allocated on demand.
Lesson 6 — Management, Kubernetes
Cloud managementControlling and monitoring cloud resources, storage, networks, apps, security policies and access.
Infrastructure as CodeManaging infrastructure through code instead of manual configuration.
Load balancerDistributes incoming traffic among multiple servers or instances.
Auto-scalingAutomatically increasing or decreasing resources according to demand.
KubernetesOpen-source container orchestration platform for deploying, managing and scaling containerized apps.
PodSmallest deployable unit: one or more containers sharing one IP and optional volumes, co-scheduled, ephemeral.
ResilienceAbility of a system to continue operating when failures occur.
Lesson 7 — Storage
Block / file / object storageFixed-size addressable blocks / hierarchical files over NFS/SMB / immutable objects (data + metadata + key) over REST.
GFS / HDFSGoogle's master/chunkserver DFS with 64 MB chunks / open-source NameNode/DataNode DFS with 128 MB blocks.
DurabilityData is not lost (S3: 11 nines); different from availability.
Erasure codingStoring data plus parity so lost blocks can be rebuilt; ~1.5× overhead instead of 3×.
Lesson 8 — Server virtualization
Full / para / hardware-assistedBinary translation, unmodified guest / modified guest with hypercalls / CPU extensions (VT-x, AMD-V).
vMotion / Storage vMotionLive migration of a running VM to another host / of its disk files to another datastore on the same host.
vSwitchSoftware Ethernet switch inside ESX connecting VM vNICs to physical uplinks (vmnics).
DRS / HA / SRMAuto load balancing across hosts / restart VMs after host failure / failover to a DR site.

Part D — Exam-style questions with model answers

A mock paper mixing all lessons. Attempt each under timed conditions before reading the answer.

Q1. Define a distributed system. Explain four of its characteristics and two of its challenges. (10 marks)
A distributed system is a collection of independent computers that appears to its users as a single coherent system, communicating over a network to achieve a common goal; nodes do not share memory, cooperate only by messages and have no global clock. Characteristics: resource sharing (hardware, data and services shared, e.g. one file server); scalability (grow by adding nodes horizontally); concurrency (many requests processed simultaneously, so shared data must be protected); transparency (distribution hidden, e.g. location and failure transparency). Challenges: partial failures (some nodes fail while others run, and a node cannot tell crashed from slow); consistency (keeping replicated data in sync under concurrent updates).

Q2. A bank and a social network both replicate data across data centres. Using the CAP theorem, explain which property each should give up during a network partition and why. (8)
CAP: a distributed data store can provide at most two of consistency (every read returns the latest write or an error), availability (every request gets a non-error response) and partition tolerance (keeps operating despite lost/delayed messages). Partitions are unavoidable, so the choice is C or A. The bank should be CP: during a partition a replica that cannot coordinate refuses or delays withdrawals and balance reads, because showing a stale balance could allow overdrawing, a real financial loss. The social network should be AP: replicas keep serving posts that may be slightly stale and converge later (eventual consistency), because an old feed is acceptable but downtime loses users.

Q3. Compare IaaS, PaaS and SaaS using a diagram of the responsibility stack. Give an example and suitable use of each. (10)
(Draw the stack: applications, data, runtime, middleware, OS, virtualization, servers, storage, networking.) IaaS: provider manages virtualization and below; customer manages the OS, middleware, runtime, data and applications; e.g. AWS EC2; for lift-and-shift migrations, dev/test, HPC. PaaS: the provider also manages OS, middleware and runtime; the customer manages only the app and data; e.g. Google App Engine, Heroku; for developers who want to deploy code with auto-scaling, CI/CD and managed databases. SaaS: provider manages everything; customer just uses the software; e.g. Gmail, Microsoft 365; for end users needing ready applications.

Q4. Explain the difference between sequential consistency and eventual consistency. For P1: W(x)a; P2: W(x)b; P3: R(x)a, R(x)b; P4: R(x)a, R(x)b, state whether the history is sequentially consistent. (8)
Sequential consistency: the result is as if all operations were executed in one sequential order seen identically by all processes, respecting each process's program order but not real time. Eventual consistency: if updates stop, all replicas eventually converge to the same value, with no ordering or timing guarantee meanwhile; it favours availability (DNS, NoSQL). The history is sequentially consistent: P3 and P4 both observe a then b, so the single order W(x)a, W(x)b explains every read.

Q5. Describe the Two-Phase Commit protocol with a diagram. Explain the situation in which it blocks and how Three-Phase Commit avoids it. (12)
(Draw coordinator and participants with VOTE-REQUEST, YES/NO, COMMIT/ABORT.) Phase 1: the coordinator asks every participant whether it can commit; each prepares, logs and votes YES or NO. Phase 2: if all voted YES the coordinator broadcasts COMMIT, otherwise ABORT; participants apply it, giving all-or-nothing atomicity. Blocking: if the coordinator crashes after participants voted YES but before they receive the decision, they cannot commit or abort alone and must wait holding locks. 3PC inserts a PREPARE-TO-COMMIT phase acknowledged by participants before the final COMMIT, so every participant knows the group's intent; after a coordinator crash survivors use timeouts or a new coordinator: if any received PREPARE-TO-COMMIT they commit, otherwise they abort. It avoids blocking under crash-only failures without partitions, at the cost of more messages and complexity.

Q6. Compare Type 1 and Type 2 hypervisors, and virtual machines with containers. Recommend a technology for (a) running Windows and Linux on one server, (b) a microservice web shop with sudden traffic spikes. (12)
Type 1 runs directly on hardware (ESXi, Hyper-V, Xen, KVM): near-native performance, smaller attack surface, used in data centres. Type 2 runs as an application on a host OS (VirtualBox, VMware Workstation): easy to install, more overhead, inherits host OS risks, used on laptops. VMs include a full guest OS: strong isolation, GBs, minutes to boot, lower density. Containers share the host kernel: weaker isolation, MBs, seconds to start, higher density. (a) VMs on a Type 1 hypervisor, since different guest operating systems are needed. (b) Containers orchestrated by Kubernetes (possibly inside VMs for tenant isolation), since microservices need fast startup, density and rapid horizontal scaling.

Q7. Draw a highly available three-tier web architecture on AWS and explain how it survives the loss of an availability zone. Define RTO and RPO and recommend a DR strategy for an online shop that may be down for at most 30 minutes. (12)
(Draw VPC across two AZs: public subnets with NAT gateways, private subnets with web and app servers in Auto Scaling groups, an ALB in front, RDS primary in AZ1 replicating to a secondary in AZ2.) If AZ1 fails, the ALB's health checks send traffic only to AZ2, the Auto Scaling group launches replacement instances there, and RDS fails over to the secondary, so no single point of failure stops the service. RTO is the maximum acceptable downtime; RPO is the maximum acceptable data loss measured in time. With an RTO of about 30 minutes, pilot light suits: the database is continuously replicated to the DR region (small RPO) and application servers are started and DNS (Route 53) switched over in tens of minutes, more cheaply than warm standby or multi-site.

Q8. Explain the Kubernetes architecture and the role of a Pod. What happens when (a) a container in a Pod crashes, (b) the node running a Deployment's Pod fails? (10)
A cluster has a control plane (API server as the entry point, scheduler choosing nodes, controller manager keeping actual state equal to desired state, cluster database storing state) and worker nodes (kubelet running and reporting Pods, container runtime, kube-proxy for Service networking). A Pod is the smallest deployable unit: one or more containers that share one IP (localhost), optional volumes, are co-scheduled on one node and are ephemeral. (a) The kubelet restarts the container in place according to the restart policy (Always by default), with growing backoff (CrashLoopBackOff). (b) The Pod is lost; the Deployment controller sees fewer replicas than desired and the scheduler places a new Pod on a healthy node.

Q9. Explain the GFS architecture with a diagram. Why does data not flow through the Master? Compare GFS with HDFS. (12)
(Draw client, Master, chunkservers with replicated chunks.) A single Master keeps metadata (namespace, file-to-chunk mapping, chunk locations); chunkservers store 64 MB chunks, each replicated 3× across machines/racks. A client asks the Master for the chunk handle and locations, then reads/writes directly with chunkservers. Separating the metadata path from the data path stops the single Master becoming a throughput bottleneck. HDFS: open source (Hadoop); NameNode/DataNodes; 128 MB blocks; Active/Standby NameNodes for HA; explicit rack awareness; erasure coding in 3.x; general Hadoop workloads. GFS: internal Google, single Master, 64 MB, basic placement, Google batch workloads.

Q10. Compare full virtualization, para-virtualization and hardware-assisted virtualization. Explain vMotion. (10)
Full virtualization: the hypervisor uses binary translation to rewrite sensitive instructions, so unmodified guests run (ESXi, Hyper-V). Para-virtualization: the guest kernel is modified to make hypercalls, giving the best performance but needing OS changes (Xen, Oracle VM). Hardware-assisted: CPU extensions (Intel VT-x, AMD-V) trap sensitive instructions in hardware, so unmodified guests run with simpler, faster hypervisors; MMU (EPT/RVI) and I/O (VT-d/AMD-Vi) extensions extend this. vMotion live-migrates a running VM between ESX hosts without downtime: vCenter checks compatibility, registers the VM on the target, copies memory and state while tracking changed pages in a bitmap, briefly quiesces the VM, copies the bitmap, starts it on the target, makes a final memory copy and unregisters it from the source; shared VMFS storage means disks do not move.
