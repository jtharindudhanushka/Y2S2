1. Cloud management and software deployment (slides 3–5)

Cloud management is the process of controlling and monitoring cloud-based computing resources, storage, networks, applications, security policies, and users & access permissions. It ensures resources are available, secure, efficiently used, properly monitored and cost-effective.

Software deployment is the process of making an application available for users. Lifecycle:

Resource provisioning = allocating computing resources to an application: virtual machines, containers, databases, storage, network connections and security groups (virtual firewalls that say which traffic may reach a resource).

3. Load balancing (slides 8–9)

A load balancer distributes incoming network traffic among multiple servers or application instances.

Figure 2 — Slide 8: without vs with a load balancer.

Benefits: improved performance · higher availability · better use of resources · reduced risk of failure · supports horizontal scaling. The LB also runs health checks and stops sending traffic to a failed server.

Type (slide 9)Works atRoutes by / used for
Application load balancingApplication layer (Layer 7, HTTP)URL paths, hostnames, HTTP headers, application content. E.g. /images/* to image servers, /api/* to API servers
Network load balancingNetwork/transport layer (Layer 4, TCP/UDP)IP address and port only; very fast. High-performance apps, TCP/UDP traffic, low latency
Global load balancingAcross regions (often via DNS)Sends users to the nearest/healthy region: lower latency, survives regional failure, less pressure on one data centre

How it picks a server (standard algorithms): round robin (1, 2, 3, 1, 2, 3…), least connections (the server with fewest active connections), weighted (bigger servers get more). Example: 6 requests, round robin over 3 servers ⇒ S1 gets requests 1 and 4, S2 gets 2 and 5, S3 gets 3 and 6.

4. Auto-scaling (slides 10–12)

Auto-scaling automatically increases or decreases cloud resources according to demand. Slide 10: normal traffic ⇒ 2 instances; high traffic ⇒ 8; low traffic ⇒ back to 2.

Common scaling metrics: CPU utilization · memory usage · number of requests · queue length · response time · schedule / time of day.

Scaling type (slide 11)MeaningExample
HorizontalAdding or removing instancesServers 2 → 6
VerticalIncreasing the power of an existing serverMore CPU or memory
AutomaticResources change automatically based on rulesAdd servers when CPU > 70%

Horizontal scaling is often preferred in the cloud because it improves availability and supports distributed applications.

Worked example: how many instances?

Each instance handles about 200 requests/s at 70% CPU. Rule: keep CPU near 70%; min 2, max 10. Traffic: 300 req/s at night, 1,500 req/s in a sale.

TrafficCalculationInstances
300 req/s300 / 200 = 1.5 → round up = 2 (also the minimum)2
1,500 req/s1,500 / 200 = 7.5 → round up8
3,000 req/s3,000 / 200 = 15, but max is 1010 (each runs hotter; raise the max or optimise)
Benefits (slide 12)
  • Handles unexpected traffic
  • Improves application availability
  • Reduces manual work
  • Avoids paying for unnecessary resources
  • Supports business growth
Challenges
  • Poorly configured rules may cause instability (scaling up and down repeatedly, "flapping")
  • Scaling may take time (new instances need minutes to boot)
  • Some applications are difficult to scale (they keep state on one server)
  • Databases may become bottlenecks
  • Sudden traffic increases can raise costs

Auto-scaling should be combined with monitoring, testing and cost controls.

5. Kubernetes (Lecture 06 slides 13–18; Part II slide 2)

5.1 The problem and the answer

The problem: your app is packaged into containers, and now there are dozens or thousands running across many machines. Who decides which machine runs which container? What happens when a machine dies? How do containers find each other?

The answer: Kubernetes is a container orchestrator, an open-source platform for deploying, managing and scaling containerized applications. You describe what you want ("run 3 copies of this app") and Kubernetes places, monitors, restarts and scales your containers across a cluster of machines automatically. It helps organisations: run containers across multiple machines · automatically restart failed containers · scale applications · perform software updates · manage networking and service discovery · maintain the desired application state.

Why containers? (slide 14) A container packages the application, its libraries and configuration. Advantages: consistent behaviour across environments, faster startup than VMs, efficient use of resources, easier deployment, simplified dependency management.

Key idea: desired stateKubernetes is declarative: you declare the desired state (e.g. 3 replicas of web:v2). Controllers constantly compare it with the actual state and act to close the gap (start, stop or move Pods). This loop is why it "self-heals".

5.4 Deployment process (slide 17)

Figure 4 — From code to users (slide 17).
  1. Build the application.
  2. Create a container image.
  3. Store the image in a container registry.
  4. Write a Kubernetes deployment file (YAML).
  5. Apply the configuration to the cluster (kubectl apply).

deployment.yaml (worked example)Meaning
apiVersion: apps/v1 kind: DeploymentThis document describes a Deployment
metadata: name: webIts name is "web"
spec: replicas: 3Desired state: 3 Pods
selector: matchLabels: {app: web}Manage the Pods labelled app=web

If a node dies and one Pod is lost, the Deployment controller sees 2 ≠ 3 and the scheduler starts a new Pod on another node. Changing image to v3 triggers a rolling update.

5.5 Self-healing and updates (slide 18)

Self-healing
  • Restarting failed containers
  • Replacing unhealthy Pods
  • Rescheduling workloads on available nodes
  • Maintaining the desired number of replicas
Also supports
  • Rolling updates: replace Pods a few at a time with the new version, so the app never goes fully down
  • Rollbacks: return to the previous version
  • Health checks (probes): test whether a container is alive/ready
  • Automated service discovery

Rolling update trace (3 replicas, v1 → v2): start v1 v1 v1 → add one v2 → when healthy remove one v1 (v1 v1 v2) → v1 v2 v2 → v2 v2 v2. At every step some Pods serve users: zero downtime. If v2 fails its health checks, kubectl rollout undo returns to v1.

6. Pods from scratch (Lecture 06 Part II)

6.1 The apartment analogy (slide 3)

ApartmentKubernetes Pod
Roommates share one street address and one set of utilities (water, electricity); they walk between rooms freely; if the building is demolished all roommates are displaced together.Containers in a Pod share one network address (IP) and, optionally, storage volumes; they are always scheduled onto the same node; if the Pod is removed every container in it goes with it.
apartment = Pod · address = Pod IP · utilities = shared volumes · roommates = containers. A Pod is not a container: it is a thin wrapper that holds one or more containers plus the resources they share.

6.2 What is a Pod, formally? (slides 4–5)

The smallest deployable unit in Kubernetes. Kubernetes never schedules a bare container; it always schedules a Pod.

  1. Shared context: containers share the same network namespace and, optionally, storage volumes.
  2. Co-scheduled: all containers in a Pod are always placed on the same node and scheduled together.
  3. Single IP address: the Pod gets one cluster IP; containers inside talk to each other over localhost.
  4. Ephemeral by design: Pods are disposable — Kubernetes replaces failed Pods rather than repairing them in place.
Without PodsWith Pods
No natural way to say "these two containers must always run together"The Pod spec explicitly groups containers that belong together
No shared network identity for tightly-coupled helpers (logging, proxying)Every container shares one IP and talks over localhost
No shared storage between cooperating containers without extra plumbingA volume declared once in the Pod spec is available to every container

6.3 Anatomy of a Pod (slide 6)

Figure 5 — Every Pod is one network and storage boundary, however many containers it holds (slide 6).

Key facts: one IP per Pod, shared by all containers · containers communicate via localhost · volumes outlive container restarts · init containers run in order, then exit · defined in a single YAML manifest.

6.7 Restart policy and self-healing (slide 14)

restartPolicyBehaviourUsed for
Always (default)Restart no matter how the container exitsWeb servers, APIs
OnFailureRestart only on a non-zero exit code (an error)Batch jobs
NeverNever restart, success or failureOne-shot tasks

What "self-healing" actually means: a crashed container restarts in place, in the same Pod, following the policy, with a growing backoff delay between attempts (status CrashLoopBackOff: it keeps crashing, so Kubernetes waits longer each time: about 10 s, 20 s, 40 s… up to 5 min). But if the Pod itself is deleted or its node fails, nothing recreates it — that is the job of a controller such as a Deployment. Durability lives one layer up.

Worked example: a batch Pod with restartPolicy: OnFailure exits with code 1 ⇒ restarted. Next run exits with code 0 ⇒ not restarted; phase Succeeded. With Never, the first exit code 1 ⇒ phase Failed. With Always a web server that exits even with 0 is restarted.

Key takeaways (Part II slide 15): What — a Pod bundles containers behind one IP and optional shared volumes. Why — "these containers belong together, always". How — YAML (apiVersion, kind, metadata, spec) + kubectl. Behaviour — Pending → Running → Succeeded/Failed; containers restart per policy. Beyond Pods — Deployments recreate lost Pods.

8. Monitoring, security, example, best practices (slides 22–29)

Monitoring and observability (slide 22). Important areas: CPU and memory, response time, error rates, network traffic, active users, deployment success/failure, cloud spending. Observability uses metrics (numbers over time), logs (event records), traces (the path of one request through many services), alerts and dashboards. Goal: find problems before users are seriously affected.

Security in cloud deployment (slide 23): strong IAM · principle of least privilege · encrypt data in transit and at rest · secure container images · update software regularly · store secrets securely · network segmentation · monitor suspicious activity · vulnerability scanning. Security is a shared responsibility between provider and customer.

Example: online shopping application (slide 24) uses containers for app services, Kubernetes to manage them, a load balancer for customer requests, auto-scaling during sales, a managed database for orders, and object storage for product images. During a major sale: more customers → more application Pods → load balancer distributes traffic → application remains available.

Advantages of cloud deployment (slide 25)
  • Faster time to market
  • Flexible resource usage
  • Global availability
  • Automated scaling
  • Easier disaster recovery
  • Reduced physical infrastructure
  • Support for CI/CD
Challenges of cloud management (slide 26)
  • Unexpected costs; security misconfigurations
  • Vendor dependence; complex Kubernetes management
  • Network failures; data privacy concerns
  • Difficult troubleshooting; lack of skilled personnel
  • Poorly designed applications

Best practices (slide 27): automate infrastructure and deployment · load balance critical apps · configure auto-scaling carefully · deploy across multiple failure zones · monitor performance and cost · secure identities, networks and data · test backup and recovery · use containers consistently · keep configurations under version control · review architecture regularly. Cloud technology "does not automatically guarantee a reliable or efficient system".

9. Exam-style questions with model answers

Q1. Define cloud management and software deployment. (4 marks)
Cloud management is the process of controlling and monitoring cloud computing resources, storage, networks, applications, security policies and user access so that they are available, secure, efficiently used, monitored and cost-effective. Software deployment is the process of making an application available to users: develop, test, package, deploy, monitor, update/scale.

Q2. What is Infrastructure as Code? Give two tools and four benefits. (6)
IaC manages infrastructure through code files instead of manual configuration (write, review, deploy, monitor). Tools: Terraform, AWS CloudFormation, Azure Resource Manager, Ansible. Benefits: repeatable deployments, fewer configuration errors, faster creation, version control, better team collaboration.

Q3. What might happen if an application has no load balancer? Describe three types of load balancing. (7)
All traffic hits one server; under load it becomes slow or unavailable, and it is a single point of failure; horizontal scaling is impossible. Application LB: layer 7, routes by URL path, hostname, headers, content. Network LB: layer 4, routes TCP/UDP traffic by IP and port, high performance, low latency. Global LB: distributes users across geographic regions to cut latency and survive regional failures.

Q4. Why is auto-scaling useful during unexpected traffic increases? State two challenges. (5)
It adds instances automatically when metrics such as CPU, requests or queue length rise, so the application stays available and responsive without manual action, and removes them afterwards so you do not pay for idle capacity. Challenges: badly configured rules cause instability; scaling takes time; some apps or databases are hard to scale; sudden spikes raise costs.

Q5. Distinguish horizontal and vertical scaling. (3)
Horizontal: add or remove instances (2 → 6 servers); improves availability, preferred in the cloud. Vertical: make one server more powerful (more CPU/RAM); limited by machine size.

Q6. What problem does Kubernetes solve? Describe its architecture. (8)
With many containers across many machines, someone must decide placement, restart failures, scale, update and connect them. Kubernetes is a container orchestrator that does this automatically to maintain a declared desired state. A cluster has a control plane (API server: entry point; scheduler: places Pods on nodes; controller manager: keeps actual state equal to desired; cluster database: stores state) and worker nodes (kubelet: runs and reports Pods; container runtime: runs containers; kube-proxy: networking for Services) that host Pods.

Q7. Explain Pod, Deployment, Service, Ingress, ConfigMap/Secret and Namespace. (6)
Pod: smallest deployable unit with one or more containers. Deployment: desired number and version of instances. Service: stable network access to a group of Pods. Ingress: external HTTP/HTTPS access. ConfigMap/Secret: configuration values and sensitive data. Namespace: separates resources within a cluster.

Q8. What is a Pod? Why does Kubernetes schedule Pods rather than containers? (6)
A Pod is a thin wrapper around one or more containers that share one network namespace (one IP, talk over localhost) and optional storage volumes, are always co-scheduled on the same node, and are ephemeral. Kubernetes uses Pods because they explicitly group containers that must run together, give tightly coupled helpers a shared network identity, and let cooperating containers share volumes without extra plumbing.

Q9. Explain the sidecar pattern and the init container with examples. (6)
Sidecar: a helper container in the same Pod as the app, e.g. the app writes logs to a shared emptyDir volume and a fluentd log-shipper reads and forwards them; teams can change each independently while they still scale and schedule together. Init container: runs to completion before app containers start, e.g. wait-for-db loops nc -z db 5432 every 2 s and the app starts only after the database is reachable; multiple init containers run in order.

Q10. Describe the Pod lifecycle phases and the three restart policies. Does restarting a container recreate a deleted Pod? (8)
Pending (accepted, waiting for scheduling/images), Running (bound to a node, at least one container running), Succeeded (all exited successfully, no restart), Failed (all exited, at least one with error), Unknown (state cannot be confirmed, lost contact with node). Policies: Always (default, web servers), OnFailure (restart on non-zero exit, batch jobs), Never (one-shot). Restarts happen in place with growing backoff (CrashLoopBackOff). No: if the Pod is deleted or its node fails nothing recreates it; a controller such as a Deployment must do that.

Q11. How can an organisation reduce unnecessary cloud costs? Why design for failure? (6)
Auto-scaling, shutting down unused resources, right-sizing instances, reserved/discounted pricing, monitoring usage with budgets and alerts, storage tiers, removing unused disks/IPs/snapshots, serverless for suitable workloads. Design for failure because in large systems failures will occur; using multiple AZs, no SPOFs, load balancers, replication, automated recovery, health checks, backups and tested DR plans keeps the service running.
