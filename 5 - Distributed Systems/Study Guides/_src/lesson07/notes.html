1. Why cloud storage matters (slide 3)

Numbers on the slide: 181 ZB of global data created/replicated by 2025 (IDC estimate); 99.999999999% (11 nines) designed object durability for Amazon S3; distributed file systems like GFS built to reach exabytes (1 EB = 1018 bytes = a million terabytes).

ForceWhy it pushes storage to be distributed
ScaleSingle machines cannot hold or serve modern datasets
DurabilityHardware fails constantly at scale, so redundancy must be automatic
ElasticityStorage must grow and shrink independently of compute

So storage designs go in one direction: decoupled, distributed and fault-tolerant.

3. Google File System (GFS) (slides 11–13)

AspectSlide 11
Design philosophyAssumes hardware failure is the norm, not the exception — reliability comes from software-level replication, not fault-tolerant hardware
Workload fitOptimised for large files (100 MB+) with sequential reads and append-heavy writes — not general-purpose small-file access
ConsistencyDeliberately relaxed/weak, traded for higher throughput on Google's workloads (crawling, indexing, MapReduce I/O)
LegacyIts master/chunkserver design directly inspired HDFS and later systems

GFS architecture (slide 12)

Figure 2 — A single Master holds metadata; chunkservers store replicated 64 MB chunks; data flows client ↔ chunkserver directly.
  1. Metadata request: the client turns "byte offset in file" into a chunk index (offset ÷ 64 MB) and asks the Master for that chunk.
  2. Chunk location: the Master replies with the chunk handle (ID) and which chunkservers hold its replicas. The client caches this.
  3. Data transfer: the client reads/writes the data directly with a chunkserver. The Master never touches the data.

Replication: each 64 MB chunk is replicated 3× by default across chunkservers (often across racks), so losing any single machine never loses data. Key design choice: separating the metadata path (through the Master) from the data path (client ↔ chunkserver) stops the Master becoming a throughput bottleneck, even though it remains a single point of coordination.

Worked example: chunks and replicas

A 1 GB (1,024 MB) log file in GFS: 1,024 ÷ 64 = 16 chunks. With 3× replication: 16 × 3 = 48 chunk replicas, using 3 GB of raw disk. To read byte offset 200 MB the client asks for chunk index ⌊200 ÷ 64⌋ = 3 (the 4th chunk, counting from 0). The Master stores only a small metadata record per chunk; the 1 GB of data never passes through it.

GFS consistency model and limitations (slide 13)

Consistency model
  • Relaxed rather than strict: favours throughput over strict correctness guarantees.
  • Concurrent writes to the same region may leave it "consistent but undefined": all replicas hold the same bytes, but they may be a mix of fragments from several writers, so no single write is visible whole.
  • Record appends are at-least-once: if an append fails on one replica the client retries, so duplicates and padding are possible.
  • Applications must tolerate this (checksums, unique record IDs to drop duplicates).
Key limitations
  • Single Master is a metadata bottleneck and historical single point of failure.
  • Poor fit for many small files (all metadata in Master memory).
  • Not for low-latency random writes or interactive apps.
  • Tightly coupled to Google's workloads — never released as a product.

4. Hadoop Distributed File System (HDFS) (slides 14–17)

An open-source file system heavily inspired by GFS, built for the Apache Hadoop ecosystem. Originally built to support MapReduce; now underlies Spark, Hive and more. Widely deployed outside any single company, on commodity hardware, on-premises or in the cloud.

GFS termHDFS termRole
MasterNameNodeHolds metadata (namespace, block locations)
ChunkserverDataNodeStores the actual data blocks
Chunk (64 MB)Block (128 MB default)Unit of storage and replication; 3× by default
Figure 3 — HDFS (slide 15): Active/Standby NameNodes for high availability; DataNodes with rack-aware replicas (block A: 2 copies on rack 1, 1 on rack 2).
  • High availability: an Active NameNode serves requests; a Standby NameNode keeps in sync through the shared edit log (the journal of every metadata change) and takes over if the active fails. This fixes the original single point of failure.
  • Rack awareness: HDFS deliberately places replicas across racks (e.g. 2 copies on one rack, 1 on another), so a whole rack or its top-of-rack switch failing never loses data — a refinement beyond GFS's original design. Two on the same rack keeps write traffic cheaper; one elsewhere protects against rack loss.

HDFS features and the small-file problem (slide 16)

FeatureExplanation
Write-once, read-manyOptimised for batch analytics (MapReduce, Spark, Hive), not transactional updates. Files are written, closed, then read many times.
128 MB default block sizeLarge blocks minimise metadata and suit sequential scans of huge datasets.
Erasure coding (HDFS 3.x)Reed-Solomon coding stores data blocks plus a few calculated parity blocks; lost blocks can be rebuilt from the rest. Storage overhead drops to ~1.5× instead of 3×, at extra CPU cost to rebuild.
Small-file problemEvery file's and block's metadata lives in NameNode RAM; millions of small files can exhaust memory and hurt performance.

Worked example: replication vs erasure coding, and small files

CaseCalculation
Store 600 MB with 3× replication600 × 3 = 1,800 MB raw disk; survives losing any 2 copies
Same 600 MB with Reed-Solomon RS(6,3): 6 data blocks + 3 parity blocksRaw = 600 × 9/6 = 900 MB (1.5×); survives losing any 3 of the 9 blocks, but rebuilding needs CPU
1 GB stored as one file vs as 10,000 files of 100 KBOne file = 8 blocks (128 MB) ⇒ ~9 metadata objects. 10,000 small files = 10,000 file entries + 10,000 blocks ⇒ ~20,000 objects in NameNode RAM for the same data: about 2,000× the metadata.

5. Amazon S3 (slides 18–21)

A managed object storage service — not a traditional distributed file system.

ConceptMeaning
BucketTop-level container for objects; globally unique name; bound to one AWS region
ObjectThe unit of storage: data plus metadata, addressed by a key inside a bucket
KeyThe unique identifier of an object in a bucket. Flat namespace: "folders" are just key prefixes (photos/2026/cat.jpg is one key)
REST APIAll access (console, CLI, SDKs) goes through HTTP(S) calls: GET, PUT, DELETE, LIST
PUT    https://my-bucket.s3.amazonaws.com/photos/2026/cat.jpg   # upload (whole object)
GET    https://my-bucket.s3.amazonaws.com/photos/2026/cat.jpg   # download
GET    https://my-bucket.s3.amazonaws.com/?prefix=photos/2026/  # LIST keys with this prefix
DELETE https://my-bucket.s3.amazonaws.com/photos/2026/cat.jpg

Durability and replication (slide 19)

  • 99.999999999% ("11 nines") designed durability per year. Intuition: store 10 million objects and you would expect to lose one about once every 10,000 years.
  • Multi-AZ by default: objects stored redundantly across multiple Availability Zones in the region; a whole AZ can fail without data loss.
  • No server management: replication, hardware failures and scaling are handled internally; users never provision nodes.
  • Versioning: keeps every version of an object (protects against accidental overwrite/delete). Cross-Region Replication (CRR): asynchronously copies objects to a bucket in another region. Object Lock: WORM (write once, read many) protection for compliance (retention periods, legal holds).

Durability vs availability: durability = the data is not lost; availability = you can reach it right now. S3 can be briefly unreachable yet still durable.

Lifecycle policies move objects between classes automatically as they age. Example: website images in Standard → after 30 days to Standard-IA → after 1 year to Glacier Deep Archive for a 7-year legal retention.

Consistency and access control (slide 21)

Consistency model
  • Strong read-after-write consistency for all requests since December 2020.
  • Applies to new-object PUTs, overwrite PUTs and DELETEs alike.
  • Replaced the earlier eventual consistency for overwrites/deletes.
  • Simplifies apps: no stale reads after a write.
Security & access control
  • IAM policies: which users/roles can act on which buckets.
  • Bucket policies: resource-level rules (allow/deny by IP, VPC).
  • Encryption at rest: SSE-S3 (S3-managed keys), SSE-KMS (AWS Key Management Service keys), SSE-C (customer-provided keys).
  • Block Public Access guards against accidental public exposure.

EBS is bound to a single AZ — snapshot it to move across AZs/regions. Point-in-time snapshots are stored durably in S3, incremental after the first (only changed blocks). Volumes can be resized and their type changed without downtime.

EFS: Elastic File System (slide 25)

A fully managed, elastic NFSv4 file system shared across many instances and AZs. Storage classes: EFS Standard (frequent, multi-AZ), EFS Standard-IA (auto-tiers infrequent files, cheaper), EFS One Zone / One Zone-IA (single AZ, cheaper); lifecycle management moves files between classes. Throughput modes: bursting (throughput scales with storage size, with burst credits), provisioned (fixed throughput regardless of size), elastic (scales up/down automatically with the workload). Grows and shrinks automatically — no capacity planning.

7. DFS design trade-offs (slide 27)

Trade-offExplanation
1. Consistency vs availabilityStrong consistency costs latency/availability during partitions; eventual consistency improves availability but risks stale reads. GFS/HDFS are relaxed; S3 is strong (CAP, Lesson 4).
2. Metadata: centralized vs distributedA single master (GFS) is simple but a scaling/SPOF risk; distributed metadata (Ceph, HDFS Federation) scales further but needs consensus protocols (Paxos/Raft) so the metadata servers agree.
3. Replication strategyFull 3× replication is simple and fast to recover but costly; erasure coding cuts storage to ~1.5× at the cost of CPU-heavy rebuilds.
4. Block size and access patternLarge blocks (64–128 MB) suit sequential big-file workloads; small blocks suit random access but blow up metadata overhead.

Key takeaways (slide 28): (1) match storage type to access pattern; (2) GFS and HDFS pioneered the master/worker DFS pattern with relaxed consistency for large sequential batch work; (3) S3 is a different design point: managed object storage trading file-system semantics for massive scale and near-zero operations; (4) AWS pairs S3 with EBS (block) and EFS (file), each with its own durability, scaling and cost model; (5) storage design is a continuous set of trade-offs: consistency vs availability, replication cost vs durability, latency vs throughput.

8. Exam-style questions with model answers

Q1. Compare block, file and object storage with an example and a use case of each. (9 marks)
Block: data in fixed-size independently addressable blocks; the OS puts a file system on top; lowest latency, random read/write; usually attached to one VM; scales per volume; for databases and boot volumes (AWS EBS). File: hierarchical directories and files accessed over NFS/SMB with POSIX semantics (permissions, locking); many clients mount it at once; medium scalability; for shared home directories, CMS, lift-and-shift apps (AWS EFS). Object: flat namespace of immutable objects (data + rich metadata + unique key) accessed by REST HTTP calls; higher latency but virtually unlimited scale; for backups, static assets, data lakes, media archives (Amazon S3).

Q2. Draw and explain the GFS architecture, including how a read works. (8)
(Draw Figure 2.) A single Master stores all metadata (namespace, file-to-chunk mapping, chunk locations); many chunkservers store 64 MB chunks, each replicated 3× across chunkservers/racks. Read: the client computes the chunk index from the byte offset and asks the Master; the Master returns the chunk handle and replica locations; the client then reads the data directly from a chunkserver. Separating the metadata path from the data path keeps the Master from becoming a throughput bottleneck.

Q3. Describe the GFS consistency model and two limitations. (5)
GFS uses relaxed consistency for throughput: concurrent writes can leave a region consistent but undefined (same bytes on all replicas but mixed fragments), and record appends are at-least-once, so duplicates and padding can occur; applications use checksums and unique IDs. Limitations: the single Master is a metadata bottleneck and single point of failure; poor for many small files; not for low-latency random writes; never released as a product.

Q4. How does HDFS improve on GFS? (6)
HDFS is open source (Apache Hadoop); uses a NameNode/DataNode design with 128 MB blocks (less metadata); provides high availability with Active/Standby NameNodes synchronised by the edit log, removing the SPOF; uses explicit rack awareness (e.g. two replicas on one rack, one on another) to survive rack failures; and supports erasure coding in 3.x, cutting overhead from 3× to about 1.5×.

Q5. What is the small-file problem in HDFS? (3)
All file and block metadata is held in NameNode RAM, so millions of small files create millions of metadata entries that can exhaust NameNode memory and slow it down, even when the total data is small.

Q6. Compare 3× replication with erasure coding. (4)
3× replication keeps three full copies: simple, fast recovery, but 200% storage overhead. Erasure coding (Reed-Solomon) stores data plus parity blocks and rebuilds lost blocks mathematically: ~1.5× storage, but rebuilding costs CPU and is slower.

Q7. Explain buckets, objects and keys in S3, and how S3 achieves durability. (6)
A bucket is a globally uniquely named, region-bound container; an object is data plus metadata; a key uniquely identifies an object in a bucket, in a flat namespace where "folders" are key prefixes; all access is through the REST API. S3 is designed for 11 nines durability by storing objects redundantly across multiple AZs automatically, with versioning, cross-region replication and Object Lock for further protection.

Q8. What consistency model does S3 provide today? Why does it matter? (3)
Strong read-after-write consistency for all PUTs (new and overwrite) and DELETEs since December 2020, replacing eventual consistency for overwrites and deletes. Applications no longer need to handle stale reads after a write.

Q9. Recommend S3 storage classes for: website images, unknown access pattern, 7-year compliance archive. (3)
S3 Standard (frequent, milliseconds); S3 Intelligent-Tiering (unknown/changing pattern, auto-optimised); Glacier Deep Archive (lowest cost, retrieval up to 12 h), ideally with Object Lock.

Q10. Compare S3, EBS and EFS. (6)
S3: object, accessed by API, unlimited scale, higher latency, backups/data lakes, 11 nines multi-AZ. EBS: block, attached to one EC2 instance, fixed but resizable, lowest latency, databases/boot volumes, single AZ with snapshots to S3. EFS: file (NFS), shared by many instances across AZs, elastic, low-medium latency, shared content/home directories, multi-AZ in Standard class.

Q11. Classify GFS, HDFS and S3 as block, file or object storage and justify. (Assignment Part B) (6)
GFS and HDFS are distributed file systems: they expose a hierarchical namespace of files and directories, internally split into large chunks/blocks stored on many servers. S3 is object storage: a flat namespace of immutable objects with metadata, addressed by key via a REST API, with no real directories or in-place updates.

Q12. Discuss four design trade-offs when building a distributed file system. (8)
Consistency vs availability (strong costs latency/availability under partitions; eventual risks stale reads). Centralized vs distributed metadata (a single master is simple but a bottleneck/SPOF; distributed metadata scales but needs Paxos/Raft consensus). Replication strategy (3× is simple and quick to recover but costly; erasure coding saves space but costs CPU on rebuild). Block size (large blocks suit sequential big files and small metadata; small blocks suit random access but inflate metadata).
